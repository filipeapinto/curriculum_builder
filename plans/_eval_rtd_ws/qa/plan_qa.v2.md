## Findings

### 1. High — `retry.py` and `test_retry.py` are already in the baseline `git status --porcelain`, so verification step 1 fails at baseline and the step-6 delta assertion cannot hold

**Evidence.** `git status --porcelain` in `/Users/filipepinto/Projects/curriculum_builder` today contains, among 74 entries:

```
A  runtime/retry.py
A  tests/runtime/test_retry.py
```

Both files are staged additions — they have never been committed, so they do not appear in `git diff --name-only` (which returns the six paths the plan correctly names in step 0.4), but they do appear in `git status --porcelain`, which is the command the plan chose for its snapshot. Against that:

- Verification step 1 says the snapshot is a **pass** only if "`runtime/retry.py` and `tests/runtime/test_retry.py` do not already appear in it". They do. Step 1 fails at baseline, before any edit, and section 0 is framed as fail-fast ("stop rather than adapt").
- Verification step 6 and the matching acceptance criterion require the post-change set to differ from the baseline "**only** by the addition of `runtime/retry.py` and `tests/runtime/test_retry.py`", and then state "No pre-existing entry may disappear or **change status**; if one has, uncommitted work was disturbed and that must be reported immediately". Editing a staged-added file changes its porcelain code from `A ` to `AM` — it is a status change of a pre-existing entry, not an addition. The same repository already demonstrates this exact transition on three paths: `AM plans/simplification/prompt/implement_curriculum_runtime.prompt.v6.md`, `AM runtime/run_curriculum.py`, `AM runtime/session_bridge.py`.

**Impact.** The plan's first verification step is red at baseline with no stop condition covering it, and the two files whose modification is the entire point of the plan are exactly the ones the snapshot rule says must not already be there. If the implementer proceeds anyway, the post-change delta shows two pre-existing entries changing status, which the plan itself defines as evidence that "uncommitted work was disturbed and that must be reported immediately" — a guaranteed false alarm on the plan's own work, and one acceptance criterion that can never be satisfied. This is the same class of defect as round-1 finding 2, relocated rather than removed.

**Minimal required remediation.** State in step 0.4 that `runtime/retry.py` and `tests/runtime/test_retry.py` are already staged additions (`A `) in the baseline snapshot, and rewrite verification step 1's pass condition accordingly (they are expected to appear as `A `; what must not appear is an `M`/`AM` worktree modification of either). Rewrite verification step 6 and its acceptance criterion so the permitted delta is "the porcelain codes of `runtime/retry.py` and `tests/runtime/test_retry.py` change from `A ` to `AM`, and nothing else changes" instead of "addition of two paths".

### 2. High — Verification step 4(b) asserts something test 3.6 is designed to contradict

**Evidence.** Verification step 4 says pass "requires both: (a) ... and (b) **the new tests from step 3**, run against the unmodified source, error with `AttributeError: 'RetryTracker' object has no attribute 'begin_unit'`". Step 3 defines six tests, 3.1–3.6. Test 3.6 (`test_tracker_without_begin_unit_is_unchanged`) is explicitly specified as asserting "the pre-existing single-unit behaviour still holds **when `begin_unit` is never called**" — so it cannot raise `AttributeError`, and it passes against the unmodified source. I confirmed this empirically: with all six tests written as specified and run against unmodified `runtime/retry.py` in `/tmp/rtqa2`, the result is `Ran 9 tests ... FAILED (errors=5)` — five `AttributeError`s and test 3.6 passing.

**Impact.** Verification step 4 as written can never pass, and step 4 is a "pass requires both" gate. Worse, the result file mandate requires recording "the 4(b) `AttributeError` observations"; an implementer taking 4(b) at face value would record that all new tests errored with `AttributeError`, which is false, putting an incorrect observation into the plan's own evidence record. Failing 4(b) is also not covered by any stop condition (only 4(a) is), so the implementer is left with an unpassable step and no prescribed route.

**Minimal required remediation.** Scope 4(b) to the five tests that call `begin_unit` — e.g. "tests 3.1–3.5, run against the unmodified source, error with `AttributeError: 'RetryTracker' object has no attribute 'begin_unit'`; test 3.6 passes against the unmodified source by design, since it never calls `begin_unit`."
