# RetryTracker Per-Unit State Reset Plan v1 — Focused QA

## Verdict

**CHANGES REQUIRED — 0 Critical, 3 High.** The plan's technical core is sound and its factual claims about the source check out: `runtime/retry.py` matches the described baseline exactly, `RetryTracker` has no production instantiation anywhere (only `runtime/retry.py`, `tests/runtime/test_retry.py`, and planning/eval material reference it), `python3 -m unittest discover -s tests/runtime -t .` reports `Ran 47 tests` / `OK`, and the three quoted `policy/limits.v1.yaml` entries and rationales are verbatim correct. I applied the proposed `begin_unit` verbatim to a scratch copy under `/tmp/rtqa` and wrote tests 3.1–3.6 as specified: the code works, mutates no configuration, and breaks nothing — no gate is sensitive to it (`FR-P5-ENGINE-GENERIC` only scans for `curricula/<name>/` paths and check ids). What blocks approval is the verification layer, not the fix: test 3.1's threshold arithmetic is off by one and, taken literally, fails *after* the correct change; the git-cleanliness acceptance criteria are unsatisfiable at this repository's baseline and invite reverting unrelated uncommitted work; and the gate comparison in verification step 7 refers to a baseline the plan never instructs anyone to capture, while two gates are already red.

## Findings

### 1. High — Test 3.1 as specified fails against the *fixed* source

**Evidence.** Plan 3.1 says to "assert that the same non-narrowing set can be submitted `repeat_threshold` times again before `RetryLimit` is raised". `revision()` raises when `self.failures[key] >= self.repeat_threshold`, so with the default `repeat_threshold=2` only **one** further non-narrowing submission succeeds and the second raises — which is exactly what the pre-existing `test_repeat_failure_limit` at `/Users/filipepinto/Projects/curriculum_builder/tests/runtime/test_retry.py:21-26` demonstrates. I applied the plan's `begin_unit` to `/tmp/rtqa/runtime/retry.py` and wrote 3.1 literally (loop `range(t.repeat_threshold)` of successful submissions, then `assertRaises`): it errors with `RetryLimit: repeated failure set did not narrow` on the second loop iteration, against the patched source. The same file's "intended" variant (one success, then raise) passes.

**Impact.** An implementer following 3.1 as written produces a red suite after a correct fix. The acceptance criterion "the runtime suite reports 53 tests, `OK`" then cannot be met, and the plan's stop conditions offer no route out — the plausible reactions are to loosen `revision()` (explicitly forbidden by 2.5 and by the "byte-for-byte unchanged" criterion) or to abandon the step.

**Minimal required remediation.** Restate 3.1's assertion in terms the source actually satisfies: after `begin_unit("unit-2")`, `repeat_threshold - 1` further non-narrowing submissions of the same set succeed and the `repeat_threshold`-th raises `RetryLimit` — i.e. the counter restarts, matching `test_repeat_failure_limit`.

### 2. High — The git-cleanliness acceptance criteria are unsatisfiable at this baseline

**Evidence.** Verification step 6 says "`git diff --stat` — pass means exactly two files changed", and the acceptance criteria say "`git diff --name-only` lists exactly `runtime/retry.py` and `tests/runtime/test_retry.py`" and "`policy/limits.v1.yaml`, `schemas/`, and every module under `runtime/` other than `retry.py` are untouched". At baseline, before any edit, `git diff --name-only` in `/Users/filipepinto/Projects/curriculum_builder` already returns six paths: `plans/simplification/prompt/implement_curriculum_runtime.prompt.v6.md`, `policy/limits.v1.yaml`, `runtime/run_curriculum.py`, `runtime/session_bridge.py`, `schemas/limits.schema.v1.json`, `tests/gates/fr_p4_policy_schemas.py`. Two of the paths the criteria name as "untouched" — `policy/limits.v1.yaml` and `schemas/limits.schema.v1.json` — are among them, as are two `runtime/` modules other than `retry.py`. The plan contradicts itself here: verification step 1 concedes "Other paths in the repository are expected to be dirty and must be left alone."

**Impact.** Two acceptance criteria and one verification step can never pass, so "done" is unverifiable by the plan's own definition. Worse, an implementer treating them as hard gates has an obvious way to make them pass — `git checkout`/`git restore` on the offending paths — which would destroy uncommitted work in `policy/limits.v1.yaml`, `schemas/limits.schema.v1.json`, `runtime/run_curriculum.py`, `runtime/session_bridge.py`, and `tests/gates/fr_p4_policy_schemas.py`.

**Minimal required remediation.** Rephrase both the verification step and the acceptance criteria as a delta against a pre-change snapshot: capture `git status --porcelain` in step 0 and require that the post-change set differs from it only by `runtime/retry.py` and `tests/runtime/test_retry.py`, with an explicit instruction never to revert a pre-existing dirty path.

### 3. High — Gate verification compares against a baseline the plan never captures, and two gates are already red

**Evidence.** Verification step 7 says "`./tests/run_gates.sh <phase>` — pass means the same result as the baseline capture from step 0.3's surrounding context", but step 0.3 captures only the unittest run; no step in section 0 runs the gates. Step 4.2 compounds it: "Run the repository gates for the current phase **if they were green at baseline**". They are not. The most recent phase-5 record, `tests/results/gate_results.p5.20260803T141136.834494Z.json`, shows `FR-P0-NOSTALE FAIL` (8 stale-path hits) and `FR-P0-CLEAN FAIL` (dirty worktree). `FR-P0-CLEAN` fails by construction for any uncommitted change (`tests/gates/fr_p0_structure.py:589-603` fails on any non-empty `git status --porcelain`), so it will still be red after this work. The plan also never names the phase, and the result file mandates recording "the gate result compared to baseline".

**Impact.** By the time step 4.2 is reached the change is already applied, so the baseline is no longer obtainable without stashing a repository that has both staged and unstaged work. The mandated result-file field cannot be produced honestly, and a fresh reader of a post-change gate run sees two FAILs with no way to attribute them — either a false alarm or a tempting, out-of-scope "repair" of `FR-P0-NOSTALE`.

**Minimal required remediation.** Add a step-0 gate baseline: run `./tests/run_gates.sh 5` before any edit and record the result, naming `FR-P0-NOSTALE` and `FR-P0-CLEAN` as known-red and `FR-P0-CLEAN` as unavoidably red while the change is uncommitted. Drop the "if they were green at baseline" conditional in 4.2.

## Observations (non-blocking)

- Verification step 4 and the matching stop condition ("the new tests in 3.1–3.3 **pass** against the unmodified source") are vacuous. Against unmodified `runtime/retry.py`, every test that calls `begin_unit` errors with `AttributeError: 'RetryTracker' object has no attribute 'begin_unit'` — verified in `/tmp/rtqa`. The check can never trigger and proves nothing about the reset defect, since a missing attribute would fail identically whether or not the reset semantics are correct.
- Test 3.6 as specified is a character-for-character duplicate of the existing `test_repeat_failure_limit` (`/Users/filipepinto/Projects/curriculum_builder/tests/runtime/test_retry.py:21-26`); it passes before and after the change.
- `RetryTracker` has no caller in any `runtime/` module (a grep for `revision|retry|repeat_threshold|max_revisions` across `runtime/*.py` excluding `retry.py` returns nothing), so `begin_unit` ships as dead code until a wiring change happens. The plan discloses this in its scope section, so it is recorded here rather than as a finding.
