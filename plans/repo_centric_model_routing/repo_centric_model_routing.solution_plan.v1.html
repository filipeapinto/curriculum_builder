Solution plan · v1 · awaiting approval

Make repository routing authoritative across skills and plans

Replace competing SOTA-local model and measurement rules with versioned repository policy, resolved routing records, explicit project ceilings, and deterministic drift prevention.

IntentSourceScopeWorkFlowVerificationDecisionsRisksDeliveryApproval

Executive intent

Outcome. Every model-bearing repository activity is classified against one repository task taxonomy, resolved through one model registry and routing policy, constrained by one model-work budget/fallback policy, and recorded in a versioned routing decision before execution. Skills describe work and required independence; plans set project-specific numeric ceilings and authority boundaries. Neither may establish competing model eligibility, effort floors, substitutions, measurement hierarchies, or unavailable-metric behavior.

This addresses the verified root cause—non-exclusive routing authority—while preserving the useful distinction between repository policy, skill classification, and project authorization.

Scope and constraints

Included

  • Versioned successors in policy/routing/ for task taxonomy, model registry, routing policy, and model-work budget/fallback policy.
  • New or versioned schemas for the budget policy and routing-decision provenance.
  • SOTA plan-create, plan-execute, role-skill, contract, and template updates needed to consume central routing.
  • Deterministic validators, fixtures, compatibility preflight, repository documentation, and portable package inventory.
  • Read-only handling of issued plans and explicit migration rules for future plan versions.

Excluded and non-goals

  • No retrospective editing of issued plans, reports, execution logs, or deprecated schemas.
  • No claim that policy declarations alone provide runtime enforcement.
  • No execution of SOTA research or modification of external work-lib artifacts.
  • No broad redesign of curriculum generation, quality gates, or controller lifecycle beyond routing/budget integration points.
  • No guarantee that a registered model is available in every runtime.

Constraints

  • Existing versioned policies and schemas remain byte-unchanged; successors use the next repository version.
  • The active runtime remains authoritative for availability, but substitution must stay within the centrally eligible pool and be recorded before affected work.
  • Independent challenge must be routed from an eligible different model family or block; it may not silently degrade to self-review.
  • Project plans retain concrete ceilings, warning thresholds, authority, and approved deviations, but must use the central measurement hierarchy and fallback semantics.
  • Central policy files required by portable skills must be included in a deterministic package/preflight manifest.

Affected components

policy/routing/, routing and limits schemas, selector gates and fixtures, policy/checks.vN.yaml, controller/failure declarations where routing evidence is referenced, the SOTA skill family, SOTA HTML plan template and validator helpers, and routing documentation.
