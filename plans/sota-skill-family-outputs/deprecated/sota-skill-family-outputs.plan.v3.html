SOTA skill-family remediation plan

Version 3 · 19 August 2026 · Predecessor: v2 · Implementation authority: none

1. Decision

Approve a smaller SOTA family contract and the addition of sota-slop-remove.

Do not approve the v2 folder tree, its large schema set, or its separate machine files for every state and stage.

The target is a run that another person can inspect without forcing every study into the same internal layout. The family contract will require evidence, provenance, challenge, verification, and an honest final state. It will not require a directory or schema unless a test depends on it.

3. Question, scope, and exclusions

Question. What is the smallest shared contract that makes SOTA runs reproducible, reviewable, and hard to misreport?

Intended decision. Decide which family rules, files, skill changes, and tests to implement.

In scope. The eight installed sota-* skills, their direct references, the family guide, the two audited runs, the plan and report formats, and the proposed sota-slop-remove skill.

Out of scope. Rewriting historical runs, inventing missing provenance, executing a new SOTA study, or changing unrelated skills.

Evidence boundary. Repository files, the two audited run packages, current skill contracts, user feedback, and the Pstack unslop source. Claims outside those sources remain unverified.

4. Minimal contract

Required run structure

research/<effort>/
├── plan/
│   └── <effort>.plan.vN.html
└── runs/<run-id>/
    ├── run.yaml              identity, plan digest, executors, status, outputs
    ├── evidence.jsonl        sources, exclusions, extractions, claim links
    ├── report.html           human-readable result
    └── verification.json     deterministic and semantic checks

Study-specific files may sit below the run directory. The approved plan names them. They do not become family requirements.

Conditional files

  • events.jsonl is required only when a run is resumed, delegated across processes, or expected to exceed four hours.
  • Raw source copies, incident timelines, benchmark outputs, and challenge working files are required only when the approved method needs them.
  • External outputs may remain elsewhere when run.yaml records their path and digest.

Four final fields

execution: NOT_STARTED | RUNNING | BLOCKED | FAILED | COMPLETE
evidence_conclusion: NOT_ASSESSED | INCONCLUSIVE | PARTIAL | SUPPORTED | CONTRADICTED
verification: NOT_RUN | FAIL | PASS
human_decision: PENDING | ACCEPTED | REJECTED | REVISION_REQUESTED

PASS does not mean accepted. Implementation remains unauthorized unless the human owner gives separate, explicit authority.

6. sota-slop-remove

The new skill will adapt Lauren Tan's Pstack unslop skill. The source is MIT-licensed. The implementation will retain attribution and record the source commit digest.

When it runs

Run it on every SOTA plan, preliminary report, synthesis report, verification narrative, and final answer. For research execution, it runs after the author completes the draft and before independent challenge. Run it again after material revisions.

What it removes

  • Puffery, promotional language, vague attribution, generic conclusions, chatbot phrases, filler, stacked hedges, and abstract jargon.
  • Forced groups of three, false ranges, repeated bold-label lists, title-case headings, decorative presentation, and sentences that could be pasted into an unrelated report unchanged.
  • Claims about importance, quality, maturity, readiness, or confidence that lack evidence or a defined test.

What it must preserve

  • Meaning, evidence IDs, citations, quotations, numbers, confidence, limitations, dissent, and decision status.
  • Required technical terms when a plain substitute would be less exact.
  • Machine-readable payloads, code, paths, schemas, and source text.

Required self-audit

  1. Mark every sentence that states no fact, instruction, decision, limit, test, or supported interpretation.
  2. Delete it or replace it with the missing concrete content.
  3. Compare the revised report with the findings and evidence. Any semantic difference fails the gate.
  4. Return the cleaned artifact and a short change count. Do not create a second prose report about the cleanup.

7. Method and dependency flow

  1. sota-method-lead inventories current requirements and applies a subtraction test: remove a proposed requirement unless a specific failure and verifier check justify it.
  2. sota-evidence-review traces the two audited runs and current skills to identify the minimum evidence and provenance needed.
  3. sota-incident-analyze is used only if a disputed historical failure needs reconstruction.
  4. sota-synthesize drafts the contract, schemas, validator behavior, skill changes, and migration notes.
  5. sota-slop-remove cleans the human-facing drafts without changing their substance.
  6. sota-independent-challenge tests both under-specification and unnecessary machinery.
  7. sota-verify runs deterministic tests, checks semantic preservation, links, rendering, and the accepted challenge dispositions.
  8. The human owner accepts, rejects, or requests revision. No model grants implementation authority.

Dependency text. Inventory and evidence review may run in parallel. Synthesis waits for both. Slop removal waits for a complete draft. Challenge waits for the cleaned draft. Verification waits for challenge dispositions. Human review waits for verification.

Data flow. Current skills and run evidence enter the method and evidence roles. They produce requirement-to-failure mappings. Synthesis turns those mappings into proposed files and tests. Slop removal edits only the human-readable layer. Challenge returns objections to synthesis. Verification receives the final artifacts and produces verification.json.

Derivation. The evidence set is bounded to eight skills, their direct references, two historical runs, and one external skill. Six extraction calls allow one per major evidence group. Four synthesis calls cover contract, schemas, validator/tests, and final integration. Confidence in these ceilings is medium because file volume is known but defect density is not.

Measurement. Record calls, model, effort, tokens when available, elapsed time, retries, and outputs in run.yaml. Warn at 80% of any ceiling. Stop at 100%. If token or cost measurement is unavailable, use call and elapsed-time ceilings and mark the missing measure.

Hard stops. Stop after 16 total model calls, 8 hours elapsed execution, 2 retries for the same failed operation, 2 slop-removal passes per artifact, or any request for new authority. A retry must change the input or method. Two review passes with no new material defect establish saturation.

9. Acceptance tests

  • A minimal valid run containing the four required artifacts passes.
  • A missing plan digest, source identity, claim-to-evidence link, challenge disposition, or verification result fails.
  • A plan can add study files without changing the family contract.
  • A short study is not forced to create lifecycle, receipt, authority, incident, or terminal-answer directories.
  • The validator catches the known false-pass and provenance defects in the two historical runs without changing them.
  • sota-slop-remove removes seeded puffery, vague claims, generic conclusions, forced triads, filler, and decorative formatting.
  • The slop gate fails if editing changes a number, citation, evidence ID, confidence label, limitation, finding, or decision state.
  • Every paragraph in the final report contains a fact, instruction, decision, limit, test, or supported interpretation.
  • The HTML renders without horizontal overflow and all local links resolve.
  • All Critical and High challenge findings are resolved or explicitly accepted by the human owner.

10. Outputs and approval

Execution will produce the six implementation artifacts in section 5, updates to the existing SOTA role skills and family guide, regression fixtures for both audited runs, and one concise verification report. It will not migrate or rewrite the historical runs.
