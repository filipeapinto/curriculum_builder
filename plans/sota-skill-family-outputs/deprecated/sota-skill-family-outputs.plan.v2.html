3. TO-BE: the proposed operating model

A family contract owns the invariant rules. Plans provide values and may strengthen them. Every run starts from the same templates, writes the same canonical records, passes the same mandatory verifier, and ends with five independent state values.

Family owns

  • Required folders and artifact classes
  • Schema registry and stable IDs
  • Append-only lifecycle events
  • Invocation and provenance receipts
  • Challenge and human-decision records
  • Non-waivable verification
  • Terminal-answer vocabulary

Each plan owns

  • Research question and intended decision
  • Sources, queries, eligibility, and appraisal
  • Corpus, sample, method, and analysis
  • Budget below family safety limits
  • Conditional typed extensions
  • Additional stricter checks

Precedence: a plan may add or tighten requirements; it may not remove, rename, reinterpret, waive, or bypass a family requirement.

Legacy policy: old runs stay unchanged. A read-only tool reports PASS, FAIL, PARTIAL, or UNKNOWN for each new requirement.

  5. CHALLENGE_DISPOSITIONED
  6. EXECUTION_COMPLETED
  7. VERIFICATION_PASSED

No human decision event exists yet.

Final terminal answer

{
  "run_id": "RUN-SOTA-EXAMPLE-20260819-01",
  "research_support": "SUPPORTED",
  "execution": "COMPLETE",
  "verification": "PASS",
  "human_acceptance": "PENDING",
  "implementation_authority": "NONE",
  "plain_language": "Research is supported and mechanically verified, but is not human-accepted and authorizes no implementation."
}

Why this matters: “COMPLETE” and “PASS” can no longer be mistaken for “ACCEPTED” or “AUTHORIZED.”

8. How the remediation would be executed and tested

  1. Freeze the current skills, dependencies, guide, schemas, and both legacy runs.
  2. Finalize four human decisions: schema registry/compatibility, universal vs conditional stages, legacy policy, and approval-authenticity strength.
  3. Create the listed contracts, schemas, templates, validators, tests, and guide.
  4. Create positive examples and negative fixtures reproducing ICF-006–ICF-010.
  5. Map both legacy runs read-only to the new contract.
  6. Independently challenge bypasses, false passes, ambiguous states, over-standardization, and migration risk.
  7. Run deterministic and semantic verification; no mandatory check may be waived.
  8. Return frozen outputs, exact digests, residual risks, and compatibility results for human acceptance.

Acceptance tests

  • A new run from templates has one manifest, event stream, invocation stream, verifier report, authority stream, and terminal answer.
  • Missing IDs, digests, provenance, challenge dispositions, or required artifacts fail validation.
  • A plan that weakens a family rule fails before execution.
  • Both historical packages receive truthful read-only compatibility reports without mutation.
  • All Critical and High findings are resolved before approval.
