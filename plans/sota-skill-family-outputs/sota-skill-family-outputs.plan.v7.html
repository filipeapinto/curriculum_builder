1. Question and intended decision

Primary question. What changes to the installed SOTA skill family will ensure that every new SOTA study uses the same compact output structure, preserves the same minimum evidence and state meanings, and receives the same baseline verification while still allowing study-specific methods?

Intended decision. After implementation evidence and independent verification exist, the human owner will decide whether the revised SOTA family is fit for use on new studies and whether any legacy migration should be authorized.

This plan is a remediation design and execution contract awaiting approval. It does not itself authorize implementation, accept results, alter historical runs, or grant deployment authority.

2. Scope and evidence boundary

In scope

  • A minimal conditional plan template owned by sota-plan-create.
  • The compact plan/run topology selected in report v8.
  • A family contract covering required contents, precedence, extensions, lifecycle, provenance, challenge, verification, and terminal states.
  • Updates to all seven currently installed SOTA skills and their direct references.
  • Reuse or explicit extension of the repository execution-log schema.
  • Deterministic validation, minimal and complex fixtures, and read-only legacy assessment.
  • An updated standalone SOTA family guide and remediation report.

Excluded

  • Changing research questions, evidence sources, instruments, evaluations, or conclusions to make studies identical.
  • Restoring the deleted sota-incident-analyze skill without a separate owner decision.
  • Creating a file or directory for every role or workflow stage.
  • Rewriting historical runs, fabricating missing provenance, or treating compatibility assessment as migration.
  • Unrelated skill families, generic repository plan templates, deployment, or release.

Evidence boundary. The sole originating finding record is report v8. Execution may inspect the current seven installed sota-* skills, their direct references and existing schemas, the two historical run trees named by the report, the current family guide, and repository tests. Plans v1–v6 provide provenance only and are not governing instructions.

Assumptions. Report v8 remains pending human review; therefore this plan also remains awaiting approval. Current working-tree edits and the deletion of sota-incident-analyze belong to the user and must not be reversed. No preliminary study is required because report v8 fixes the remediation classes, the current family is small, and the two required test shapes are known. If schema reuse or lifecycle applicability cannot be resolved within this boundary, stop for a new plan version.

  1. Plans may add or strengthen controls but cannot remove, rename, weaken, or contradict family requirements.
  2. Every run records stable study, plan, run, activity, finding, challenge, verification, and decision identifiers where applicable.
  3. Producer, installed skill/version, actual model/tool/version, effort, time, inputs, outputs, and explicit unknown provenance are recorded.

  6. The final report separately records research support, execution, verification, human acceptance, and implementation authority.
  7. Historical packages are evaluated read-only; absence remains absence.

4. Work plan

  1. Freeze scope and inventory. Record current digests and status for report v8, seven installed skills, direct references, relevant schemas, family guide, and both historical run trees. Do not alter user changes.
  2. Map requirements. Map every report-v8 correction and verified defect class to a contract clause, owning skill, output artifact, and deterministic test. Label report facts, owner decisions, planning choices, and unknowns separately.
  3. Define the family contract. Specify the compact topology, plan/log/report responsibilities, strengthen-only precedence, lifecycle applicability, provenance, challenge, failure, and state semantics.
  4. Create the minimal plan template. Add a family-owned conditional HTML template and remove the requirement to use the LLM-failure plan as the universal structure. Preserve it as a complex example only.
  5. Bind records to schemas. Reuse the existing execution-log contract where compatible. Create only the smallest versioned extensions or report contracts required for otherwise unexpressible invariants.
  6. Update installed skills. Make sota-plan-create, sota-plan-execute, sota-method-lead, sota-evidence-review, sota-synthesize, sota-independent-challenge, and sota-verify produce, consume, and validate the same contract.
  7. Build fixtures and validator. Create one minimal valid study, one complex valid study, and focused invalid fixtures for each baseline rule.
  8. Assess legacy packages. Run the same baseline in read-only mode against both historical runs. Record nonconformance and unknown provenance without migration or repair.
  9. Update documentation. Regenerate the standalone family guide from the implemented skills and contract; document how callers start a study, where outputs appear, how failures route, and what evidence establishes trust.
  10. Synthesize, challenge, correct, and verify. Produce the remediation report and traceability matrix, freeze them for independent challenge, correct accepted findings, run all deterministic checks, and deliver results for human decision.

Eligibility and evidence handling

Include only current family files, directly consumed repository contracts, report-v8 evidence, named historical packages, and tests necessary to prove the corrections. Exclude unrelated schemas and inferred historical events. Cite repository paths and stable IDs. Deterministic inspection establishes existence, syntax, links, hashes, and schema conformance; model judgment is reserved for contract design, classification, synthesis, and challenge.

11. Approval and terminal conditions

Current state: plan AWAITING_APPROVAL; execution NOT_STARTED; verification NOT_RUN; human acceptance PENDING; implementation authority NONE.

Approval requested. Approve or request changes to this plan as the complete remediation contract. Plan approval does not itself authorize implementation; execution begins only after the human owner separately directs execution of this exact version.

Success. All AC-01–AC-13 checks pass, no Critical or High challenge remains unresolved, all required outputs exist, budgets remain within ceilings, legacy digests are unchanged, and the final state envelope is complete.

Blocked. A required dependency or authority decision is missing, a material scope change requires report synchronization, a hard measurement fallback is unavailable, or user-owned/historical data cannot be preserved.

Failed. A required test remains failed after its allowed retry, the hard budget is reached, a historical artifact is modified, or required provenance is fabricated.
