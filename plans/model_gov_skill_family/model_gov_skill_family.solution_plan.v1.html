Build a repository-wide model-governance skill family

Place all model-routing governance in one self-contained package under governance/model-routing/, expose it through four bounded Codex skills, and require every model-bearing workflow to obtain and verify a central routing decision.

IntentSourceScopeTriggersWorkFlowVerificationDecisionsRisksDeliveryApproval

Executive intent

Chosen approach. Create one canonical, portable model-governance package at governance/model-routing/ and a four-member Codex skill family: $model-route, $model-route-verify, $model-route-package, and $model-route-govern. Shared rules, schemas, contracts, fixtures, validators, and packaging metadata live only in the governance package. The skills are bounded interfaces over that package; other skills call the family instead of owning private routing rules.

Scope and constraints

Included

  • Canonical governance/model-routing/ package with policies, schemas, contracts, fixtures, validators, README, and package manifest.
  • Four Codex skills with distinct authority and trigger boundaries.
  • Migration of active routing manifests, schemas, validators, and SOTA-local allocation behavior into the family architecture.
  • Mandatory routing preflight for model-bearing work, execution-log linkage, post-execution verification, and clean-room package validation.
  • Compatibility treatment for immutable historical plans and records.
  • Family guide documenting entry points, handoffs, failures, outputs, and trust evidence.

Excluded

  • Unrelated governance domains such as security, release approval, general provenance, or non-model resource policy.
  • Retrospective modification of issued plans, reports, logs, or deprecated policies.
  • Silent model substitution, automatic governance mutation, or self-approval by any skill.
  • Guaranteeing model entitlement or provider telemetry unavailable to the runtime.
  • Executing the routing remediation before plan approval.

Consumer trigger rule

Every skill whose workflow can cause a model call must invoke $model-route before that call or consume a still-valid routing decision supplied by its approved execution contract. Every material model result must pass $model-route-verify before downstream acceptance. Deterministic-only activities do not invoke a model and record that classification instead.

Failure routing

  • No eligible or available model → BLOCKED; return to human authority or governance revision.
  • Independent family unavailable → BLOCKED; never substitute self-review.
  • Provider tokens unavailable → apply the centrally authorized proxy; block only if no authorized measure is observable.
  • Decision/execution mismatch → FAIL; preserve evidence and prohibit acceptance.
  • Missing package dependency → run $model-route-package and report the complete missing set once.
  • Required policy change → stop ordinary routing and hand off to explicitly authorized $model-route-govern.

Build $model-route as the universal pre-execution interface

Changes: implement classification, candidate selection, availability check, independence check, budget-mode selection, decision validation, and blocking behavior through canonical package validators. WP-03 · VERIFY SKILL

Build $model-route-verify as the post-execution assurance interface

Inputs: WP-01 decision/execution contracts. Targets: .codex/skills/model-route-verify/. Changes: compare policy and decision provenance, decided/executed model and effort, usage/proxy evidence, substitution/deviation, independence, and log linkage; emit evidence-backed terminal status. Dependencies: WP-01. Owner: verification skill and deterministic comparison capability. Risks: verifier waiving mismatches. Verification: AT-07. Outputs: skill and verification schema/fixtures. Done: every mismatch fixture fails and no verification status grants human acceptance.

WP-04 · PACKAGE SKILL

Build $model-route-package for complete portability

Inputs: WP-01 package manifest. Targets: .codex/skills/model-route-package/. Changes: inventory, validate, export/copy only with authorization, and preflight the complete governance-plus-skill family; report all missing or incompatible dependencies in one result. Dependencies: WP-01. Owner: packaging skill capability. Risks: unauthorized writes or partial copies. Verification: AT-08, AT-09. Outputs: skill, package validator, clean-room fixture. Done: a fresh repository receives a complete usable family without sequential missing-file blockers.

WP-05 · GOVERN SKILL

Build $model-route-govern with restricted mutation authority

Inputs: WP-01 contracts and explicit governance-change authority. Targets: .codex/skills/model-route-govern/. Changes: codify next-version creation, compatibility analysis, immutable predecessors, schema/fixture synchronization, manifest updates, approval state, and migration output. Require an approved issue/plan or explicit authority before writes. Dependencies: WP-01. Owner: governance-maintenance skill capability. Risks: ordinary routing escalating into policy mutation. Verification: AT-09. Outputs: skill and governance-change validator. Done: ordinary requests cannot trigger governance writes and every authorized change produces a complete versioned package.

WP-06 · CONSUMER MIGRATION

Remove private routing authority from other skills and plans

Inputs: WP-02–WP-05, C-04/C-05. Targets: SOTA family, plan graph, execution contracts, active routing callers, templates. Changes: replace model assignments with task classifications and route-decision handoffs; retire active SOTA-local allocation policy after callers migrate; require plans to store decision IDs, governing package versions/digests, concrete ceilings, authority, and approved deviations without redefining eligibility or fallback. Dependencies: WP-02, WP-03. Owner: consumer-skill maintainers. Risks: loss of plan executability. Verification: AT-10–AT-12. Outputs: migrated consumers and sample plans. Done: no active consumer owns routing values and plans remain operationally complete.

WP-07 · ENFORCEMENT AND COMPATIBILITY

Make family invocation observable and non-bypassable

Inputs: WP-02, WP-03, WP-06, PD-03. Targets: execution log schema, preflight/controller gates, checks and fixtures. Changes: require a valid decision ID for every model call; compare decided and executed routes; reject expired, incompatible, unregistered, or unverified decisions; handle historical plans through compatibility check, explicit deviation, or new plan version; keep deterministic operations model-free. Dependencies: WP-06. Owner: runtime and gate capability. Risks: declared but unenforced rules. Verification: AT-10–AT-13. Outputs: executable enforcement and migration matrix. Done: bypass fixtures fail independently of wording and existing safety-critical tests still pass.

WP-08 · FAMILY DOCUMENTATION AND ASSURANCE

Document the family and independently verify the complete system

Inputs: all prior outputs. Targets: governance README, family guide, trigger matrix, final verification report. Changes: document start points, triggers, handoffs, authority, outputs, failure routing, package installation, compatibility, and trust evidence; run the full fixture, clean-room, consumer, and regression suite. Dependencies: WP-04, WP-05, WP-07. Owner: family documentation and independent QA capability. Risks: documentation diverging from validators. Verification: AT-14. Outputs: standalone family guide and final receipt. Done: an unfamiliar agent can select the correct family member and all claims link to executable evidence.

Dependency and execution flow

WP-00 baseline→WP-01 package→WP-02 routeWP-03 verifyWP-04 packageWP-05 govern→WP-06 migrate→WP-07 enforce→WP-08 assure
  1. G-01 approval: source finding acceptance and this plan’s approval are required before implementation.
  2. G-02 baseline: no migration begins until WP-00 accounts for all active and immutable artifacts.
  3. Parallelism: WP-02–WP-05 may run in parallel only after WP-01 passes package validation.
  4. G-03 consumer migration: consumers migrate only after route and verify interfaces pass their own fixtures.
  5. G-04 retirement: no private policy is retired until all active callers pass central routing tests.
  6. G-05 release: package, triggers, enforcement, compatibility, and regression evidence must all pass before declaring completion.
  7. Stop: stop on governance cycles, weakened safety routes, missing family member, unobservable decision/execution linkage, unauthorized mutation, or unavailable independent model family.
  8. Recovery: keep the last valid governance version active, preserve all issued artifacts, and revise only new mutable implementation work through version control.
