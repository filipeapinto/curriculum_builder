# Plan 25 predecessor observations

1. Plan 23 treated prompt-graph evolution as the workload and an immutable promoted
   graph as success. Its population, mutation, fitness, QA-gate, and promotion
   terminals could all complete without a curriculum unit, rendered page, or workbook.
2. Plan 23's graph mechanics—typed state, reducers, explicit execution/context edges,
   correlation keys, immutable artifacts, bounded cycles, and honest failures—remain
   useful only when applied to curriculum production rather than graph candidates.
3. Plan 24 corrected the stated product boundary but made constructing and proving
   factory code the workload. Its P0–P6 sequence ended in implementation proof, so the
   desired curriculum-production graph remained embedded inside a project plan.
4. Plan 24's useful production topology is retained directly: manifest validation,
   capability proof, source research, curriculum domain creation and verification,
   complete unit writing, visuals, rendering, every-page inspection, independent
   product review, targeted repair, acceptance, resume, exact coverage, workbook QA,
   and final audit.
5. Plan 25 removes the extra abstraction. `curriculum_factory.graph.v1.md` is the
   factory that receives runtime inputs and produces accepted curriculum artifacts.
6. Graph engineering is therefore the factory architecture itself: typed production
   state, deterministic control authority, bounded model jobs, explicit context,
   guarded edges, joins, invalidation, repair, resume, and product-only terminals.
7. The active repository already supplies deterministic primitives for manifest
   validation, curriculum verifier fixtures, check catalogues, source/claim checks,
   routing decisions, logging, hashing, retry tracking, checkpointing, rendering,
   page inspection, lifecycle state, and workbook assembly. Their presence does not
   permit a simulation or partial bridge to masquerade as factory success.
8. Active runtime evidence also exposes gaps the graph must fail closed around:
   simulation-only controller acceptance, an in-session authoring bridge, a cross-family
   review bypass, `ACCEPTED_PENDING_REVIEW`, and workbook completion before the complete
   review/release denominator. Plan 25's acceptance conjunctions supersede those paths
   for a factory activation.
9. Prompt quality and graph closure are conformance evidence, not curriculum quality.
   Acceptance evaluates current structured artifacts, visual bytes/provenance, exact
   shipped PDFs, every rendered page, independent findings, and complete raw evidence.
10. Models perform only eight bounded curriculum jobs. Controller code owns validation,
    routing application, state, joins, reducers, counters, rendering commands,
    acceptance, checkpoint/resume, assembly, release audit, and terminals.
11. Repair is versioned and artifact-scoped. Every repairable failure has one owner,
    allowed diff, immutable parent, invalidation/retest closure, biting bound, and
    truthful exhaustion; workbook repair cannot change accepted units.
12. The only success meanings are `UNIT_ACCEPTED` for the requested unit and `COMPLETE`
    for the exact manifest's accepted workbook. Plans 23 and 24 remain unchanged as
    historical rejected approaches.
