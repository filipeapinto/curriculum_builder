# Plan 21 v2 graph-formalism and durable-runtime review — round 1

## Verdict

**CHANGES_REQUIRED — 2 Critical, 4 High, 1 Medium.** The v2 overlay is correctly
bound to the exact v1 plan-manifest bytes, and the old v1 validator still rejects
representative missing-route, future-producer, and unbounded-repair mutations.
The effective v2 graph is nevertheless not compiled, hashed, or statically
validated as one object. More importantly, independent runtime probes admitted
P6 PASS using one meaningless file as all test and artifact evidence, admitted a
fabricated sandbox proof whose engine was plain text and whose roots did not
exist, and admitted the same resume twice when both calls observed the same
unpersisted checkpoint. These are executable counterexamples to the new
invariants, not objections to wording.

The v2 exit rule requires zero unresolved Critical and High findings
(`graph_engineered_subscription_execution.plan.v2.yaml:78-82`). This package
cannot pass.

## Findings

### 1. Critical — Byte recomputation still admits PASS without evidence that any test ran

The v2 manifest usefully carries exact test/artifact identities, file paths,
sizes, and hashes (`contracts/evidence_manifest.schema.v2.json:3-16`). The
validator also enforces exact node denominators, reads regular files, recomputes
their bytes, compares artifact aggregates, and recomputes the event ID
(`tools/validate_plan_v2.py:101-162`). Fabricated hash values and missing files
therefore fail when the caller's node, current paths, and evidence root are
trusted.

That trust is the unresolved Critical defect:

- `evidence_root`, `current.resolved_test_evidence_paths`, and
  `current.resolved_artifact_paths` are caller-supplied arguments. They are not
  fields of a typed, digest-bound compiled-node contract, and the function never
  proves that `evidence_root` is one of the compiled authorized roots
  (`tools/validate_plan_v2.py:101-128,136-146`). Passing `/` made
  `/etc/hosts` an accepted in-root source.
- A test source is never parsed or validated as a deterministic test receipt.
  Any nonempty regular bytes are accepted if the manifest and event both assert
  PASS and name their recomputed hash (`tools/validate_plan_v2.py:125-135`). The
  same arbitrary file may be reused for every required test without rejection.
- Artifact bytes are not validated against the artifact's declared output
  schema. The code proves only source-list equality and byte aggregation
  (`tools/validate_plan_v2.py:136-154`).
- The event ID is a digest of a reconstructed semantic JSON object, not of a
  controller-owned evidence manifest or an independently verified test-result
  receipt (`tools/validate_plan_v2.py:155-157`).

The independent P6 probes met the exact 24-test and five-artifact denominators,
used correct byte hashes and aggregate hashes, and had a correctly recomputed
event ID. Both `/etc/hosts` and the explicit “proves no test ran” file admitted
PASS. This violates the overlay's evidence rule
(`graph_engineered_subscription_execution.plan.v2.yaml:22-26,72-74`) and P6's
release test (`prompts/v2/P6_end_to_end_release_and_supersession.addendum.v2.md:3-12`).
Because this event can select `PLAN_APPROVED`, the defect is Critical.

**Required remediation.** Compile immutable evidence-source descriptors into
each node, bind their digest into the effective graph/current checkpoint, and
make the controller derive test status from schema-valid deterministic receipts
whose command/test ID, exit code, run, node, attempt, input digest, and output
digest all match. Pass a compiled authorized-root set—not an arbitrary root—to
admission. Reject untyped receipts, cross-test source reuse unless explicitly
compiled as a typed aggregate, artifact/schema mismatch, and any source-map
change without a new effective-graph digest.

### 2. Critical — Sandbox admission authenticates claim files but never proves a sandbox ran

The overlay promises actual profile/engine bytes, recomputed roots, OS ownership
and mode, and executed escape probes before model launch
(`graph_engineered_subscription_execution.plan.v2.yaml:35-36,77`). The P2
addendum repeats that requirement
(`prompts/v2/P2_subscription_worker_adapter.addendum.v2.md:7-15`). The executable
validator does less:

- Absolute profile, engine, root-evidence, and probe paths bypass
  `allowed_roots`; containment is applied only when a path is relative
  (`tools/validate_plan_v2.py:230-241,268-276`).
- The declared `resolved_roots` are compared between two JSON documents and
  hashed, but the directories need not exist and are not derived from the engine
  profile (`tools/validate_plan_v2.py:249-264`).
- Escape probes are not executed. The helper checks seven IDs, then hashes the
  bytes of each claimed receipt; it never parses the receipt, invokes the engine,
  or observes a denial (`tools/validate_plan_v2.py:265-276`).
- The alleged engine need only be a regular file with matching claimed bytes,
  uid, and mode. Its format, identity, executable behavior, and relationship to
  `profile_document.engine` are not checked (`tools/validate_plan_v2.py:236-248`).
- `base_contract_hash` is schema-shaped but never compared with the frozen P0
  contract anywhere in `validate_assurance_bytes()`
  (`contracts/baseline_assurance_addendum.schema.v2.json:4-8`;
  `tools/validate_plan_v2.py:230-287`).

The independent fixture used a plain-text “engine,” two nonexistent roots, and
seven files whose content said `ALLOWED`; the root-evidence JSON separately
asserted their status was `DENIED`. It was accepted, even though all assurance
sources were absolute paths outside the supplied allowed root. A hash mismatch
was correctly rejected, proving the positive counterexample exercised the
intended path rather than bypassing validation accidentally.

**Required remediation.** Resolve every assurance source inside a compiled,
immutable controller-read root; identify and execute the pinned engine; derive
roots independently from its actual profile/configuration; require canonical
existing roots with ownership, mode, overlap, and symlink checks; execute every
probe against that engine; and admit only controller-produced typed receipts
binding invocation, exit status, observed denial, stdout/stderr hashes, profile
hash, engine hash, and time. Compare the assurance base hash to the actual frozen
P0 contract.

### 3. High — Resume checking is neither an atomic durable transition nor bound to a typed trusted authority

The function now verifies continuation/command fields, exact external record
bytes, time bounds, file modes, and a real signature
(`tools/validate_plan_v2.py:171-220`). Random signature forgery was rejected,
and passing the returned consumed state to a second call was also rejected.

The claimed durable semantics do not exist. `validate_resume_once()` checks two
lists in the supplied dictionary, returns a copied dictionary with appended IDs
and an incremented integer, and performs no compare-and-swap or durable write
(`tools/validate_plan_v2.py:221-227`). Calling it twice with the same original
checkpoint admitted twice. Two concurrent or cold processes can therefore both
validate before either caller persists the returned object. The self-test masks
this by manually feeding `updated` into its second call
(`tools/validate_plan_v2.py:455-461`), which is not the cold-process/CAS property
required by P3 (`prompts/v2/P3_durable_graph_runtime.addendum.v2.md:3-14`).

The supposed durable fields are not even representable in the frozen state
contract. The closed runtime schema declares `consumed_continuation_ids` but not
`consumed_command_ids` or `checkpoint_generation`
(`contracts/runtime_state.schema.v1.json:4-28`), while v2 supplies no runtime
state override (`graph_engineered_subscription_execution.plan.v2.yaml:12-21`).
Direct validation rejected a state containing both fields required by the v2
helper.

Authority provenance is also caller-trusted. Root owner uid, authorization
root/path, model roots, public-key path/hash, and authorization time all arrive
through `current`; none is bound to a validated P0 assurance digest
(`tools/validate_plan_v2.py:190-212`). The independent probe generated an
Ed25519 key and authorization root as the same uid running the validator, passed
that uid and key hash in `current`, and was accepted. The function also never
checks `active_continuation_hash`, although the v1 runtime schema exposes it.

**Required remediation.** Define a v2 runtime-state/checkpoint schema containing
the consumed continuation, command and nonce sets plus generation/version. Load
the expected generation and active continuation from a durable store, verify
authority configuration against the digest-bound P0 assurance record, and
atomically compare-and-swap the checkpoint plus consumption record before
returning an activation. Prove two simultaneous processes yield exactly one
winner and prove crash-before/after behavior using a real store. The operator
key/root must be provisioned under an identity the model/controller cannot
create, chmod, or replace; do not accept its trust anchor from the request's
`current` dictionary.

### 4. High — No effective graph is compiled, merged, or digest-bound

`load()` correctly recomputes the v1 plan hash and compares it with the overlay
(`tools/validate_plan_v2.py:52-59`), resolving the narrow base-manifest binding.
The old validator is then run against the unchanged base
(`tools/validate_plan_v2.py:290-300`). Representative old graph mutations still
failed as expected.

The v2 delta is never merged back into that graph. `effective_node()` adds only
subtask IDs and extra outputs (`tools/validate_plan_v2.py:93-98`), but
`validate()` never calls it. It checks only that addendum files have three
headings and contract files are meta-valid, then validates the base registry
(`tools/validate_plan_v2.py:290-308`). It does not:

- re-run uniqueness/ownership/schema/topology checks after additional outputs;
- attach v2 controller/guard contracts, status state, prompt addenda, evidence
  ports, resume ports, or subtask denominators to one normalized graph;
- reconcile prompt addenda with their node or exact required subtasks;
- compute an effective graph or prompt digest from base plus overlay/addenda;
- bind the v1 schema, validator, contracts, or prompts—only the v1 plan YAML is
  covered by `base.sha256`.

Consequently, the validator accepted a P1 additional output already owned by P0,
removal of P0's required assurance output, attaching P1's addendum to P0,
shrinking P6 from its declared eleven subtasks to three arbitrary IDs, and
replacing every evidence-admission rule name with arbitrary strings. The v2
schema permits generic paths, arbitrary additional-output strings, any three
subtask IDs, and generic rule strings
(`graph_engineered_subscription_execution.schema.v2.json:21-45`). This
contradicts the effective-graph requirement in the P1 and orchestrator addenda
(`prompts/v2/P1_graph_ir_and_static_compiler.addendum.v2.md:3-14`;
`prompts/v2/P_ALL_graph_orchestrator.addendum.v2.md:3-12`).

**Required remediation.** Implement one deterministic `compile_effective_graph`
operation with closed overlay semantics. It must merge all contract, controller,
node, state/status, prompt, and output changes; re-run every v1 and v2 invariant
on the merged IR; emit the normalized effective graph and digest; and require
all event, ledger, evidence, checkpoint, and resume helpers to accept that
immutable compiled object/digest rather than caller-supplied node/current maps.
Add the five accepted overlay mutations above to a biting compiler suite.

### 5. High — Registry checking proves names exist, not ownership or resolved types/values

Registry usage equality, schema-file existence, schema meta-validity, and dotted
property existence are now enforced (`tools/validate_plan_v2.py:76-90`). The
prior nonexistent/unused registry defects are therefore materially improved.

The overlay additionally promises owner precedence and resolved-value schema
validation (`graph_engineered_subscription_execution.plan.v2.yaml:33-34,76`).
Neither occurs. `_resolve_schema_property()` returns only a Boolean after finding
property names; it does not return or validate the resolved subschema
(`tools/validate_plan_v2.py:66-73`). `validate_registry()` never reads `owner`,
compares producer/consumer ancestry, resolves an owner artifact, or validates a
runtime value.

The independent mutations therefore accepted:

- changing `contract://anti_regression_sources` to owner P0 even though P0
  consumes it, so its owner does not strictly precede every consumer;
- resolving that contract to the existing scalar `goal` field rather than the
  anti-regression source list; and
- resolving the P4 tests selector to the existing scalar baseline `version`
  field rather than a path list.

**Required remediation.** Compile each entry to an exact typed subschema and
source owner, enforce strict control/context ancestry for every consumer,
validate output ownership separately from input consumption, and validate the
actual resolved value/cardinality against the consumer port. Add wrong-owner,
same-node-owner, existing-wrong-type resolver, empty resolution, and
multi-value/cardinality mutations.

### 6. High — Ledger completeness is denominator-exact but committed output claims remain unverified

The current P0–P6 overlay defines node-owned required subtask IDs
(`graph_engineered_subscription_execution.plan.v2.yaml:37-65`). With the genuine
P6 `effective_node`, a one-subtask ledger was correctly rejected by the new set
comparison (`tools/validate_plan_v2.py:165-168`). This closes the narrow
self-denominator defect.

The validator still accepts every subtask as `COMMITTED` with arbitrary
hash-shaped `output_hashes`. Neither v1 nor v2 ledger admission receives output
paths/bytes, checks that the outputs exist, binds them to node-authorized
artifacts, or cross-checks them with the evidence manifest. An exact eleven-ID
P6 ledger with every output hash set to zero passed. This violates P6's explicit
requirement that all committed outputs exist and hash correctly
(`prompts/v2/P6_end_to_end_release_and_supersession.addendum.v2.md:9-14`) and can
make replay skip work that never committed.

The node denominator is also an unbound caller argument: the one-subtask ledger
passed when paired with a caller-mutated node. That is exploitable because
Finding 4 establishes there is no immutable compiled effective-node digest.

**Required remediation.** Bind ledger admission to the immutable effective node
and subtask-set digest. Compile each subtask's input and output descriptors;
recompute committed output bytes and compare them with the phase evidence
manifest and authorized artifact set. Make `COMMITTED` a controller-derived
state following atomic output admission, not a ledger assertion. Mutation-test
missing files, fabricated hashes, cross-subtask output reuse, unauthorized
outputs, and caller-substituted node contracts.

### 7. Medium — The v1 coverage source digest remains non-relational

Version 2 does not override the v1 coverage-denominator schema or helper. The
v1 validator still checks aggregate counts and within-category duplicate IDs but
does not recompute `source_digest`, relate record `source_hash` values to it, or
define cross-category ID scope (`tools/validate_plan.py:94-101`). This known
integrity gap remains Medium; it does not determine the failed verdict because
the Critical/High findings already do.

## Confirmed working controls

The review did not treat a falling defect count as success. These controls were
independently confirmed on the exact frozen bytes:

- the overlay's recorded v1 plan digest equals the actual v1 plan bytes;
- base v1 validation still rejects missing failure routing, future artifact
  consumption, and an unbounded repair edge;
- exact current P6 test, artifact, and node-owned subtask set comparisons bite;
- evidence file byte/size/hash and event-ID mismatches bite when the trusted
  source configuration is held constant;
- registry unused/missing-schema/nonexistent-property checks bite;
- an invalid operator signature bites; and
- supplied sandbox engine-byte mismatches bite.

These are useful local controls, but they do not close the accepted
counterexamples.
