SOTA Research

Turn an explicitly approved, self-contained research plan into an auditable evidence package with independent challenge, deterministic verification, and human-controlled acceptance.

Overview

Use this family for bounded state-of-the-art research that must preserve source provenance, budgets, challenges, verification, and human authority. Do not use it for exploratory browsing without an approved protocol, ordinary issue remediation, or implementation work. Planning starts with $sota-plan-create; after explicit human approval, runtime starts with $sota-plan-execute <approved-plan-path>. The component contracts and shared baseline are present, but no trustworthy end-to-end execution record was found.

System context

Family boundary: the seven skills below govern planning and research execution. The human owner, repository, network search services, deterministic tools, renderers, schema/link validators, and final implementation work are outside boundary. The external runtime supplies installed skills and permitted tools.

Outside · callerHuman owner supplies the research need, approves the plan, and accepts or rejects the result.
Inside · planningsota-plan-create produces the immutable plan.
Inside · orchestratorsota-plan-execute controls five delegated role skills and repair routes.
Outside · dependenciesRepository, network sources, deterministic tools, execution-log schema, renderers and validators support the run.
Outside · outputsPlan, report.html, execution-log.json, optional evidence/, verification and five states return to the caller.

Structural flow: caller → planning → human approval → orchestrator → method → evidence review → synthesis → independent challenge → verification → human acceptance. Material contract changes return to planning; artifact defects return to their owning role and replay downstream work.

Responsibility: create the next immutable, self-contained plan version and hold it at the approval gate.

INCaller inputs: research directory, question, intended decision, owner, evidence boundary, originating issue/report; optional repository format and feedback. Gate preconditions: required family/plan references exist. Fixed dependencies: template, allocation policy, version selector.
OUTresearch/example/plan/example.plan.v1.html; optional synchronized issue/report vN+1; status awaiting approval; validation and version report.

sota-plan-execute

Responsibility: orchestrate the approved plan, enforce gates/budgets, and deliver the verified package for human acceptance.

INCaller input: approved plan path. Gate preconditions: latest version, explicit approval, complete baseline fields, installed role skills. Fixed dependencies: family and execution contracts, deterministic tools, approved allocations.
OUTCaller-facing result: terminal status, output paths, verification, budget, deviations, limitations, acceptance state. Direct writes: canonical execution-log.json initialization/control records. Delegated outputs: report.html, source/appraisal/extraction/challenge/verification content with owning role writers. Control outputs: gate decisions, warnings, stops, replay and plan-return routing.
Complete example: $sota-plan-execute research/example/plan/example.plan.v1.html → research/example/runs/run-20260820/report.html, execution-log.json, optional evidence/ present because the plan requires it, terminal dimensions, verification results, budget usage, and acceptance PENDING. Compatibility markers: no closure_receipt.json or BLOCKED.md is defined by this family.

sota-independent-challenge

Responsibility: independently test frozen evidence and synthesis before verification.

INFrozen evidence package and synthesis; optional plan-specific challenge criteria; no synthesizer defenses.
OUTChallenge register with stable IDs, severity, evidence, affected finding, required action, and disposition requirement.

Responsibility: deterministically check the plan and completed package without granting acceptance.

INApproved plan, family baseline, run package, challenge dispositions; optional stricter plan checks.

Quick start

Default entry point

Obtain an explicitly approved, self-contained plan created by $sota-plan-create. From the repository root invoke $sota-plan-execute research/<sota-slug>/plan/<sota-slug>.plan.vN.html. The run root is research/<sota-slug>/runs/<run-id>/. The first expected artifact is initialized execution-log.json. Completion requires a verified package, five terminal state values, and submission to the human owner; verification does not imply acceptance.

Requirements and constraints

  • Run from a repository with the seven installed SOTA skills and readable contract references.
  • Use an explicitly approved self-contained plan; supporting files cannot supply missing execution instructions.
  • Use deterministic tools for hashing, schemas, links, counts, deduplication, and rendering where possible.
  • Network use is limited by the approved evidence boundary, sources, dates, ceilings, permissions, and external-spend controls.
  • Write permission is required for the research plan/run directories; prior plan and report versions remain immutable.
  • Human authority is required for plan approval, research acceptance, and implementation authority.
  • Excluded: silent plan repair, fabricated provenance, self-acceptance, and implementation without separately granted authority.
