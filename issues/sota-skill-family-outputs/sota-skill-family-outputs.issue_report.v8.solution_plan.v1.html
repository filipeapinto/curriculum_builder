Issue-remediation plan · v1 · draft · 2026-08-20

Make SOTA runs structurally comparable without erasing study-specific method

Owner: repository human owner · Predecessor: none · Implementation authority: NONE

Executive intent

This plan remedies the documented failure of the SOTA skill family to enforce common artifact locations, record shapes, lifecycle states, verification order, and terminal-result language. The target is a compact family-owned baseline that every SOTA plan and run must satisfy while allowing study questions, evidence, budgets, evaluations, and substantive results to differ. Completion requires a minimal and a complex fixture to pass the same family checks and to receive the same finding for the same injected defect.

Current gate: the source issue is HUMAN_REVIEW_PENDING. This draft is a test of plan-createe and a prospective execution contract. No work package may begin until the owner approves the issue direction and separately approves a plan version.

Scope and constraints

Included

  • Family contract, minimal plan template, plan/execution/report/log schemas, lifecycle vocabulary, preflight rules, family-first verification, fixtures, and caller documentation for the installed sota-* skills.
  • Compatibility behavior for historical runs that preserves original artifacts and explicitly reports unavailable provenance.
  • Updates to the planning, execution, role, and verification skills required to bind the shared baseline.

Excluded

  • Rewriting either historical run, inventing missing receipts, changing study conclusions, or forcing identical research questions, sources, corpora, budgets, evaluations, or substantive outputs.
  • Executing new SOTA research or approving the issue, plan, results, or implementation.

Constraints

  • Issued plans and historical evidence remain immutable.
  • The approved plan remains the study-specific execution contract, but it may only strengthen the family baseline.
  • Conditional stages must use explicit applicability and reason fields; omitted does not mean passed.
  • All schema/version changes require deterministic validation and readable error messages.

Work packages

WP-01 · Baseline inventory and decision closure

Objective: compare the current SOTA family, schemas, templates, validators, and both historical run trees against COR-01–COR-05; identify already-landed work and exact gaps without changing files. Inputs: source report and current repository. Dependencies: issue-direction approval. Owner/capability: method lead plus repository inspection. Outputs: gap matrix, proposed field dictionary, affected-file list, and decisions DEC-01–DEC-03 ready for owner disposition. Done: every proposed edit traces to a correction and existing equivalent work is reused.

WP-02 · Family baseline and conditional plan template

Objective: define immutable universal requirements and a minimal conditional template. Targets: sota-plan-create, the shared family contract, plan contract, and template. Changes: encode “strengthen, never weaken,” explicit applicability, required identity/provenance/budget/challenge/verification/acceptance fields, and preflight rejection of missing baseline requirements. Dependencies: WP-01 and DEC-01. Verification: AT-01 and AT-03. Done: minimal and complex plans are complete without irrelevant mandatory sections.

WP-03 · Canonical run package, schemas, and state model

Objective: make every new run discoverable and machine-checkable. Targets: execution contract plus versioned JSON schemas for the manifest/plan metadata, execution-log.json, and report terminal state. Changes: define the compact directory layout; stable IDs and cross-record references; timestamps and actor/skill assignment receipts; optional evidence rules; and separate enumerated fields for research support, execution, verification, human acceptance, and implementation authority. Dependencies: WP-01, DEC-01, DEC-02. Verification: AT-02 and AT-05. Done: invalid combined or missing states and broken references are rejected.

WP-04 · Family-first verification and invariant enforcement

Objective: ensure equivalent defects receive equivalent findings. Targets: sota-verify, deterministic validators, and execution preflight. Changes: run structural/schema/link/ID/provenance/state checks before plan-specific tests; abort plan execution when a family baseline is weakened; distinguish tool failure, unavailable measurement, failed verification, and pending human authority. Dependencies: WP-02 and WP-03. Verification: AT-03–AT-05. Done: family failures block plan-specific success from producing a passing final disposition.

WP-05 · Role-skill and handoff alignment

Objective: align method, evidence, synthesis, challenge, execution, and verification skills with the same identifiers, records, and authority vocabulary. Targets: installed SOTA role-skill contracts and caller-facing documentation. Changes: specify each role's required inputs, outputs, record writes, assignment receipt, and prohibited authority in shared terms. Dependencies: WP-02 and WP-03. Verification: cross-skill contract audit plus schema-valid example handoffs. Done: no role skill introduces a competing location, field, or terminal term.

WP-06 · Fixtures, regression suite, and compatibility guidance

Objective: prove the family contract across different study complexity and document safe treatment of legacy runs. Targets: one minimal fixture, one complex fixture, injected-defect variants, validator tests, and migration guidance. Dependencies: WP-04, WP-05, DEC-03. Changes: validate discovery, schemas, link integrity, lifecycle, terminal states, and family-first ordering; define read-only legacy adapters or explicit unsupported status without rewriting evidence. Verification: all AT-01–AT-06. Done: deterministic suite passes clean fixtures and produces equal findings for equal defects.
