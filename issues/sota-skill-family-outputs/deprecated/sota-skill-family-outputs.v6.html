The SOTA workflow has rules, but no shared definition of a valid run

We proved two specific contract gaps. The plan creator forces every study to copy one unusually complex example, while the verifier checks only whatever each plan happens to require. Therefore two “SOTA runs” can have different required files and different pass/fail rules.

AnswerQuestionProofCauseFixNot provedDecision

What did we prove?

CONFIRMED: The SOTA skills do not define one minimum package and one minimum verification suite that every run must satisfy.

Why that matters: A plan can omit a control, and the verifier will omit the same control. The verifier therefore cannot reliably detect that the plan weakened the family method.

What we suggest: Add one small SOTA-owned plan template, one compact run layout, and one baseline validator. Let individual plans add stricter or study-specific requirements.

Priority

P0. The current workflow can report success without testing the same minimum conditions from one study to the next.

Confidence

High for the two contract gaps below. The exact historical skill version used by each old run was not proved.

Why is this happening?

Root cause: The plan is treated as the entire execution contract, and verification trusts that plan as the complete source of checks. There is no higher-level SOTA contract that says, “every plan must include at least these things, every run must produce these files, and the verifier must always run these tests.”

AffectedNew SOTA plans, SOTA executions, and SOTA verification.
Not the problemDifferent research questions, sources, experiments, sample sizes, conclusions, or human-facing report formats.
Concrete riskA weak plan can generate a weak run and still be “verified” because the verifier checks only the weak plan.

Why this fixes the issue: every run becomes discoverable and testable the same way, while the plan still controls the study-specific method.

Acceptance test: create one minimal study and one complex study from the template; run both; prove that the same baseline validator checks both; prove that removing any baseline requirement makes verification fail.

Not proposed: one giant directory tree, a separate file for every role or stage, identical research methods, or retroactive rewriting of old runs.
