P0 · Open · Method integrity

The SOTA skill family lacks an enforceable common research contract

Two executions attributed to the same skill family use incompatible run topology, canonical records, lifecycle evidence, verification thresholds, and terminal-answer semantics. The plans vary legitimately; the underlying method varies without control.

Issue

The defect is not that two studies reached different substantive conclusions or produced different domain-specific evidence. The defect is that the skill family does not enforce one invariant execution method beneath those differences.

A plan should define the research question, evidence boundary, search strategy, instruments, evaluation design, domain outputs, and stricter project-specific controls. It should not be free to redefine where a run lives, which audit records are canonical, what lifecycle states mean, which baseline checks verification must apply, or how a research answer is expressed.

At present, “processed by the SOTA skill family” does not guarantee a stable method. It describes a loose set of role labels whose concrete execution contract can change from plan to plan.

The correct consistency boundary

Legitimate plan variation

Questions, hypotheses, sources, eligibility rules, appraisal instruments, experiment design, corpus size, domain analysis, and human-facing deliverables may differ.

Required family invariants

Run root, lifecycle, approvals, canonical records, identifiers, provenance, budgets, challenges, verification baseline, failure behavior, and terminal-state vocabulary must remain stable.

“The answer must be the same” means the answer must use the same semantic contract—not that unrelated questions must receive the same conclusion. Every report must resolve its question as SUPPORTED, PARTIALLY_SUPPORTED, NOT_SUPPORTED, INCONCLUSIVE, or BLOCKED, with evidence strength and scope. Execution completion, verification conformance, human acceptance, and implementation authority must be reported separately.

Likely contract failure

Root-cause status: hypothesis requiring the linked audit.

  1. sota-plan-execute describes controls but does not appear to impose a canonical physical run package and schema suite.
  2. Role-skill output contracts are semantic summaries rather than precise, interoperable artifact contracts.
  3. Plans can effectively redefine family method instead of parameterizing a fixed method.
  4. sota-verify derives checks from each approved plan without an explicit, non-waivable family baseline.
  5. Durable skill-version and invocation provenance is insufficient to prove which instructions produced either run.

These are not final findings. The audit must trace each inconsistency to exact skill instructions, plan clauses, run records, or missing rules.

Expected family contract

execution/<run-id>/
├── manifest/
├── approvals/
├── protocol/
├── records/
│   ├── activities/
│   ├── budget/
│   ├── sources/
│   ├── analysis/
│   ├── synthesis/
│   └── challenge/
├── evaluation/        # optional when method requires it
├── verification/
└── reports/

The exact names remain subject to audit, but the family must own one authoritative topology and machine-readable record layer. Plans may add scoped artifacts, never remove or relocate required classes.

  1. One invariant lifecycle: start gate → calibration when required → human protocol gate → evidence work → analysis/evaluation → synthesis → independent challenge → correction → deterministic verification → human acceptance.
  2. Versioned schemas and stable identifiers for manifest, approvals, activity events, budgets, deviations, sources, findings, challenges, verification, and terminal result.
  3. A normalized research-answer state, separated from execution, verification, acceptance, and implementation states.
  4. A family-level verification baseline that plans may strengthen but cannot omit, weaken, or relabel.
  5. Explicit extension points for research-specific methods, instruments, corpora, and presentation deliverables.
  6. Deterministic structural and semantic conformance tests for every run package.

Acceptance criteria

  • The skill family publishes one canonical execution, artifact, state, and verification contract.
  • Every run has one discoverable execution/<run-id>/ root and authoritative manifest.
  • Equivalent artifact classes use the same canonical path class, schema, ID rules, and producer/consumer ownership.
  • Markdown, HTML, and CSV are optional or derived views, not substitutes for required canonical records.
  • Plans parameterize or strengthen the method but cannot remove required stages, records, gates, checks, or fail-closed behavior.
  • Equivalent defects produce equivalent verification outcomes under the common baseline.
  • Every result independently reports research support, execution state, verification state, human acceptance, and implementation authority.
  • Both case-study packages are tested against the same conformance suite and receive precise findings.
  • Skill and run provenance identify the exact skill versions and assigned agents used.

Required audit before redesign

Run the Goal–Loop–Test inconsistency audit prompt. Do not modify the skill family until the human owner reviews the verified inconsistency register and approves a canonical contract.
