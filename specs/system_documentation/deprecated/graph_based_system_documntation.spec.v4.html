Model-agnostic documentation skills for graph-based LLM systems

This specification defines model-agnostic skills that produce engaging, accurate documentation for graph-based LLM systems through a visualization-led approach. It defines the required evidence, behavior, outputs, and quality checks—not a particular model, package, tool, runtime, or graph framework.

Purpose

Make a complex LLM system understandable at a glance, then explorable in depth.Readers should first see the verified system flow and its important paths; concise text, tables, and source links then explain what the visual cannot.

A conforming skill may run in Codex, GPT/ChatGPT, Claude, Grok, or another platform. Claims and visuals come from inspected evidence; gaps remain visible.

Graph forms

A graph can be implicit in prompt orchestration or explicit in a graph runtime. The skill must document verified behavior, not impose a framework-shaped model on either form.

FormExampleEvidence to inspect
Prompt-orchestratedAn orchestrator prompt selects or sequences prompts, tools, agents, or handoffs.Orchestrator and component prompts, routing instructions, tool definitions, traces, and tests.
Framework-definedA framework such as LangGraph declares and executes nodes, edges, and state.Graph definition, runtime or compiled graph, node code, traces, and tests.

Do not infer formal nodes or edges solely from a prompt sequence, or treat a declared path as proof that it executed. Where routing semantics are not evidenced, document a sequence or workflow rather than a graph.

Evidence contract

Inspect available sources before writing or drawing. Every operational claim and visual label must resolve to an inspected source, or be visibly marked unknown, proposed, conflicting, stale, or unverified. Each graph visual must state whether it represents declared topology, observed execution, inferred behavior, or unknown scope; it must not mix these without a legend.

Fact familyDocumented factsTypical evidence
GraphSteps or nodes, handoffs or edges, entries, branches, loops, joins, failures, and terminals.Prompts, graph definitions, routing configuration, traces, tests.
Data and effectsInputs, outputs, state, validation, side effects, tools, and sensitive-data handling.Prompts, code, schemas, configuration, policy.
ExecutionRun IDs, time/version scope, covered and unexercised paths, artifacts, checks, retries, recovery, and observed terminals.Logs, manifests, receipts, audits, test results.

Visualization-led output contract

  1. Start with the graph. When graph topology is claimed, the first substantive element is a readable system map. It shows evidenced entry points, nodes, directed edges, decisions, loops, joins, failure or blocked paths, terminals, and external boundaries. If topology cannot be evidenced, show the evidence gap instead of inventing a graph.
  2. Use the right visual. Use a graph for topology, a sequence for order, a state view for transitions, and a data-flow view or table for contracts. Use text for definitions, caveats, and precise instructions.
  3. Progressively disclose detail. Begin with the system map; then offer focused views for a node, decision, data flow, execution trace, or failure path. Do not compress the entire system into one unreadable diagram.
  4. Make every visual inspectable. Show a title, takeaway, scope, evidence/freshness status, source references, and a legend where needed. Provide an adjacent prose or tabular equivalent; use semantic SVG title and desc where applicable. No meaning may depend on color alone.
  5. Keep the visual honest. A renderer may arrange verified facts but must not invent entities, links, execution outcomes, or confidence.

HTML is the preferred reader-facing format when it improves visual navigation or exploration. It must have a static, no-JavaScript baseline; external assets are not required for comprehension.

Required content and behavior

Inventory and extractionRecord inspected and unavailable sources; build a fact model with source identifiers and versions or digests when available.
VerificationCheck claims and visual labels against the fact model; reconcile declared topology with observed execution; flag unsupported, contradictory, or stale material.
Reader journeyDeliver: a visual overview; graph walkthrough; focused node/data/evidence views; operations and recovery guidance; and a verification record.
Verification recordState scope, sources inspected, source versions/digests, verification time, excluded scope, unavailable checks, and unresolved conflicts.

Quality gates

  1. Accurate: claims and visual labels are traceable to inspected evidence; declared and observed paths are distinct; partial coverage is never presented as complete.
  2. Visualization-led: the visual overview precedes explanatory prose; each additional visual answers a clear reader question rather than decorating or repeating content.
  3. Accessible: use semantic structure, adequate contrast, keyboard-operable interaction, and text alternatives for visuals.
  4. Readable offline: basic comprehension requires no CDN, remote font, remote image, or JavaScript.
  5. Fresh: show verification time and source version/digest; clearly mark unavailable or stale checks.
  6. Rendered QA: inspect the output at desktop and narrow widths; verify readable, unclipped labels, non-overlapping edges and legends, working links, and visual-to-fact-model traceability.
  7. Safe: write versioned outputs only to an approved location and do not overwrite accepted artifacts without authorization.
Design guidance informed by HTML documentation skills assessment. A conforming skill favors verified visuals over prose while preserving evidence, accessibility, and a truthful verification record.
