Model-agnostic documentation skills for graph-based LLM systems

This specification defines model-agnostic skills that produce engaging, accurate documentation for graph-based LLM systems through a visualization-led approach. The documentation covers behavior and the contracts, configuration, assumptions, and operational conditions that make that behavior possible.

PurposeGraph formsSystem contractsEvidenceVisualization approachContentQuality

Purpose

Make an LLM system understandable at a glance and operable in detail.Readers first see the verified flow; they can then inspect the contracts, configuration, assumptions, evidence, and failure behavior behind it.

A conforming skill may run in Codex, GPT/ChatGPT, Claude, Grok, or another platform. It defines the required documentation result, not a model, package, tool, runtime, or graph framework.

Graph forms

FormExampleEvidence to inspect
Prompt-orchestratedAn orchestrator prompt selects or sequences prompts, tools, agents, or handoffs.Orchestrator and component prompts, routing instructions, tool definitions, traces, and tests.
Framework-definedA framework such as LangGraph declares and executes nodes, edges, and state.Graph definition, runtime or compiled graph, node code, traces, and tests.

Do not infer formal nodes or edges solely from a prompt sequence, or treat a declared path as proof that it executed. If routing semantics are not evidenced, document a sequence or workflow rather than a graph.

Required system-contract documentation

Graph topology alone is not sufficient. The skill must extract and document the following contract families whenever they are in scope and evidence is available.

Contract familyWhat the documentation must showTypical evidence
System boundaryActors, external systems, trust boundaries, entry/exit interfaces, owned and excluded responsibilities.Architecture, API definitions, integration configuration, policy.
Node and tool contractPurpose; inputs and outputs; prompt/model behavior; tool or side-effect boundary; failure, timeout, retry, repair, and terminal semantics.Prompts, node code, tool definitions, tests, run records.
State and schema contractField name, type, requiredness, reader/writer, validation, default, lineage, persistence/checkpoint boundary, merge or mutation rule, version/migration, and redaction rule.State models, JSON Schema, reducers, migrations, policy.
Route contractSource, target, trigger or guard, route class (deterministic, model-selected, tool-result, or human/external), transferred payload/state, and outcome.Routing prompts, graph definitions, code, tests, traces.
Configuration contractParameter name, type, allowed/default value, scope, source of configuration, effect, sensitivity, reload behavior, and change/release implications.Environment schemas, configuration files, feature flags, deployment manifests.
Assumptions and invariantsPreconditions, guarantees, resource or model dependencies, safety/privacy constraints, idempotency, ordering, and conditions that invalidate an outcome.Policy, design records, tests, SLOs, incident/runbook records.

Do not expose secret values. Document a sensitive parameter’s purpose, source class, and handling rule instead.

Evidence contract

Inspect available sources before writing or drawing. Every operational claim, parameter, assumption, and visual label must resolve to an inspected source, or be visibly marked unknown, proposed, conflicting, stale, or unverified.

Each graph visual must state whether it represents declared topology, observed execution, inferred behavior, or unknown scope; it must not mix these without a legend. Observed views name their run IDs, time/version scope, sampling limits, covered paths, and unexercised declared paths.

Visualization-led output contract

  1. Start with the graph. When topology is claimed, the first substantive element is a readable system map showing evidenced entries, nodes, directed edges, decisions, loops, joins, failures, terminals, and external boundaries. If topology cannot be evidenced, show the evidence gap instead.
  2. Visualize contracts where relationships matter. Use state/data-flow views for schema lineage and ownership, route views for decisions and payload transfer, and configuration-impact views for parameters that change behavior. Use a table when it is clearer than a diagram.
  3. Progressively disclose detail. Follow the overview with focused views for nodes, routes, state, configuration, execution, and recovery. Do not compress the entire system into one unreadable diagram.
  4. Make every visual inspectable. Show a title, takeaway, scope, evidence/freshness status, source references, and a legend where needed. Provide an adjacent prose or tabular equivalent; use semantic SVG title and desc where applicable. No meaning may depend on color alone.
  5. Keep visuals honest. A renderer arranges verified facts; it does not invent entities, links, parameter effects, execution outcomes, or confidence.

HTML is preferred when it improves visual navigation or exploration. It must have a static, no-JavaScript baseline; external assets are not required for comprehension.

VerificationCheck claims and visuals against the fact model; reconcile declared topology with observed execution; flag unsupported, contradictory, or stale material.
Reader journeyDeliver a visual overview; graph walkthrough; node, route, schema/state, configuration, and assumptions reference; operations and recovery guidance; and a verification record.
Verification recordState scope, sources inspected, source versions/digests, verification time, excluded scope, unavailable checks, and unresolved conflicts.

Quality gates

  1. Accurate: claims, contract entries, and visual labels are traceable to inspected evidence; declared and observed paths are distinct; partial coverage is never presented as complete.
  2. Complete within scope: document available schemas, contracts, parameters, assumptions, policies, and dependencies alongside graph behavior, and name excluded or unavailable material.
  3. Visualization-led: the visual overview precedes explanatory prose; each additional visual answers a clear reader question rather than decorating or repeating content.
  4. Accessible: use semantic structure, adequate contrast, keyboard-operable interaction, and text alternatives for visuals.
  5. Readable offline: basic comprehension requires no CDN, remote font, remote image, or JavaScript.
  6. Fresh: show verification time and source version/digest; clearly mark unavailable or stale checks.
  7. Rendered QA: inspect the output at desktop and narrow widths; verify readable, unclipped labels, non-overlapping edges and legends, working links, and visual-to-fact-model traceability.
  8. Safe: write versioned outputs only to an approved location and do not overwrite accepted artifacts without authorization.
Design guidance informed by HTML documentation skills assessment. A conforming skill documents the verified system and its operating contract, while clearly reporting every unavailable source or check.
