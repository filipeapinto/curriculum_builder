Model-agnostic documentation-skill specification for graph-based LLM systems

This specification defines model-agnostic skills for documenting graph-based LLM systems. It specifies the required evidence, behavior, outputs, and quality checks—not a shared package, model, tool, host runtime, or graph framework.

Purpose

Produce trustworthy documentation for an implemented graph-based LLM system.It must explain the graph, its data and evidence, its failure paths, and the sources that support its claims.

This specification can guide a Codex, GPT/ChatGPT, Claude, Grok, or other agent-platform skill. It concerns the documented system and result, not how either is packaged or run.

Graph implementations

A graph may be implemented informally or formally. The documentation skill must document the behavior it can verify, regardless of implementation style.

Implementation styleExampleDocumentation evidence
Prompt-orchestratedAn orchestrator prompt selects or sequences multiple prompts, tools, agents, or handoffs.Orchestrator and component prompts, routing instructions, tool definitions, run traces, and tests.
Framework-definedA graph is declared and executed by a framework such as LangGraph.Graph definition, runtime configuration or compiled graph, node code, traces, and tests.

Do not infer formal nodes or edges merely because prompts are sequenced. Conversely, do not treat a framework declaration as proof that every declared path executed. Record the level of evidence available for each claim.

Principles

  1. Evidence first: derive claims from inspected sources, not prompts, recollection, or plausible inference.
  2. State uncertainty: mark unavailable, conflicting, stale, or unverified information instead of filling gaps.
  3. Keep claims traceable: connect each operational claim and diagram label to its evidence.
  4. Declare limits: state which sources and validations were available and which were not.

The specification does not require a particular model, source code, plugin format, context window, browser, connector, diagram renderer, or graph framework.

Required evidence

Inspect and record the sources available to the skill. Missing evidence is a documented gap, not a reason to invent a substitute.

Fact familyRequired factsTypical evidence
GraphName/version, nodes or steps, edges or handoffs, entries, branches, loops, joins, and terminals.Orchestration prompts, graph definitions, compiled graphs, routing configuration, traces, tests.
Node and statePurpose, inputs, outputs, side effects, failure behavior, state fields, validation, and sensitive-data handling.Prompts, code, schemas, configuration, policy.
ExecutionRuns, calls, artifacts, checks, verdicts, retries, resume behavior, and terminals.Logs, manifests, receipts, audits, test results.

Required behavior

CapabilityBehavioral requirement
InventoryLocate candidate sources; state what was inspected and what was unavailable.
ExtractBuild a fact model with source identifiers, versions or digests when available, and explicit unknown or conflict states.
VerifyBind prose and visuals to the fact model; flag unsupported, contradictory, or stale claims.
ExplainOrganize the material for readers and use diagrams only for confirmed entities and relationships.
PublishProduce semantic, navigable documentation and a verification record. HTML must remain understandable without JavaScript.

Required documentation contract

  1. Overview: purpose, boundary, constraints, and top-level graph.
  2. Graph walkthrough: entries, branches, loops, failures, and terminals—not only the happy path.
  3. Node and data reference: contracts, state, effects, checks, and source references.
  4. Operations guide: preconditions, observability, recovery, limitations, and evidence gaps.
  5. Verification record: sources inspected, versions/digests where available, verification time, excluded scope, unavailable checks, and unresolved conflicts.

Every reader-facing document must show its scope and freshness. A visual must have a prose or tabular equivalent. A document that cannot verify a claim must label it unknown, proposed, or unverified.

Quality gates

  1. Traceability: every operational claim resolves to inspected evidence or is visibly marked unsupported.
  2. Truthful coverage: record what was included and excluded; never imply system-wide coverage from a partial scan.
  3. Accessible output: semantic structure, keyboard-operable interaction, adequate contrast, no color-only meaning, and text alternatives for diagrams.
  4. Offline baseline: no required CDN, remote image, remote font, or JavaScript dependency for basic comprehension.
  5. Freshness: show source version/digest and verification time; mark unavailable or stale checks clearly.
  6. Safe writes: create versioned outputs only in an approved location and do not overwrite accepted artifacts without authorization.
A conforming skill honors this evidence, traceability, accessibility, and verification contract, while clearly reporting any unavailable source or check.
