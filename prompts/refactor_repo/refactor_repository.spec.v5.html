Curriculum Factory repository refactor

Align product and repository identity, adopt an installable Python source layout, classify directories by lifecycle, and separate disposable run output from durable fixtures and evidence.

GoalsIdentitySchema IDsSourceOutputsInventoryDeliverablesTestsExternal steps

1. Goals

  • Use Curriculum Factory consistently as the human-facing product name.
  • Adopt consistent repository, distribution, and Python-package names.
  • Move production Python code into an installable src layout without combining that move with an unsupported subsystem redesign.
  • Classify every top-level directory by owner, reader, and lifecycle.
  • Keep generated run output separate from tracked fixtures and retained evidence.
  • Make installation, imports, tests, commands, and documentation work from a fresh clone.

3. Schema identifier rule

Treat a schema $id as a versioned contract identifier, not branding text.

  1. Preserve the existing $id when the schema keeps the same filename version and semantic contract, even if the URI contains the old repository name.
  2. Do not rewrite a published or referenced $id in place solely for naming consistency.
  3. Use the new canonical namespace when creating a new schema version. Update all corresponding $ref values, registries, fixtures, and documentation in the same change.
  4. An existing identifier may change only when repository-wide reference analysis proves it has no consumer and the migration records the old-to-new mapping. If consumer absence cannot be proven, preserve it.
  5. Tests must validate both reference resolution and the recorded identifier decision for every live schema.

Phase one must add packaging configuration, update imports and entry points, correct module commands, mocks, fixtures, documentation, and every repository-root calculation based on __file__. Tests must run against the installed distribution rather than repository-root path injection.

Later decomposition

Subsystem decomposition is a separate decision. Propose a subpackage only when the inventory demonstrates all of the following:

  • a cohesive responsibility shared by multiple modules;
  • a stable boundary with identifiable callers and dependencies;
  • lower coupling or clearer ownership than the current placement;
  • no import cycle introduced by the move; and
  • focused tests that can verify the boundary.

Names such as orchestration, routing, retrieval, rendering, validation, and persistence are candidates to evaluate, not prescribed directories. Any decomposition requires its own target tree and evidence in the execution plan.

Keep policy/, schemas/, curricula/, docs/, and outputs/ outside src/.

5. Output lifecycle and fixture migration

Keep outputs/ as the ignored runtime write boundary.It should be empty between runs. Durable tests, fixtures, research evidence, and audit evidence must not depend on files stored there.

At execution time, enumerate every child of outputs/ and record its size, producer, tracked and untracked consumers, reproducibility, evidence value, and proposed disposition. Do not copy point-in-time counts or sizes from this specification into the plan as current facts.

Fixture inclusion rule

A migrated run fixture must contain a machine-readable manifest. Every retained file must have:

  • its fixture-relative path and SHA-256 digest;
  • at least one named active consumer;
  • the assertion, citation, or behavior that requires the file;
  • whether exact bytes are required or a generated equivalent is acceptable; and
  • the source run and migration date.

No file may remain in the fixture without a manifest entry and active consumer. Every consumer must resolve to a retained file or a documented generator. Tests must enforce both directions of this relationship. This consumer-closure rule defines “minimal”; no arbitrary file-count or byte cap applies.

Disposition rules

  • Move exact historical bytes only when a test assertion or active evidence citation depends on them.
  • Generate test-local data when the test checks behavior rather than historical content.
  • Move retained non-test evidence to a tracked evidence or archive location instead of disguising it as a test fixture.
  • Remove an output run only after all consumers are migrated, replaced by generators, retired, or shown to be historical-only.
  • After migration, deleting all generated children beneath outputs/ must not break tests or active repository references.

6. Required inventory

Create a read-only inventory tool for this refactor. It must emit both a human-readable report and timestamped machine-readable data, run without modifying the repository, and return a nonzero exit status when collection is incomplete. Run it immediately before planning and again before destructive cleanup. Record:

  • the current value and target value for each identity in §2;
  • every top-level directory, its owner or reader, tracked and ignored state, lifecycle, and disposition;
  • all imports, module commands, and entry points rooted at runtime;
  • all __file__-based root traversal and absolute checkout paths;
  • all live references to old identity, package, source-path, and output-run names;
  • packaging, installation, build, and test configuration;
  • producers and consumers of every output child and questionable directory, including PSIM/ and specs/; and
  • schema-ID and other compatibility-sensitive decisions.

Classify each directory as production source, repository contract, domain input, generated runtime data, cache or scratch data, test fixture, retained evidence, active documentation, or deprecated history. Do not rename or delete an unresolved directory.

7. Deliverables

  1. Inventory tool and reports: reproducible read-only collection plus timestamped findings, classifications, consumers, and proposed dispositions in human- and machine-readable forms.
  2. Execution plan: ordered phases, target tree for each phase, dependencies, rollback points, authorization boundaries, and validation commands.
  3. Execution prompt: exact phase order, permitted mutations, stop conditions, test commands, and completion evidence.
  4. Executable tests: automated checks covering §8.
  5. Fixture manifests: bidirectional consumer closure for every retained run-derived file.
  6. Exceptions inventory: retained legacy identifiers or paths with rationale and removal conditions.
  7. Migration report: final identities, directory dispositions, changes, test results, removed outputs, retained evidence, exceptions, and pending external operations.

8. Executable acceptance tests

  1. Installed imports: production code imports as curriculum_factory from the installed src-layout distribution without repository-root or ad hoc sys.path assistance.
  2. CLI behavior: documented entry points and module commands preserve expected arguments and exit behavior.
  3. Root resolution: production code finds policies, schemas, curricula, and the output boundary from the new package location.
  4. Output containment: a run directory beneath outputs/ is accepted; an external path is rejected before artifact creation.
  5. Fixture closure: every retained fixture file has a valid manifest entry and active consumer; every declared fixture dependency resolves.
  6. Ignored-state independence: no test or active evidence reference requires durable files beneath ignored outputs/.
  7. Empty-output resilience: the full suite passes with no generated children beneath outputs/.
  8. Schema identity: live $id and $ref values resolve and match the recorded preserve-or-version decision.
  9. Reference integrity: live code, automation, and documentation contain no stale identities or paths except recorded exceptions.
  10. Documentation integrity: documented paths resolve and documented commands execute in their stated environment.
  11. Fresh-clone reproducibility: required fixtures are tracked or produced through documented deterministic setup.
  12. Regression and scope: the existing tests and gates pass, no test is weakened to accommodate the move, and the final delta contains only intended changes plus recorded pre-existing work.
  13. Inventory reproducibility: the inventory tool completes from a fresh clone, does not change the working tree, produces schema-valid machine-readable output, and reports unresolved collection failures as failures rather than empty results.

9. External completion steps

After all executable acceptance tests pass, request authorization to rename the remote repository and local checkout to curriculum_factory. Then update the Git remote and clone documentation and record the observed results in the migration report. These are completion steps, not automated acceptance tests.
