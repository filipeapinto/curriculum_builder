SOTA Research

Plan, execute, challenge, verify, and hand off an auditable state-of-the-art research package under explicit human approval.

Overview

Use this family when a consequential research question needs a versioned protocol, auditable evidence, incident reconstruction, comparative synthesis, independent challenge, deterministic verification, and human acceptance. Do not use it for casual lookup, unplanned browsing, or work whose owner will not approve scope, budget, and acceptance criteria.

The default entry point is $sota-plan-create. Its approved plan is the sole execution contract for $sota-plan-execute. The component contracts are installed; no trustworthy family integration run was found.

System context

Solid ordering means a governed handoff; repair routes return failed artifacts to their owning writer. A review utility dependency means independent challenge consumes frozen synthesis; visualization alternate entry and test repair terminology are compatibility labels only—there is no visualization skill or test-repair skill in this family. Review rejection routes to synthesis disposition; verification failure routes to the owning producer and mandatory verification replay.

Quick start

Default entry point
$sota-plan-create "Create a SOTA research plan in research/r104 for: Why did run R-104 fail? Intended decision: select repository controls. Owner: research lead. Evidence boundary: run logs and approved external literature."

Run from the repository root so structural references and version discovery resolve. Required inputs are the research directory, question, intended decision, owner, and evidence boundary. The first expected artifact is research/r104/plan/<stem>.v1.html with status awaiting approval. Planning completes when its path, predecessor, changes, validation results, and approval state are reported. Execution begins only after explicit human approval: $sota-plan-execute "Execute the approved plan at research/r104/plan/<stem>.v1.html". Execution completes with a verification-backed completion report and an explicit human-acceptance state.

Requirements and constraints

  • Run in a repository containing the structural reference research/llm_failure_analysis/plan/sota_research.plan.v5.html; its absence blocks planning.
  • Install all role skills assigned by the plan. Python 3 is required for plan version selection; deterministic hashing, validation, link/schema checks, rendering, and visual inspection tools are required as named by the plan.
  • Filesystem permissions must allow new versioned plan and run artifacts while preserving predecessors and source evidence unchanged.
  • Network use is limited to approved sources, queries, dates, ceilings, and external-spend controls. Offline or unavailable behavior must be embedded in the plan.
  • Model/tool allocations and deviations must be embedded; the execution run must record actual executor, model version, and effort.
  • Only humans approve plans, material method/budget/authority decisions, and final acceptance. Skills propose, execute, challenge, and verify; they do not self-approve.
  • Excluded: casual research, silent plan repair, overwriting versions, inferring success from artifact volume, and treating verification as acceptance.
