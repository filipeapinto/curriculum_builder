HTML documentation skills: what is worth adopting?

There are credible skills for producing polished HTML artifacts, but no single off-the-shelf skill is a complete answer for an LLM graph runtime. The strongest approach is to use a proven HTML-artifact pattern, then create a small project-specific skill that treats the graph, state contracts, and run evidence as source-of-truth inputs.

AnswerCandidatesRecommendationDesign requirementsSources

Answer

Best immediate reference: Claude’s html-artifacts skill. It is specifically designed to produce self-contained HTML instead of Markdown when an interactive or polished artifact is appropriate. Its focused references for research reports, diagrams, flowcharts, and matching an existing design system are directly useful for this project.

For Codex, the strongest public pattern found is OpenAI’s build-report skill from the role-specific plugins repository. It is not a documentation-site skill, but its HTML delivery standards are unusually mature: a single primary HTML artifact, accessible fallbacks, dark-mode support, and explicit provenance. Codex also has a built-in sites-building capability in this environment, which is appropriate only when this becomes a hosted site rather than local repository documentation.

Neither candidate understands this repository’s LangGraph factory. Installing one wholesale would improve presentation but would not prevent documentation drift. The recommended durable solution is a project-owned llm-graph-html-docs skill, influenced by these patterns and paired with checks against the live graph/config/schema files.

Recommended implementation path

1. Keep one HTML source of truth

Author the reader-facing pages directly as HTML. Do not write Markdown then convert it; that recreates the format split the project wants to remove.

2. Extract graph facts

Use a deterministic extractor to build a checked JSON data contract from graph definitions, node configuration, schemas, and route policy.

3. Render a stable site

Render that data into semantic HTML pages with shared CSS. Keep prose and operational guidance as authored content; keep facts generated or validated.

4. Verify before publish

Fail a documentation check when a node, edge, schema, routing rule, terminal outcome, or cited path no longer matches the runtime.

Create a focused internal skill named llm-graph-html-docs. Its trigger should cover requests to document, visualize, update, or publish this curriculum runtime’s LLM/LangGraph flow as HTML. Bundle: an HTML shell, a graph-data extractor, a source-link checker, a node-catalog template, and an accessibility/visual QA checklist.

The external html-artifacts skill is a good visual/interaction reference; OpenAI’s build-report is a good quality and provenance reference. The internal skill should be the one actually invoked for this repository.

Non-negotiable design requirements for the LLM graph site

  1. Layered reader journeys. Start with a business-level overview, then graph flow, then node-level detail, then operational evidence. Do not expose a raw implementation DAG as the landing page.
  2. Executable facts stay traceable. Every node description identifies its implementation/configuration source; every evidence assertion identifies its receipt/schema source.
  3. Failure paths are first-class. Make retries, repair loops, BLOCKED, NOT_AVAILABLE, and terminal recommendations visible alongside the happy path.
  4. Accessible no-JavaScript baseline. A reader must still be able to read every node, edge, table, and diagram equivalent without JavaScript. SVG diagrams need text alternatives.
  5. No hidden network dependency. Use local assets and inline/static fallbacks. A cloned repository should render its documentation without a CDN.
  6. Explicit freshness. Surface graph/config versions and the exact generation or verification timestamp. Documentation that cannot prove freshness must say so.

Assessment conclusion: adopt the HTML-artifact and provenance patterns; build a small repository-specific HTML documentation skill rather than installing a generic converter as the authoritative workflow.
