Documentation skill set for graph-based LLM-driven systems

Specify an agent-agnostic skill set that turns an implemented graph-based LLM system into trustworthy, usable documentation. The skill set must run on both Claude Code and Codex through a shared core plus thin host adapters.

GoalSystem modelSkill setDocumentationHost adaptersQuality gatesOpen decisions

Goal

Generate documentation that explains how a real graph-based LLM system works, what it can do, how it fails, and what evidence supports each claim.Documentation must be derived from inspected system artifacts—not inferred from a prompt, a diagram, or an agent’s recollection.

The deliverable is a documentation capability, not an HTML generator. HTML is the preferred reader-facing format when it makes graph topology, state, evidence, comparison, or interaction easier to understand. Markdown, JSON, YAML, source code, and receipts remain valid inputs and may remain the best format for contracts, configuration, and diffable operational records.

In scopeOut of scope
Extracting graph facts; documenting nodes, edges, data contracts, state transitions, routes, failure handling, evidence, and operational status; rendering explainers and diagrams; checking freshness and visual accessibility.Changing runtime behavior; accepting releases; inventing missing source data; hiding uncertainty; replacing the system’s schema, audit, test, or observability layers.

Documentation source model

Before prose or visuals are written, the skill set must build a checked documentation model from authoritative repository artifacts. The model supplies facts; prose and diagrams supply explanation.

Node contractPurpose, owner, accepted inputs, produced outputs, side effects, allowed tools, failure outputs, and implementation/configuration path.Node implementation, schemas, prompt/configuration files, and declared tool policy.
State and data contractsState fields, read/write ownership, schema/version, lineage, validation rules, and sensitive-data handling.State models, reducers, schemas, migrations, and policy.

Required skill set

Use small, composable skills rather than one opaque “make documentation” instruction. A coordinator may route among them, but no one skill may silently become the source of truth.

CapabilityResponsibilityMust not do
System inventoryLocate candidate graph, schema, policy, source, test, and evidence artifacts; report which were actually read.Assume a conventional directory layout or claim access to absent systems.
Fact extractionProduce a normalized, machine-checkable documentation model with source paths and identifiers.Fill gaps with plausible topology, contracts, or outcomes.
Claim verificationBind every operational statement and visual label to the documentation model; identify unsupported, stale, or contradictory claims.Approve its own unsupported prose or treat existence of a source file as proof of execution.
Information architectureChoose reader journey, audience level, document sections, and which facts deserve a table, diagram, or prose explanation.Flatten a complex graph into a single unreadable diagram or expose raw implementation detail without orientation.
Diagram renderingRender a visual from an approved diagram brief: exact entities, relationships, labels, audience, detail level, and source IDs.Invent graph entities, conceal failure paths, or substitute visual appeal for factual validation.
HTML document assemblyCreate semantic, navigable, self-contained HTML that incorporates validated prose, tables, diagrams, citations, and freshness status.Require JavaScript, remote assets, or a specific host preview to make the document understandable.
Publication QACheck source links/IDs, no-JavaScript readability, accessibility, rendered legibility, and explicit freshness before release.Report documentation as current when verification did not run or sources cannot be resolved.

Required documentation outputs

  1. Executive overview. Purpose, system boundary, primary outcomes, constraints, and a top-level diagram.
  2. Graph walkthrough. Entry points, node flow, decisions, joins, retry/repair loops, terminals, and failure paths.
  3. Node catalogue. One navigable record per node: contract, data in/out, allowed effects, implementation source, checks, and failure behavior.
  4. Data and evidence trace. How facts, sources, artifacts, hashes, checks, and verdicts move through the system.
  5. Operations guide. Preconditions, run modes, observability, recovery/resume behavior, known gaps, and how to determine whether a result is current.
  6. Reader-level variants. The same factual model expressed for an executive, operator, engineer, or reviewer without changing the underlying claims.

Every document must display its covered system version or digest, inspected sources, verification time, and unresolved gaps. A diagram must have text alternatives and a tabular or prose equivalent for readers who cannot use the visual.

Quality and acceptance requirements

  1. Traceability: every node, edge, state field, terminal, and operational claim resolves to an inspected source identifier or is visibly marked unknown.
  2. Truthful coverage: state which graph/evidence artifacts were included and excluded; never imply complete system coverage from a partial scan.
  3. Failure-first completeness: show non-happy paths whenever source artifacts declare them.
  4. Accessibility: semantic headings, keyboard-operable interaction, contrast sufficient for text, no color-only meaning, and text alternatives for SVG/visual content.
  5. Offline readability: no required CDN, remote font, remote image, or JavaScript dependency; the file remains understandable when opened locally.
  6. Rendered QA: inspect the emitted HTML in a browser or render path when available; otherwise record the unavailable validation rather than claiming visual review.
  7. Freshness: display when and against which source digest/version the document was checked; fail or visibly stale-mark a document when that check cannot run.
  8. Safe writes: produce versioned outputs in an approved documentation location; do not overwrite a prior accepted artifact without explicit authorization.
