curriculum_factory

A single-operator, contract-first pipeline that turns one curriculum manifest into reviewed, accepted curriculum units and a workbook. It is a LangGraph state machine in which all routing authority is code-owned: models author and review artifacts, and are structurally prevented from deciding what happens next.

Terms and naming

Read this before the figures. Every ID convention and overloaded word the rest of the guide depends on is defined here once, and the two names that collide with unrelated things in this repository are separated explicitly.

Node ID convention

Every node in the compiled graph is <prefix><number>_<VERB_PHRASE>. D… is a deterministic node — plain Python, no model, code-owned routing. M… is a model node — the only nodes that reach a model, and only through the transport. Numbering is positional, not chronological: D00–D32 are the product path in run order, and the D9x band is cross-cutting infrastructure reachable from almost anywhere — D90 reserves a model attempt, D91 classifies a model failure, D92 re-enters after a resume, D96 is the interrupt gate, D98 is the single terminal writer. D00R and D06B are later insertions into an already-frozen numbering, not sub-steps of D00/D06. §4 carries a row for every ID that appears in any figure or table in this guide. observed

Two names that collide with something else in this repository

"Plan 26" is a plan directory, and "engine root" has three prose aliases
  • Plan 25 / Plan 26 are engine-generation codenames, and they are the numbered directories plans/25_curriculum_factory_graph/ and plans/26_langgraph_curriculum_factory/ — the plan that specified each generation gave it its name. The current runtime is Plan 26 and says so in its own docstrings (src/curriculum_factory/__init__.py:1, "The Plan 26 curriculum-factory runtime"). What is unrelated is plans_internal/, which holds documentation- and refactor-tooling plans and has no engine generation in it, and plans/27_…, which is a remediation plan against Plan 26 rather than a further generation. A "Plan 26" reference in code therefore points at a specification under plans/26_…/, not at an abstract release label. observed
  • "Engine root", "engine tree" and "repository data root" are one value. The CLI flag is --engine-root; transport.py:2088 assigns it as self.engine_root = roots.repository_root(engine_root), and roots.py:1,33 calls that same value the repository data root. "Engine tree" appears only in prose (including v1–v4 of this guide) and is not a code identifier. §9 lists the distinct roots the code really has — engine, curriculum, output, package-resource — which are four different things. observed

1Purpose and boundary

The system consumes one immutable curriculum manifest and one immutable engine tree, and produces accepted curriculum units — domain data, written content, visuals, a rendered PDF — and finally an assembled workbook, entirely underneath a caller-supplied output root. Its single actor is a human operator on their own machine, holding their own Claude and Codex subscription credentials. There is no service, no API and no second user. observed

Its entry interface is one CLI invocation; its exit interface is a JSON terminal record on stdout plus a process exit code. Between those two points it makes exactly one call to compiled.invoke() (run_curriculum.py:827) — the CLI runs no product step itself.

What it is on the hook for

  • Deriving the unit count and order from the supplied manifest, not from configuration.
  • Proving, before any model runs, that the sandbox and both model CLIs are actually present and behave as the frozen registry expects (D03_PROVE_CAPABILITIES).
  • Never letting a model decide a route, a verdict or a terminal.
  • Writing nothing outside the output root it was given.
Exclusions a reader will otherwise assume
  • Curriculum content is not in the package. curricula/, policy/, schemas/ and meta_prompt/ are repository-owned data supplied by path at runtime. Packaging confirms this: pyproject.toml includes only curriculum_factory* from src/.
  • No scheduling, queueing, concurrency or multi-run coordination. One flock per output root is the entire concurrency model; a second process gets exit 3 and does nothing.
  • No graceful stop. The mechanism exists but is not wired — see §12.
  • No backup, retention, rotation or cleanup of anything it writes. Verified absent across the checkpoint DB, all ledgers and the artifact store.
  • Not portable off macOS. build_sandboxed_argv raises CapabilityProofFailed when sandbox_mechanism() is "none", which is the case on any non-Darwin host (transport.py:928).

Assumptions it makes about its environment, each enforced rather than documented: an operator-owned ~/.claude.json and ~/.codex/auth.json exist; no *_API_KEY variable is set (their presence fails the capability proof); pandoc/typst and the poppler tools are installed; and the output root is empty or absent for a fresh run.

Repository inputs, concretely

The figure above names four things the factory reads at --engine-root / --curriculum. Naming them is not enough to work with them, so here is what each one actually contains — the smallest real slice that shows its shape, not an invented example.

curricula/*/manifest — a curriculum's single source of truth, e.g. curricula/arduino_kit/arduino_kit_curriculum.v5.yaml (the one real manifest in the repository: 35 units, L01–L35). --curriculum accepts either this file directly or its parent directory — _resolve_curriculum_root() (run_curriculum.py:191-201) takes the file's parent either way. observed

The manifest filename is load-bearing, and the CLI never takes it by path Whatever --curriculum resolves to, the engine globs the curriculum root for *curriculum.v<N>.yaml, ignores anything under a deprecated path segment, and picks the highest N (nodes/inputs.py:418-437). A manifest named anything else is invisible; two manifests in one directory means the higher version silently wins. There is no flag to name the file. observed

curriculum.delivery and curriculum.design_rule are free-text schema strings (type: string, no further constraint) stating the pacing rule and the pedagogical organizing principle in prose — the engine does not parse or enforce either; they are read by nothing except a human author and, presumably, whichever model prompt quotes them into a generation request. domain.calibration names one more curriculum-owned YAML file (the physical kit's measured/reference values, kit_calibration.v1.yaml) that the domain verifier's dependencies list may draw on. domain.config is the one open-shape key in the whole schema (additionalProperties: true at that node) — the engine imposes no structure on it at all; arduino_kit uses it to carry circuit_policy, a pointer to its circuit library, and the two retired top-level concepts (kit_power_profile, visual_system) that v5 moved under this domain's own ownership (see the manifest's own header comment). No generic domain template exists domain.schema, manifest_schema, calibration and verify_domain.py are shown above only as arduino_kit's own artifacts, because arduino_kit is the only curriculum in this repository (curricula/ has exactly one subdirectory) and there is no template/example domain anywhere in the tree. Can an operator add a profile? Yes — it is plain YAML with no JSON Schema anywhere in schemas/. The only constraints live in the loader (egress.py:402-452): the named profile must exist, hosts must be a non-empty list, and each entry must be a bare, lowercase, unique hostname — any of *, ?, /, :, @ or a space in a host is rejected, so no wildcards, no URLs, no ports. The file's SHA-256 becomes the policy_digest recorded on every fetch, and the file is hashed into the run's frozen inputs, so editing it between a run and its resume makes the resume refuse. Ownership is asserted in the file's own header — "Adding a host to a profile is a deliberate, reviewed change to this file, never a runtime decision" — but no CODEOWNERS or named owner exists in the repository (§10). observed

What (N30V7-F07) in that manifest comment means IDs shaped N<node>V<generation>-F<ordinal> are execution findings from the Plan 27 remediation package — not ticket numbers, not spec clauses. 3Graph behavior

The graph is framework-defined, not prompt-orchestrated. Nodes and edges are registered into a LangGraph StateGraph at build time and a model never chooses the next step: a node body emits a pending_guard record carrying one declared string value, and a pure guard function maps that value to exactly one destination. A value outside the frozen table raises RoutingViolation rather than resolving to a terminal, because a table/body disagreement is a build defect, not a run outcome (routing.py:1-26). observed

Compiling the graph on this machine yields 50 nodes and 158 edges, digest 0e1eca87080aa102…. Two rules run before any node-specific routing rule, in this order: a classified pending_failure routes to the terminal writer (to D91 for a model node, whose failures are the one class a classifier may retry), and only then does an observed interrupt route to the interrupt gate. Failure deliberately outranks interruption so that an episode which broke and was asked to stop is not recorded as merely INTERRUPTED.

Concurrency: one job in flight, N activations of it

Correcting a contradiction v4 carried

v4's §8 said dispatch is bounded "to one in-flight model activation by the graph's own shape", while §5 described union_disjoint reducers existing so two workers can return order-independently. The reducer description was right and the concurrency claim was wrong.

Send fan-out is real and is the system's only parallel dispatch. Four nodes fan out (routing.py:277-284): D06 and D06B stage M01 discover/interpret, D12 stages M04, and D10 fans out to the deterministic worker D11. D90 loops over every staged member, reserves one attempt each, and returns one Send per member — so N activations of one job run in the same superstep (LangGraph's term for one Pregel round: every node the prior round activated runs once, concurrently, before the graph advances). A runtime test asserts exactly this shape: "Two Send maps of two members each: four M01 activations, no more" (tests/runtime/test_plan26_unit_graph.py:1490-1495). The concurrency reaches the OS: the transport's own comment records that a concurrent fan-out of sandboxed launches reproducibly produced EPERM for a fraction of them (transport.py:543-545) — but this is a fixed, historical defect (N70), not a live risk. The sandbox profile now grants the installed claude CLI's own /tmp/claude-<uid> runtime-scratch path explicitly; the regression test that pins this fires nine concurrent sandboxed launches and asserts 0/9 failures, where the same fixture failed 9/9 before the fix (tests/runtime/test_plan26_transport.py:574-596). It remains here as proof that concurrency really reaches the OS, not as an open operational hazard — an operator on the current tree should not expect to see it.

Is the interrupt race real, or does it contradict "nothing can ever trigger D96" (§12)? Both claims are true and do not conflict. The "real race" is exercised by test_an_interrupt_inside_a_send_map_is_bounded_across_repeated_episodes (tests/runtime/test_plan26_unit_graph.py:1945-1962), which drives the interrupt via _run_episode(..., interrupt_after=...) — a test-harness injection that bypasses InterruptToken entirely. It proves the graph's own routing is race-safe if an interrupt were ever raised: across twelve episodes and every interleaving, exactly one terminal is written and no attempt reservation ever follows the gate. It does not mean an interrupt can fire in a live run — nothing in src/ ever calls InterruptToken.set(), so D96 is proven safe but currently unreachable in production, exactly as §12 says. observed

The accurate statement: one model job is dispatched per superstep (one dispatch per staged packet), and N activations of that job run concurrently. The six union_disjoint channels are load-bearing for exactly those workers, not defensive. What is bounded to one: one OS process per output root (flock), and one attempt per counter key, committed before dispatch. No concurrency limiter is configured — invoke_config passes only thread_id and checkpoint_ns, no max_concurrency, and policy/limits.v1.yaml's per_run.max_concurrency: 1 is inert (nothing loads that file).

Visuals: where M04 sits, and what never happens to its output

M04 is not on the M03 → D09 line that figure 2 draws; that is why the figure skips it. The real shape is D09 → D10_COMPILE_VISUAL_BRIEFS → D12_VISUAL_BARRIER_AND_JOIN, and M04 hangs off the barrier. D10 splits the visual denominator in two (nodes/visuals.py:66-74): a brief whose kind is authoritative — build_map, schematic, netlist, power_path, connectivity, safety_inset, circuit, pinout, pin_map, breadboard, wiring, electrical, terminal_block — goes to the deterministic worker D11; everything else is a model brief. D12 then stages the M04 fan-out for the model subset, or admits the visuals head directly if there is none. M04's single outgoing edge is a plain unconditional M04 → D12 (unit_graph.py:59-62), and its only predecessor is D90. A unit declaring no non-authoritative visuals never touches M04 at all. observed

What actually happens when M04 fails. M04 is the only primary model node with no edge to D91_CLASSIFY_MODEL_FAILURE — so, unlike M01/M02/M03/M05, a failed M04 activation is never transport-retried and never gets the 2-attempt D90 budget. It also never crashes the run: m04_create_unit_visuals (model_nodes.py:1555-1591) never raises on a bad candidate — a transport-level failure returns a (None, failure_update) pair, and every content violation (wrong brief, undeclared artifact, an asserted-authoritative visual — which a model may never claim, per spec section 13) returns through _reject(...). Neither path writes a visual_results entry for that key, so the candidate is simply absent when D12 joins the barrier. D12 then raises a normal unit visual finding — "visual candidate is missing hash, format, or declared provenance" (nodes/visuals.py:545-557) — which routes through the ordinary visuals_repairable path to D17, the same repair pipeline any other content defect uses. Because M04 may never produce an authoritative visual (that would violate spec section 13), every M04-sourced finding is by construction the non-authoritative case, which §3's repair discussion above establishes can actually be repaired (routes to M06, not into the broken deterministic branch). Net effect: an M04 failure costs the 2-attempt model budget it never had, but is not a dead end — it becomes one ordinary repairable finding, capped by the same 3-per-chain attempt bound as any other unit visual defect. observed

Repair: what is repairable, and what the deterministic branch actually does

The fork between the repair loop and a terminal is at D17_CLASSIFY_UNIT_FINDINGS, and there is no severity ladder for deterministic checks and no policy file involved. Repairability is structural, in four layers: observed

  1. Producer level. A deterministic gate that can name an owner and a boundary pointer emits its finding under a …_repairable guard (domain_repairable, layout_repairable, …). Anything raised instead as a SystemFailure — cause integrity, schema_contract, capability, join, tool, persistence — is unrepairable by construction and routes straight to D98.
  2. Review level. Only severity == "blocking" from M05 counts. major, minor and observation are discarded entirely (acceptance.py:209-218).
  3. Normalisation at D17. A finding is repairable only if it maps onto the five-owner vocabulary — source interpretation, curriculum domain, unit content, unit visual, unit layout (repair.py:75-81) — and carries a boundary pointer and names a parent hash that is still the current admitted head. A model's own category string is never trusted as an owner: it is mapped through a frozen keyword table, and an unmapped category is a system fault, not a finding.
  4. Exhaustion. A repairable finding becomes terminal when a bound trips (below).

Deterministic vs model repair. D19 routes by owner, not by judgement (repair.py:108-112): curriculum domain, unit content and source interpretation are model-only (→ M06); unit layout is deterministic-only; unit visual is deterministic only if every named brief is authoritative. Mechanically the deterministic branch is not a re-render — it is an RFC-6901 pointer patch of the parent body, taking each boundary pointer's replacement value from the finding's own allowed_facts map, then staging the child itself and skipping D90/M06 entirely.

Verified gap: the deterministic repair branch cannot currently succeed — for either owner that can reach it allowed_facts is only ever read, never populated, anywhere in the codebase (confirmed by searching every assignment site, not just the two producers below). D08, D09, D12_VISUAL_BARRIER_AND_JOIN and D14 all emit {check_id, owner, pointer, message[, parent_hash]} and nothing more (nodes/visuals.py:549-557 for the unit visual case, nodes/render.py:210-215,257-261 for unit layout). Only two owners can ever reach _deterministic_repair_candidate at all: unit layout (DETERMINISTIC_ONLY_OWNERS — every layout finding goes deterministic, unconditionally) and unit visual (CONDITIONAL_OWNERS — route_owner() sends it deterministic only when every named visual brief is authoritative; a non-authoritative brief always goes to M06 instead, repair.py:296-315). Both, whenever they do take the deterministic path, reach repair.py:681 with an empty map and raise SystemFailure("invalid_input", "deterministic repair has no admitted fact for boundary pointer ...") — /pages/N for layout, /visuals/<key> for visual. Every layout defect, and every authoritative-visual defect, therefore ends the run as SYSTEM_FAILURE rather than being repaired; only a non-authoritative visual defect survives, because it routes to the model instead. observed

When D17 partitions findings across more than one owner, which gets repaired first — and what happens to the rest? D18_PLAN_TARGETED_UNIT_REPAIR walks the fixed tuple REPAIR_OWNERS = ("source interpretation", "curriculum domain", "unit content", "unit visual", "unit layout") in that literal order and selects the first owner in the tuple that (a) has a partition member for this unit and (b) has no repair request already open. Everything else in the partition is not discarded — it stays latent in finding_partitions and is picked up on a later pass through D17→D18 once the selected owner's repair request resolves (or itself exhausts). One consequence worth naming: source interpretation and curriculum-domain defects are always repaired before content, visual or layout defects in the same pass, by construction, not by severity. observed From: repair.py:75-81,559-572

Does a retried attempt know why the previous one failed? For the five primary jobs (M01–M05) the answer is no — build_projection reads a fixed per-job allowlist (PROJECTION_SPECS[...].allowed, model_nodes.py:303-395) that has no prior_failure/previous_attempt field in any of the eight specs; a retried attempt 2 is dispatched with the identical projection as attempt 1, distinguished only by its attempt_ordinal. The two repair jobs are the exception: M06's and M08's allowed projections include findings/defect directly, so a repair dispatch does carry what was wrong — it is only the blind primary-job retry that is a coin flip. observed From: model_nodes.py:303-395

The release audit, and what COMPLETE has to survive

The "release audit" v4 mentioned without defining is the record produced by D32_RECOMPUTE_FINAL_RELEASE into the final_release_audits channel. It re-derives from scratch rather than reusing D28's verdict, and all five categories must pass (workbook.py:696-821): observed

Resume: D04 and D92 are two nodes, not one delegating to the other

They are separate graph nodes joined by one conditional edge, and they do different jobs. What survives a crash

Four independent layers persist, and they do not all agree on how carefully:

  • The checkpoint DB — .langgraph/checkpoints.sqlite3, LangGraph's SqliteSaver with WAL + synchronous=FULL + busy_timeout=30000, re-verified after setup() because setup may relax them. Thread id is <run_id>:episode:<ordinal:06d>; checkpoint_ns is always the empty string. observed
  • Hash-chained JSONL ledgers under .langgraph/ — each record carries prev_hash and a contiguous ordinal, so a deleted or reordered line is detectable rather than merely lost.
  • The content-addressed artifact store — blobs by SHA-256, version records, and one mutable file per stream: the head pointer. That head pointer is the only thing in the entire store that is ever overwritten; anything under an accepted/ path is refused even with overwrite=True and is chmod'd 0444/0555.
  • Egress receipts — .evidence/egress_receipts.jsonl, the only evidence log with a production writer.
Two durability guarantees that are declared but not wired

flush_checkpoint_durability() (persistence.py:555) commits, forces a full WAL checkpoint and fsyncs the DB, the WAL and the directory. Its own docstring says this is required "before a receipt or terminal may pass". It has no caller in src/. Likewise AdmissionLedger.admit() — the mechanism documented as making "a crash between a committed side effect and its checkpoint non-duplicating on retry" — is never called, so admissions.jsonl is only ever created empty.

What that costs the reader: a machine that loses power between a node returning and SQLite flushing its WAL may lose the last checkpoint, and the artifact-store side effect that node already committed will be redone on replay. The idempotency keys make redoing it safe; the missing flush means you may replay further back than the guide's own design intends. inferred

Pausing: what causes it and what the resume condition looks like

PAUSED_PREREQUISITE (exit 11, resumable) has exactly one production producer: D30_CLASSIFY_PREREQUISITE, reached when D07 finds it cannot close the source denominator and emits prerequisite_unresolved. D30 requires that exactly one named external fact is outstanding — more than one is a SystemFailure, not a pause — and builds the candidate with the fact, its locators, the attempt count, a resume frontier pointing back at D06B_RETRIEVE_SOURCE_CANDIDATES, and a required_resume_condition. observed

required_resume_condition is a non-empty string, and there is exactly one construction site (nodes/sources.py:911), so its shape is fully determined:

f"named external fact {fact} becomes retrievable"

# where `fact` is a source-request key: <unit_id>/<source_epoch>/<fact_id>
# so a real value the code produces is:

"named external fact U001/1/required_explanation:000 becomes retrievable"

It is not free text an operator can act on beyond "make that source reachable": there is no host, no URL and no suggested remedy in it. D98 re-derives the pause independently and rejects it if the string is empty or if pending_failure["class"] != "pause" — a tool, integrity or schema fault may not wear a pause candidate and look benign.

Two defects around pausing an operator should know
  • Three explicit pause sites never reach D30. PrerequisitePause is raised in D03, D06 and D06B — but the deterministic-node boundary converts any expected failure into a SYSTEM_FAILURE candidate and routing sends a truthy pending_failure straight to D98, bypassing D30. A pause raised there therefore terminates as SYSTEM_FAILURE, exit 20, non-resumable. Only D07's guard-value path (which raises nothing) produces a real pause.
  • attempts in the pause record is always 0. It reads the retrieval:<fact> counter, which no production node writes.
observed

What an operator can actually do about a PAUSED_PREREQUISITE, since the message itself names no host or URL: inferred from the pieces above, not a documented procedure — no such procedure exists in the repository.

  1. Parse <unit_id>/<source_epoch>/<fact_id> out of required_resume_condition (e.g. U001/1/required_explanation:000). The <key>:<ordinal> suffix is an index into that lab's _FACT_BEARING_KEYS entry — the four manifest fields whose list items each need a source, enumerated in §8's "widest fan-out" box below (required_explanation, core_activity, safety_focus, applications) — so ordinal 000 of required_explanation is that field's first list item in the manifest, and you can read the actual claim that needs a source back in the manifest YAML.
  2. Grep .evidence/egress_receipts.jsonl for entries around the pause and for the unit id; a host_not_pinned or unauthorized_socket_no_active_retrieval denial there is usually the reason no candidate source was ever found for that fact.
  3. If a real host exists for that claim but isn't allowlisted, add it to the manifest's retrieval_host_profile in policy/retrieval_hosts.v1.yaml (§2) — this changes the policy digest and is a reviewed change, not a runtime one, so it must happen before --resume, not during it.
  4. --resume with the same three root flags. D92 will re-enter at the stored frontier (D06B_RETRIEVE_SOURCE_CANDIDATES) and try the fact again.

What a partial --all failure leaves behind

If unit 5 of 10 exhausts its bound, the whole run stops there. Every convergence_exhausted guard routes to D98, whose only outgoing edge is END. Correction to v6: v6 stated here that D05_SELECT_NEXT_UNIT "has exactly two inbound edges" — that omitted a real one. routing.py's static GUARD_DESTINATIONS table wires exactly two forward edges into D05 (D04's fresh_initialized guard, and D23's checkpoint_correlated guard after an acceptance) — but D05_SELECT_NEXT_UNIT is also a member of RESUME_REENTRY_DESTINATIONS (unit_graph.py:138-151), so D92's dynamic resume re-entry can legitimately land there too if that is what the stored, validated frontier names (§4's node-inventory row for D05 — "Reached from: D04, D23, D92" — was already correct; this prose restatement was not). Within one uninterrupted --all invocation with no crash, D92 never fires, so the practical claim holds: the only way to reach unit 6 in that single episode is by accepting unit 5. There is no skip, defer or continue-on-failure edge, and the CLI has no per-unit loop — it makes one invoke() call and maps the terminal to an exit code. Units 6–10 never execute in that episode. observed

The four already-accepted units: their bytes are on disk and readable standalone, because artifacts are written at admission time by the node boundary, not at acceptance — <output_root>/units/<id>/versions/<channel>/blobs/<sha256> with a head pointer per channel — and each unit's PDF was written by the renderer under <output_root>/.render/<id>/<parents-digest>/<id>.pdf. Nothing deletes them; there is no cleanup path. But three caveats decide whether they are usable:

  • Acceptance itself is not on disk. D22/D23 write zero bytes — the receipt lives only in the checkpoint state and in the terminal JSON on stdout. ArtifactStore.accept(), which would seal a units/<id>/accepted/<receipt_hash>/ directory, has no production caller, so that directory is never created. There is no on-disk marker distinguishing an accepted unit from an abandoned one.
  • The layout channel has no on-disk head. D13 is not an admission node, so a repaired unit leaves several sibling .render/<id>/… directories with no tiebreaker on disk; the authoritative PDF hash is in state.
  • The output root is not reusable. CONVERGENCE_EXHAUSTED is non-resumable, and a fresh run refuses a non-empty output root that carries no resumable run. Copy the units and renders out; do not try to restart in place.

They are, in short, retained and physically usable, but only as loose artifacts — nothing in the system will treat them as accepted again, and workbook assembly could not consume them anyway (§3). observed

All eight also share one negative-space contract worth stating once: every projection spec's denied list (§2's Concreteness table and PROJECTION_SPECS, model_nodes.py:303-384) is checked against every key nested anywhere in what the model is given, not just top-level keys — so a job cannot receive a sibling unit's artifacts, prior repair history, or routing/acceptance state buried inside an otherwise-permitted field.

Structured output and its failure path

Models are invoked as subprocesses, not APIs. Codex writes result.json into its workspace; Claude's structured output is extracted from the last result event of its stream-json output. Parsing is strict single-document, and each way it can fail is its own class — empty_result, fenced_result (any markdown fence), malformed_json, trailing_material, result_is_not_an_object, duplicate_json_key, non_finite_json_constant, then schema_invalid_result against the job's JSON Schema (Draft 2020-12).

Two gates then run that a reader would not expect from a schema check. assert_no_authoritative_fields rejects a candidate — or a schema — containing any control-plane key such as a route, verdict or terminal name (transport.py:274). And workspace.assert_no_undeclared_writes(permitted_new=("result.json",)) fails the attempt if the model wrote any other file. Together these are the mechanism behind "a model has no routing authority": it is enforced at the transport boundary, not trusted to the prompt.

8Deployment

There is no deployment

The pattern deploy/** matched nothing in the source register — recorded as an evidence gap rather than silently dropped. There is no Dockerfile, no infrastructure-as-code, no service manifest, no hosting configuration anywhere in the repository. This section is therefore about the only environment that exists: an operator's laptop. observed

Runtime topology is a single Python 3.13 process (pinned >=3.13,<3.14) that spawns one short-lived sandboxed child per model activation, per render and per inspection. There are no workers, no queues, no network services, and no horizontal scaling story. Concurrency is bounded to one process per output root by flock — and that is the only bound. Correcting v1–v4: model dispatch is not limited to one in-flight activation. One job is dispatched per superstep, but D90 issues one Send per staged member, so N activations of that job — and therefore N sandboxed child processes — run at once, with no max_concurrency configured anywhere (§3). Sizing a machine for this run means sizing it for the widest fan-out the manifest produces, not for one subprocess.

What "widest fan-out" actually is, computed from the real manifest observed for M01, inferred for M04:

  • M01 (source discovery+interpret) is statically computable from the manifest — compile_unit_source_requests derives one request per entry of four fact-bearing keys (required_explanation, core_activity, safety_focus, applications; a scalar key like core_activity counts as 1). Running it against arduino_kit_curriculum.v5.yaml: the widest unit is L21 with 10 requests (the shift-register lab's longer required_explanation); the narrowest is L02/L03 with 6. Each request spawns one M01 discover activation and, if it resolves, one M01 interpret activation — so the real peak for M01 alone is on the order of 10 concurrent sandboxed claude children for this manifest, not the 4-item visual_roles count a reader might reach for first.
  • M04 (visual briefs) is not statically computable from the manifest. Its fan-out is the length of the visuals list M03's generated content declares (nodes/visuals.py:108-110, reading body.get("visuals", []) from the admitted content artifact) — a runtime, model-authored value, not a manifest field. The manifest's own visual_roles (4 for L01, the widest in this manifest) states what content generation is expected to cover, but nothing in the code enforces that the generated visuals list has exactly that length; §3's "even the deterministic SVGs never reach the PDF" gap is a symptom of the same loose coupling. Treat 4–10 as a reasonable planning range for this manifest, not a guarantee.

Per-activation resource cost is otherwise unmeasured — no RAM/CPU-per-activation figures exist anywhere in the repository; each activation is a short-lived sandbox-exec child running a CLI subprocess, so the practical bottleneck an operator will hit first is almost always the model provider's own concurrent-request limit, not local machine resources. unknown

What providers and executables really constrain

providers maps a provider name to the data classes it may receive. Only three provider names exist (anthropic, openai, primary_source_hosts) and each has a fixed set of permitted classes; an unknown provider or an undeclared class is rejected when the record is constructed. At run time, authorize_transmission() is called before the child process exists and refuses if the provider is absent from the map or any requested data class is not in its list — alongside expiry, run scope, curriculum digest and output-root checks. An empty providers map authorizes nothing, which is why the fixture in §12 works for CLI-shape tests and would fail the moment a model job dispatched.

executables is an optional list of {name, path}. D01 SHA-256s each path that exists and stores it as frozen_executable_identities; D03 re-probes the installed binary and fails the run with cause identity if either the path or the hash differs. It pins the model CLIs by content — so a claude or codex upgrade mid-run is refused rather than silently accepted. An empty list disables the pin entirely (no entry, no possible mismatch). observed

Release path. Dependencies are pinned exactly in pyproject.toml (LangGraph 1.2.9, langgraph-checkpoint-sqlite 3.1.0, jsonschema 4.26.0, PyYAML 6.0.3, Pillow 12.2.0) and hash-locked in requirements/plan26.lock, whose drift is the one thing CI enforces. There is no versioning, migration, feature-flag or rollback mechanism for the factory itself: the rollback story is git.

Verified gaps
  • The sandbox constrains the model child by port, not by host. Its network rule allows outbound TCP to any host on 443 and 80 and UDP on 53. The code says so itself and records it as a non-required capability facet named subprocess_network_scope (transport.py:1058-1066). A compromised or misbehaving CLI child can reach any host on those ports; the elaborate parent-side allowlist does not apply to it.
  • M01's WebSearch is outside every control described above. It executes inside the Claude child, so neither EgressGuard nor RetrievalPolicy sees it. Only the locators it returns are re-checked. Granting it also forces that activation to --permission-mode bypassPermissions.
  • Model stdout and stderr are persisted verbatim and hashed. Redaction is a single rule — argv tokens longer than 200 characters are replaced by a hash — applied to one field. Nothing scrubs a credential or personal datum that a CLI happened to print to stderr, and nothing redacts prompts, model outputs or state values in any ledger or checkpoint.
  • No retention or deletion exists anywhere. Everything the system writes — checkpoints, ledgers, receipts, artifacts, model output — accumulates indefinitely under the output root. By construction it cannot be truncated: a hash chain with contiguous ordinals fails its own audit if a line is removed.

11Observability

The design intent is unusually strong: six hash-chained evidence logs (events, activations, routes, executions, checkpoints, index), each append-only, flock-protected, fsync'd, schema-validated, and able to distinguish a tampered record from a deleted one from a torn append.

Blind spots — read this before you rely on anything above
  • EvidenceStore.append() is never called from src/. The store is constructed at graph.py:227 and injected into every node's RuntimeContext as evidence_service, and no node body uses it. Five of the six logs have no writer anywhere; the sixth has one writer called only from tests. evidence/*.jsonl is never created at runtime. observed
  • Consequently evidence_index_entries is always empty, so D98's log_high_water_mark ceiling is checked against nothing, and write_audit_report() never runs.
  • No logging framework at all. grep for import logging, prometheus, opentelemetry, statsd, datadog, sentry across src/ returns zero matches. No levels, no handlers, no diagnostic log file. Console output is 15 print() sites.
  • No metrics, traces, spans, dashboards, alerts, health endpoint or SLO. Nothing is exported anywhere.
  • No timing anywhere. No node duration, no model-call latency. Timestamps exist only as time.time_ns() inside ledger payloads.
  • The legacy ExecutionLogger — the one thing in the repo shaped like an operational log — carries no run id, no episode id and no time of day, only a date. It is also unreachable from langgraph_factory.
  • Episode leases are opened and never closed. close_episode() has no caller in src/, so every run leaves an open lease and every --resume is forced down the orphan-recovery branch. The plain resume branch appears to be unreachable in practice. inferred

What an operator actually has. Two things: the terminal JSON printed on stdout (kind, exit code, resumability, heads, validation results) and .evidence/egress_receipts.jsonl, which records every allowed and denied network attempt with its reason. Everything else — whether a node is slow, which unit is in flight, how many attempts have been spent — must be inferred by reading the SQLite checkpoint or watching the process. Plan for that before an incident, not during one.

Do not
  • Do not send SIGINT expecting a clean stop. InterruptToken.install() has no caller in src/, no code calls set(), and is_set() returns a private in-memory boolean — the .langgraph/interrupt.token file is written, never read. There is no signal handler in run_curriculum.py at all. Ctrl-C therefore kills the process at whatever point it had reached, leaving an open episode lease and no terminal record. D96 is compiled and reachable in the topology but nothing can trigger it. observed
  • Do not delete or empty the output root to clear a COLLISION. It holds the only copy of the checkpoint, the identity envelope and the accepted artifacts. Move it aside instead.
  • Do not edit anything under the output root by hand. The identity envelope is 0444 and hash-verified; ledgers are hash-chained; artifact records are re-hashed on read. A hand edit surfaces later as CheckpointCorrupt or EvidenceCorrupt, and the run refuses.
  • Do not change --engine-root, --curriculum or --output-root between a run and its resume. All three are hashed into run_id; the resume refuses with an identity drift naming the field.
  • Do not trust src/curriculum_factory.egg-info/entry_points.txt. It still advertises capability-cycle, finalize-evidence and session-bridge, whose modules were deleted in f6a8aca. pyproject.toml publishes one console script and that is the only one that exists.
  • Do not run two processes against one output root. The second gets exit 3 — which is the system working — but do not defeat it by copying the root.

Triage

  1. Read the terminal JSON on stdout first. It carries the kind, the failing node, the safe artifact heads and the validation rejections. It is more informative than anything on disk.
  2. If the kind is SYSTEM_FAILURE with node: "D98_WRITE_TERMINAL" and cause: "integrity", another node proposed a terminal that D98's independent re-derivation rejected; the rejected_candidate_kind and the rejection list name what did not hold. Escalate — this is a correctness fault, not an environment fault.
  3. Check .evidence/egress_receipts.jsonl for denials. A host_not_pinned or unauthorized_socket_no_active_retrieval entry usually means the retrieval profile does not list a host the run needed.
  4. For a crash with no terminal (killed process, power loss), the run left an open lease. Resume takes the orphan-recovery path, which re-enters through D92 at a validated frontier with the transport and retriever disabled for that step.
Recovery has no backup and no rollback There is no restore procedure, because there is no backup: nothing copies the output root, and the only rollback primitive in the system is git, which does not cover generated output. Artifact history is preserved by construction (every version is retained; only the head pointer moves), so a bad head can in principle be reasoned about from the version records — but no code exists to move a head backwards. Treat the output root as the single copy of the run and back it up yourself before intervening. observed
