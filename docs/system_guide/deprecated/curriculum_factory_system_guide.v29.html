curriculum_factory

A single-operator, contract-first pipeline that turns one curriculum manifest into reviewed, accepted curriculum units and a workbook. It is a LangGraph state machine in which all routing authority is code-owned: models author and review artifacts, and are structurally prevented from deciding what happens next.

Terms and naming

Read this before the figures. Every ID convention and overloaded word the rest of the guide depends on is defined here once, and the two names that collide with unrelated things in this repository are separated explicitly.

Node ID convention

Every node in the compiled graph is <prefix><number>_<VERB_PHRASE>. D… is a deterministic node — plain Python, no model, code-owned routing. M… is a model node — the only nodes that reach a model, and only through the transport. Numbering is positional, not chronological: D00–D32 are the product path in run order, and the D9x band is cross-cutting infrastructure reachable from almost anywhere — D90 reserves a model attempt, D91 classifies a model failure, D92 is the deterministic re-entry point designed for a resume — but see the corrected box in §5, "Pausing": in production every --resume is misrouted to orphan recovery before D92 is ever reached, so this node's real-world reachability is narrower than its name implies. D96 is the interrupt gate, D98 is the single terminal writer. D00R and D06B are later insertions into an already-frozen numbering, not sub-steps of D00/D06. §4 carries a row for every ID that appears in any figure or table in this guide. observed

Two names that collide with something else in this repository

"Plan 26" is a plan directory, and "engine root" has three prose aliases
  • Plan 25 / Plan 26 are engine-generation codenames, and they are the numbered directories plans/25_curriculum_factory_graph/ and plans/26_langgraph_curriculum_factory/ — the plan that specified each generation gave it its name. The current runtime is Plan 26 and says so in its own docstrings (src/curriculum_factory/__init__.py:1, "The Plan 26 curriculum-factory runtime"). What is unrelated is plans_internal/, which holds documentation- and refactor-tooling plans and has no engine generation in it, and plans/27_…, which is a remediation plan against Plan 26 rather than a further generation. A "Plan 26" reference in code therefore points at a specification under plans/26_…/, not at an abstract release label. observed
  • "Engine root", "engine tree" and "repository data root" are one value. The CLI flag is --engine-root; transport.py:2088 assigns it as self.engine_root = roots.repository_root(engine_root), and roots.py:1,33 calls that same value the repository data root. "Engine tree" appears only in prose (including v1–v4 of this guide) and is not a code identifier. §9 lists the distinct roots the code really has — engine, curriculum, output, package-resource — which are four different things. observed

1Purpose and boundary

The system consumes one immutable curriculum manifest and one immutable engine tree, and produces accepted curriculum units — domain data, written content, visuals, a rendered PDF — and finally an assembled workbook, entirely underneath a caller-supplied output root. Its single actor is a human operator on their own machine, holding their own Claude and Codex subscription credentials. There is no service, no API and no second user. observed

Its entry interface is one CLI invocation; its exit interface is a JSON terminal record on stdout plus a process exit code. Between those two points it makes exactly one call to compiled.invoke() (run_curriculum.py:827) — the CLI runs no product step itself.

What it is on the hook for

  • Deriving the unit count and order from the supplied manifest, not from configuration.
  • Proving, before any model runs, that the sandbox and both model CLIs are actually present and behave as the frozen registry expects (D03_PROVE_CAPABILITIES).
  • Never letting a model decide a route, a verdict or a terminal.
  • Writing nothing outside the output root it was given.
Exclusions a reader will otherwise assume
  • Curriculum content is not in the package. curricula/, policy/, schemas/ and meta_prompt/ are repository-owned data supplied by path at runtime. Packaging confirms this: pyproject.toml includes only curriculum_factory* from src/.
  • No scheduling, queueing, concurrency or multi-run coordination. One flock per output root is the entire concurrency model; a second process gets exit 3 and does nothing.
  • No graceful stop. The mechanism exists but is not wired — see §12.
  • No backup, retention, rotation or cleanup of anything it writes. Verified absent across the checkpoint DB, all ledgers and the artifact store.
  • Not portable off macOS. build_sandboxed_argv raises CapabilityProofFailed when sandbox_mechanism() is "none", which is the case on any non-Darwin host (transport.py:928).

Assumptions it makes about its environment, each enforced rather than documented: an operator-owned ~/.claude.json and ~/.codex/auth.json exist; no *_API_KEY variable is set (their presence fails the capability proof); pandoc/typst and the poppler tools are installed; and the output root is empty or absent for a fresh run. Added in v29: this guide also assumes the reader already has, or can obtain through their organization's normal access process, a checkout of this repository to point --engine-root at — acquiring that access (repository permissions, cloning, onboarding) is out of scope for an architecture and operations guide the same way it would be for any internal tool's runbook, and is not covered here.

Repository inputs, concretely

The figure above names four things the factory reads at --engine-root / --curriculum. Naming them is not enough to work with them, so here is what each one actually contains — the smallest real slice that shows its shape, not an invented example.

curricula/*/manifest — a curriculum's single source of truth, e.g. curricula/arduino_kit/arduino_kit_curriculum.v5.yaml (the one real manifest in the repository: 35 units, L01–L35). --curriculum accepts either this file directly or its parent directory — _resolve_curriculum_root() (run_curriculum.py:191-201) takes the file's parent either way. observed

The manifest filename is load-bearing, and the CLI never takes it by path Whatever --curriculum resolves to, the engine globs the curriculum root for *curriculum.v<N>.yaml, ignores anything under a deprecated path segment, and picks the highest N (nodes/inputs.py:418-437). A manifest named anything else is invisible; two manifests in one directory means the higher version silently wins. There is no flag to name the file. A tie on N is not an error and is not glob-order-dependent: the selection key is (version(path), path.name) — the tuple sort falls through to the full filename, lexicographically, so two files sharing the same highest N (e.g. arduino_kit_curriculum.v5.yaml and zzz_curriculum.v5.yaml) resolve deterministically to whichever name sorts last, every time, on every machine — never to whatever order the filesystem happens to return. observed

Zero matching files is not a clean argument error. When the glob finds nothing, _resolve_active_manifest() calls require(bool(candidates), "invalid_input", "no active curriculum manifest under the curriculum root", ...) (nodes/inputs.py:427-431), and require() raises a plain SystemFailure, not a CliError (nodes/__init__.py:648-652). This call happens outside the graph — before the output-root lock is even acquired (run_curriculum.py:908, ahead of _acquire_lock at line 911) — so it never reaches main()'s except CliError branch, which is what gives every other bad-input case (a bad --engine-root, an invalid retrieval profile, a lock collision) its named ARG-*/CliNotReadyError code and exit 2 or 3. Instead it falls through to the same generic except Exception that catches a genuine crash (run_curriculum.py:975-977): exit 20, and code=type(error).__name__ — literally the string "SystemFailure", not the "invalid_input" cause require() actually classified it as. An operator who names a curriculum root with no manifest in it gets the same exit code and a less specific cause label than a real internal fault, not the argument-error treatment the mistake deserves. observed

Added in v15: this happens on every live call, not once at gate time. Transport.verify_domain() is called from D08_VALIDATE_DOMAIN itself (nodes/domain.py:324), and its body loops run_one(fixture) over every declared reject fixture and every accept fixture (transport.py:2448-2465) in addition to the real domain body — so a single D08 execution launches one subprocess per fixture (up to 64) plus one for the actual validation, every time a unit's domain data is validated — not just once. Neither caches or shares results with the other. This is real, non-cached, per-validation subprocess overhead, not a one-time proof.

What happens if a fixture misbehaves — a must_reject fixture unexpectedly exits 0, or an expected_code never appears in its output: verify_domain() raises VerifierFault immediately (transport.py:2447-2451, "reject fixture ... behaved incorrectly"), before the real domain candidate is ever run. VerifierFault is a TransportError, not an ExpectedFailure/SystemFailure — so deterministic_node's except ExpectedFailure clause does not catch it (nodes/__init__.py:671), and it propagates uncaught out of D08_VALIDATE_DOMAIN's body into the outer node boundary's generic except Exception (graph.py:387), which classifies any exception it catches as cause: "unhandled" regardless of what actually went wrong. Result: SYSTEM_FAILURE, exit 20, node: "D08_VALIDATE_DOMAIN", cause: "unhandled" — the same generic bucket a raw crash would land in, not a verifier-specific cause code, and not a repairable finding. observed

Added in v28 — the REAL (non-fixture) candidate misbehaving is a different, safer path. Once every fixture passes, the actual domain body is validated by candidate = run_one(candidate_path) (transport.py:2477) — the exact same subprocess-and-regex machinery used for fixtures, but with no "expected outcome" to violate. Its result is captured as data, not raised as a fault: "result": "PASS" if candidate["returncode"] == 0 else "FAIL" (transport.py:2478). A domain body that exits nonzero, prints garbage, or matches none of the six rule-code patterns simply produces result: "FAIL" — the ordinary, repairable "unit domain" finding path, not VerifierFault. Only a genuine execution-level failure (the interpreter missing, a sandbox setup error — something that stops run_one() from returning a result dict at all) would propagate uncaught the same way a fixture fault does, landing in the identical SYSTEM_FAILURE/cause: "unhandled"/exit-20 bucket. In short: a newly-authored domain body behaving badly fails cleanly as a repairable finding; only the verifier's own test harness misbehaving, or the verifier failing to run at all, produces the harsher, non-repairable outcome. observed

Within Plan 26 the composition is deliberately one-directional. graph.py owns registration and the common node boundary but no node body; node bodies live in nodes/, model_nodes.py, workbook.py, repair.py and acceptance.py — and PRODUCTION_BINDING_MODULES (graph.py:101) rejects a callable from anywhere else by stable ID, so "the graph compiled" cannot mean "the graph compiled against a stand-in". 3Graph behavior

The graph is framework-defined, not prompt-orchestrated. Nodes and edges are registered into a LangGraph StateGraph at build time and a model never chooses the next step: a node body emits a pending_guard record carrying one declared string value, and a pure guard function maps that value to exactly one destination. A value outside the frozen table raises RoutingViolation rather than resolving to a terminal, because a table/body disagreement is a build defect, not a run outcome (routing.py:1-26). Its operator-visible outcome is the same as GraphRecursionError's (§7's dead-bound box), for the same reason: every router/guard function is registered directly with add_conditional_edges (graph.py:646-648), never wrapped by _boundary (graph.py:369), which only wraps add_node bodies. A RoutingViolation therefore escapes the graph uncaught — no pending_failure, no terminal candidate, no D98 write — and is caught only by main()'s outermost handler (run_curriculum.py:975-978), which prints a SYSTEM_FAILURE-shaped JSON to stdout with cause: "RoutingViolation" and exit 20, but persists no checkpointed terminal record. The same is true of register_workbook_path's build-time dangling-edge check (workbook.py:1289-1296) if it ever fires — that one aborts even before compiled.invoke() runs, at graph-construction time, but is caught by the identical outer handler. observed

Compiling the graph on this machine yields 50 nodes and 158 edges, digest 0e1eca87080aa102…. Two rules run before any node-specific routing rule, in this order: a classified pending_failure routes to the terminal writer (to D91 for a model node, whose failures are the one class a classifier may retry), and only then does an observed interrupt route to the interrupt gate. Failure deliberately outranks interruption so that an episode which broke and was asked to stop is not recorded as merely INTERRUPTED.

Concurrency: one job in flight, N activations of it

Correcting a contradiction v4 carried

v4's §8 said dispatch is bounded "to one in-flight model activation by the graph's own shape", while §5 described union_disjoint reducers existing so two workers can return order-independently. The reducer description was right and the concurrency claim was wrong.

Send fan-out is real and is the system's only parallel dispatch. Four nodes fan out (routing.py:277-284): D06 and D06B stage M01 discover/interpret, D12 stages M04, and D10 fans out to the deterministic worker D11. D90 loops over every staged member, reserves one attempt each, and returns one Send per member — so N activations of one job run in the same superstep (LangGraph's term for one Pregel round: every node the prior round activated runs once, concurrently, before the graph advances). A runtime test asserts exactly this shape: "Two Send maps of two members each: four M01 activations, no more" (tests/runtime/test_plan26_unit_graph.py:1490-1495). The concurrency reaches the OS: the transport's own comment records that a concurrent fan-out of sandboxed launches reproducibly produced EPERM for a fraction of them (transport.py:543-545) — but this is a fixed, historical defect (N70_LIVE_UNIT_PROOF, the remediation-plan node under which this was verified live), not a live risk. The sandbox profile now grants the installed claude CLI's own /tmp/claude-<uid> runtime-scratch path explicitly; the regression test that pins this fires nine concurrent sandboxed launches and asserts 0/9 failures, where the same fixture failed 9/9 before the fix (tests/runtime/test_plan26_transport.py:574-596). It remains here as proof that concurrency really reaches the OS, not as an open operational hazard — an operator on the current tree should not expect to see it.

Is the interrupt race real, or does it contradict "nothing can ever trigger D96" (§12)? Both claims are true and do not conflict. The "real race" is exercised by test_an_interrupt_inside_a_send_map_is_bounded_across_repeated_episodes (tests/runtime/test_plan26_unit_graph.py:1945-1962), which drives the interrupt via _run_episode(..., interrupt_after=...) — a test-harness injection that bypasses InterruptToken entirely. It proves the graph's own routing is race-safe if an interrupt were ever raised: across twelve episodes and every interleaving, exactly one terminal is written and no attempt reservation ever follows the gate. It does not mean an interrupt can fire in a live run — nothing in src/ ever calls InterruptToken.set(), so D96 is proven safe but currently unreachable in production, exactly as §12 says. observed

The accurate statement: one model job is dispatched per superstep (one dispatch per staged packet), and N activations of that job run concurrently. The six union_disjoint channels are load-bearing for exactly those workers, not defensive. What is bounded to one: one OS process per output root (flock), and one attempt per counter key, committed before dispatch. No concurrency limiter is configured — invoke_config passes only thread_id and checkpoint_ns, no max_concurrency, and policy/limits.v1.yaml's per_run.max_concurrency: 1 is inert (nothing loads that file).

One fan-out member fails and its siblings succeed: what the system does

Added in v25. The section above establishes that N activations of one job run concurrently. The question it left unanswered is the one an architect actually needs: a superstep dispatches four M01 activations, one of them fails, three return good candidates — what is the resulting state? The short answer is that there is no partial join anywhere in this system: a fan-out either completes its whole frozen denominator or it does not complete at all. Five separate mechanisms enforce that, and they are worth reading together because no single one of them is sufficient.

  1. The denominator is frozen and persisted before the first Send is issued. The dispatching node stages the exact worker projections in pending_packet, and the fan-out guard translates that staged material one-for-one — it never materializes a projection at routing time, because "a projection invented at routing time would be one no denominator committed to" (routing.py:422-449, _staged_fanout). A fan-out guard entered with no staged packet raises RoutingViolation rather than improvising a smaller map (routing.py:434-438; pinned by test_a_fanout_with_no_staged_packet_refuses_to_improvise_one, tests/runtime/test_plan26_unit_graph.py:1097). So the denominator cannot shrink to match whatever survived.
  2. The failing member never reaches the barrier. Routing resolves a failure destination before it reads the guard value at all, and for a model node that destination is D91_CLASSIFY_MODEL_FAILURE, not the join (routing.py:320-324,351-356, _failure_destination with model_node=True). The three successful siblings' results, meanwhile, are already committed to state by their own reducers. The join therefore sees three of four keys present and one absent — it does not see a failure record it might be tempted to treat as a result.
  3. The barrier refuses the partial set explicitly. D12_VISUAL_BARRIER_AND_JOIN compares the accumulated set against the complete denominator and calls require(actual == complete, "join", "the accumulated visual set does not equal the complete denominator", …), reporting the exact missing and extra key sets (nodes/visuals.py:429-437). It applies the same equality test one phase earlier to the deterministic subset before any model brief is dispatched (nodes/visuals.py:347-355). Four mutations of that denominator are exercised by test_the_visual_join_refuses_a_denominator_that_is_not_exact — missing, extra, stale_parent, cross_unit (tests/runtime/test_plan26_unit_graph.py:1160) — and eight more by test_exact_fanout_denominators, which runs those same four mutations against both the visual and the source denominator (tests/runtime/test_plan26_adversarial.py:1174). All twelve re-run for this version and passing.
  4. A retry re-dispatches only the failed member, never the whole map. This is the part most likely to surprise: when D91 authorizes a retry it names one counter key, and D90_RESERVE_MODEL_ATTEMPT skips every staged member whose key does not match (model_nodes.py:1000-1001, if retry_key is not None and key != retry_key: continue). Its own contract states the consequence plainly: "only that member is re-reserved and restaged: the other members' results are already committed and are not re-dispatched" (model_nodes.py:971-984). So the three good candidates are not regenerated, are not billed for a second time, and are not at risk of being replaced by a different answer — which matters, because the union_disjoint reducer that receives fan-out results fails rather than overwrites if a second write supplies a differing value for a key that already holds one (reducers.py:253-271, UnionConflict). Re-running a whole map after a single-member failure would turn every non-deterministic sibling answer into a hard state conflict; not re-running it is what makes the retry safe. If the classified retry names a key that matches no staged member, D90 raises rather than dispatching nothing (model_nodes.py:1018-1021).
  5. An exhausted member takes down the whole superstep rather than dispatching a partial map. If any one member has reached the frozen attempt limit, D90 returns an exhausted guard for the entire dispatch instead of sending the members that still had budget (model_nodes.py:1023-1034). The stated reason is that "the bound can never be crossed by a sibling" (model_nodes.py:982-983) — a partial map would let a healthy member consume an attempt in a superstep the run is already going to abandon.
The crash case, which is genuinely different observed

Points 2–5 describe an in-episode failure. If the process dies mid-fan-out instead, the surviving siblings' writes are not lost — LangGraph records them as pending writes on the checkpoint — and the crashed member stays on the frontier.

It is worth being precise about who provides that selective replay, because it is not this system. Re-invoking the same thread replays a committed sibling's write instead of re-running the sibling's node body: test_completed_sibling_work_replays_its_write_instead_of_re_executing (tests/runtime/test_plan26_persistence.py:452-485) raises inside one member, calls graph.invoke(None, config=config) against the same config, and asserts the surviving node executed exactly once across the failure and the retry. That is LangGraph's own pending-write behavior, exercised in-process on one thread.

--resume does not take that path. Every episode is invoked on a fresh thread — episode_thread_id() returns "{run_id}:episode:{ordinal:06d}" for a strictly increasing ordinal (persistence.py:253-260, persistence.py:860-900) — and the prior episode is reachable only through ReadOnlyCheckpointView, which exposes get_state, get_state_history, get_tuple and list and deliberately offers "no attribute through which a prior thread could be continued", making "never resume the old thread" structural (persistence.py:635-644). So a resume never re-enters the crashed superstep and never replays the sibling's pending write.

What would happen next, if a clean resume were ever reached: D04 would hand D92 a model-free frontier computed by compute_resume_frontier from the prior episode's readout, with any model destination rewritten to D91 because "an aborted model receipt must be classified before D90 can authorize another transmission" (persistence.py:1074-1100). This machinery is real and tested (the worked example below is pinned by a real test) — but per §5's "Pausing" correction and §10's crash-fate correction, it is never reached in production. D04 only runs this recovery logic for bootstrap_kind == "resume", which prepare_episode_invocation only assigns when ledger.open_lease() returns None — no open lease (persistence.py:1346,1391). Because close_episode() has no production caller, every episode's lease stays open forever, so every real --resume after the first episode finds an open lease and is classified recover_orphan instead — and D00_BOOTSTRAP_EPISODE's own guard table routes recover_orphan straight to D96_GRACEFUL_INTERRUPT_GATE (routing.py:117-120), bypassing D04, this frontier computation, and D92 entirely. The episode ends INTERRUPTED, exit 10, having done no product work — the same outcome as every other crash or pause. What follows below (the join/denominator mechanics, the worked example) is what the checkpoint structurally holds and what the code would do with it; it is not what a live --resume currently does with it. The real remedy for a crashed fan-out, like every other crash, is a fresh output root.

The trap this creates is the one classify_join_members exists to close: those surviving pending writes are present in the checkpoint, so a naive resume could read three-of-four results and conclude the join was satisfied. It cannot, because the denominator is compared against completed members only — "pending writes from a surviving sibling never shrink the denominator, so a fan-out with one crashed member cannot be joined as a partial result" (persistence.py:1052-1071). The function returns {"expected": […], "completed": […], "pending": […], "satisfied": …} and sets satisfied only when pending is empty and expected is non-empty — an empty denominator is explicitly not a satisfied join, which stops a lost denominator from reading as a finished one. A completed member outside the expected set raises PersistenceError rather than being tolerated.

Visuals: where M04 sits, and what never happens to its output

M04 is not on the M03 → D09 line that figure 2 draws; that is why the figure skips it. The real shape is D09 → D10_COMPILE_VISUAL_BRIEFS → D12_VISUAL_BARRIER_AND_JOIN, and M04 hangs off the barrier. D10 splits the visual denominator in two (nodes/visuals.py:66-74): a brief whose kind is authoritative — build_map, schematic, netlist, power_path, connectivity, safety_inset, circuit, pinout, pin_map, breadboard, wiring, electrical, terminal_block — goes to the deterministic worker D11; everything else is a model brief. D12 then stages the M04 fan-out for the model subset, or admits the visuals head directly if there is none. M04's single outgoing edge is a plain unconditional M04 → D12 (unit_graph.py:59-62), and its only predecessor is D90. A unit declaring no non-authoritative visuals never touches M04 at all. observed

What actually happens when M04 fails. M04 is the only primary model node with no edge to D91_CLASSIFY_MODEL_FAILURE — so, unlike M01/M02/M03/M05, a failed M04 activation is never transport-retried and never gets the 2-attempt D90 budget. It also never crashes the run: m04_create_unit_visuals (model_nodes.py:1555-1591) never raises on a bad candidate — a transport-level failure returns a (None, failure_update) pair, and every content violation (wrong brief, undeclared artifact, an asserted-authoritative visual — which a model may never claim, per spec section 13 — see the note below on what "spec section" cites throughout this guide) returns through _reject(...). Neither path writes a visual_results entry for that key, so the candidate is simply absent when D12 joins the barrier. D12 then raises a normal unit visual finding — "visual candidate is missing hash, format, or declared provenance" (nodes/visuals.py:545-557) — which routes through the ordinary visuals_repairable path to D17, the same repair pipeline any other content defect uses. Because M04 may never produce an authoritative visual (that would violate spec section 13), every M04-sourced finding is by construction the non-authoritative case, which §3's repair discussion above establishes can actually be repaired (routes to M06, not into the broken deterministic branch). Net effect: an M04 failure costs the 2-attempt model budget it never had, but is not a dead end — it becomes one ordinary repairable finding, capped by the same 3-per-chain attempt bound as any other unit visual defect. observed

Repair: what is repairable, and what the deterministic branch actually does

The fork between the repair loop and a terminal is at D17_CLASSIFY_UNIT_FINDINGS, and there is no severity ladder for deterministic checks and no policy file involved. Repairability is structural, in four layers: observed

  1. Producer level. A deterministic gate that can name an owner and a boundary pointer emits its finding under a …_repairable guard (domain_repairable, layout_repairable, …). Anything raised instead as a SystemFailure — cause integrity, schema_contract, capability, join, tool, persistence (a sample, not the full list — added in v14, the canonical closed set: SYSTEM_CAUSES at nodes/__init__.py:125-137 names exactly twelve — unhandled, unexpected, invalid_input, identity, integrity, schema_contract, capability, authorization, tool, join, persistence, log; the same module also defines PAUSE_CAUSES (one member, required_external_fact_unavailable) and EXHAUSTION_CAUSES (attempt_bound, fingerprint_bound), with CAUSES_BY_CLASS mapping each of the three failure_class values to its own closed set. Two of the twelve — unhandled and unexpected — read as synonyms but are not: unhandled is the one actually raised, and only from one place — the node-boundary wrapper's catch-all (graph.py:387-412) converts any unclassified Python exception escaping a node body into {"class": "system", "cause": "unhandled", "message": f"{type(error).__name__}: {error}"}, i.e. it is the signature of a bug or crash inside a node, not a designed failure path. unexpected, by contrast, is declared in the closed set but a repository-wide search finds no call site that ever raises it — it exists in the enum and nowhere else, a reserved value that has not (yet) been given a meaning. The same trace, run against the remaining five members named only as a sample above, finds four real and one dead: schema_contract is raised at more than a dozen sites across domain.py, inputs.py, content.py, repair.py and workbook.py for unparseable or contract-violating JSON/YAML; authorization is raised by inputs.py's D30/re-entry checks (for example inputs.py:1281-1284, "no external-data authorization record covers this run") whenever the authorization envelope is missing, stale against the frozen digest, or scoped to a different output root; join is raised across repair.py, sources.py, visuals.py and nodes/__init__.py:993 whenever a Send fan-in finds no staged worker packet for a destination it expected one from; persistence is raised from exactly one site (terminal.py:481-483), guarding N32's single terminal-writing implementation against being invoked twice for the same episode. log, like unexpected, is declared but never constructed anywhere in the repository — a second reserved value with no meaning yet. observed) — is unrepairable by construction and routes straight to D98. Correction: the closed set is not actually closed. The node-boundary wrapper only catches exceptions raised inside a node body. compiled.invoke(...) itself (run_curriculum.py:827) is called inside a bare try/finally that only tears down the transport guard — it does not catch anything — so an exception from LangGraph's own machinery between node bodies (most concretely, the checkpointer's SQLite write between supersteps, e.g. a full disk raising sqlite3.OperationalError: database or disk is full) propagates past _boundary entirely and is caught only by main()'s outermost except Exception (run_curriculum.py:975-978), which sets cause=type(error).__name__ — the raw exception class name, e.g. "OperationalError" or "OSError", not one of the twelve SYSTEM_CAUSES values and not "unhandled". An operator who sees a cause outside the twelve is therefore not necessarily looking at something the code cannot raise — they may be looking at exactly this: disk exhaustion, or any other fault, that occurred in the gap between node bodies rather than inside one. observed
  2. Review level. Only severity == "blocking" from M05 counts. major, minor and observation are discarded entirely (acceptance.py:209-218).
  3. Normalisation at D17. A finding is repairable only if it maps onto the five-owner vocabulary — source interpretation, curriculum domain, unit content, unit visual, unit layout (repair.py:75-81) — and carries a boundary pointer and names a parent hash that is still the current admitted head. A model's own category string is never trusted as an owner: it is mapped through a frozen keyword table, and an unmapped category is a system fault, not a finding.

New in v27 — what makes a finding "blocking" is decided by the model, not by code

The "Review level" step above is the one place in this system where a gate turns on a value no code constrains. The severity field is declared in code — a four-value string enum, ["blocking", "major", "minor", "observation"], required on every finding, in both review schemas (schemas/M05_review_actual_unit.schema.json:12,15 and schemas/M07_review_actual_workbook.schema.json:12,15). Which of the four a given defect gets is not. A repo-wide search for severity criteria found none: the M05 and M07 prompts mention severity exactly once each, only to say every finding needs one (prompts/M05_review_actual_unit.prompt.md:20, prompts/M07_review_actual_workbook.prompt.md:20); the staged review rubric (meta_prompt/assets/pedagogy.v1.md, hash-bound into the reviewer's input at nodes/review.py:125-135,210 and workbook.py:600-602,623,664) contains no severity language at all; and severity appears in only two Python files in the whole package — the two acceptance gates that read it (acceptance.py:211,217 and workbook.py:770,776), both of which do a bare string comparison against "blocking" and neither of which validates, calibrates or second-guesses the choice.

Why this is worth naming. The immediately adjacent field is handled the opposite way: a reviewer's free-text category is explicitly distrusted and mapped through a frozen keyword table to the five-owner vocabulary, with an unmapped category raised as a system fault rather than guessed (repair.py:160-202, whose own comment says the model's category vocabulary "is never trusted directly"). Severity gets no equivalent. So the guide's standing claim that routing and verdict authority are code-owned holds in a precise sense and not a loose one: the reviewer still cannot emit a verdict, score or acceptance field (its schema has none, and its prompt says so), and the controller still decides what to do with the findings. But the predicate that gate turns on — review_ok = not blocking (acceptance.py:235, workbook.py:789) — is a model's unconstrained word. A reviewer that labels a real defect major makes it vanish from acceptance entirely; one that labels a cosmetic nit blocking forces a repair cycle. Neither is detectable by any check in this repository.

The release audit, and what COMPLETE has to survive

The "release audit" v4 mentioned without defining is the record produced by D32_RECOMPUTE_FINAL_RELEASE into the final_release_audits channel. It re-derives from scratch rather than reusing D28's verdict, and all five categories must pass (workbook.py:696-821): observed

  1. coverage — declared coverage equals the frozen ordered_unit_ids and every receipt hash is current;
  2. unit_bytes — each recorded unit PDF hash equals the accepted receipt's denominator.pages.pdf_sha256;
  3. pages — inventory passes, the inspection count equals the page count, and every inspection passes;
  4. review — an M07 candidate exists for the current workbook PDF hash with zero blocking findings;
  5. repair — no open workbook repair requests remain.

On pass it emits a COMPLETE candidate carrying the audit key, workbook hash, coverage, unit receipt hashes, log high-water mark and checkpoint id. Any rejection is written as SYSTEM_FAILURE, never as COMPLETE.

Resume: D04 and D92 are two nodes, not one delegating to the other

They are separate graph nodes joined by one conditional edge, and they do different jobs. D04_INITIALIZE_OR_RESUME mints the episode id and checkpoint thread id and, on a resume, imports the prior artifact_heads, attempt_counters, cursor and unit_status verbatim after checking the recovery envelope's run id and frozen digest. It then emits either fresh_initialized → D05 or resume_imported → D92_REENTER_VALIDATED_FRONTIER. D92 is D04's only incoming edge. Its job is different: it reads the stored resume frontier (written earlier by D96 or D30) and validates it — non-empty, names a destination, the destination is not a model node, every unaccounted model activation is surfaced, and every frontier parent hash is still the current head — then emits a dynamic destination drawn from the 12 permitted deterministic re-entry points, or routes an incomplete activation to D91. D04 writes resume_from; D92 reads resume_frontier. Neither calls the other. observed

The full RESUME_REENTRY_DESTINATIONS tuple (unit_graph.py:138-151), in its declared order: D05_SELECT_NEXT_UNIT, D06_COMPILE_SOURCE_REQUESTS, D06B_RETRIEVE_SOURCE_CANDIDATES, D07_CORRELATE_AND_ADMIT_SOURCES, D08_VALIDATE_DOMAIN, D09_VALIDATE_CONTENT, D10_COMPILE_VISUAL_BRIEFS, D12_VISUAL_BARRIER_AND_JOIN, D13_RENDER_UNIT, D14_INVENTORY_AND_INSPECT_UNIT_PAGES, D15_FREEZE_UNIT_REVIEW_PACKET, and D30_CLASSIFY_PREREQUISITE. What survives a crash

Four independent layers persist, and they do not all agree on how carefully:

  • The checkpoint DB — .langgraph/checkpoints.sqlite3, LangGraph's SqliteSaver with WAL + synchronous=FULL + busy_timeout=30000, re-verified after setup() because setup may relax them. Thread id is <run_id>:episode:<ordinal:06d>; checkpoint_ns is always the empty string. observed
  • Hash-chained JSONL ledgers under .langgraph/ — each record carries prev_hash and a contiguous ordinal, so a deleted or reordered line is detectable rather than merely lost.
  • The content-addressed artifact store — blobs by SHA-256, version records, and one mutable file per stream: the head pointer. That head pointer is the only thing in the entire store that is ever overwritten; anything under an accepted/ path is refused even with overwrite=True and is chmod'd 0444/0555.
  • Egress receipts — .evidence/egress_receipts.jsonl, the only evidence log with a production writer.
Two durability guarantees that are declared but not wired

flush_checkpoint_durability() (persistence.py:555) commits, forces a full WAL checkpoint and fsyncs the DB, the WAL and the directory. 8Deployment

There is no deployment

The pattern deploy/** matched nothing in the source register — recorded as an evidence gap rather than silently dropped. There is no Dockerfile, no infrastructure-as-code, no service manifest, no hosting configuration anywhere in the repository. This section is therefore about the only environment that exists: an operator's laptop. observed

Runtime topology is a single Python 3.13 process (pinned >=3.13,<3.14) that spawns one short-lived sandboxed child per model activation, per render and per inspection. There are no workers, no queues, no network services, and no horizontal scaling story. Concurrency is bounded to one process per output root by flock — and that is the only bound. Correcting v1–v4: model dispatch is not limited to one in-flight activation. One job is dispatched per superstep, but D90 issues one Send per staged member, so N activations of that job — and therefore N sandboxed child processes — run at once, with no max_concurrency configured anywhere (§3). Sizing a machine for this run means sizing it for the widest fan-out the manifest produces, not for one subprocess.

What "widest fan-out" actually is, computed from the real manifest observed for M01, inferred for M04:

  • M01 (source discovery+interpret) is statically computable from the manifest — compile_unit_source_requests derives one request per entry of four fact-bearing keys (required_explanation, core_activity, safety_focus, applications; a scalar key like core_activity counts as 1). Running it against arduino_kit_curriculum.v5.yaml: the widest unit is L21 with 10 requests (the shift-register lab's longer required_explanation); the narrowest is L02/L03 with 6. Each request spawns one M01 discover activation and, if it resolves, one M01 interpret activation — so the real peak for M01 alone is on the order of 10 concurrent sandboxed claude children for this manifest, not the 4-item visual_roles count a reader might reach for first.
  • M04 (visual briefs) is not statically computable from the manifest. Its fan-out is the length of the visuals list M03's generated content declares (nodes/visuals.py:108-110, reading body.get("visuals", []) from the admitted content artifact) — a runtime, model-authored value, not a manifest field. The manifest's own visual_roles (4 for L01, the widest in this manifest) states what content generation is expected to cover, but nothing in the code enforces that the generated visuals list has exactly that length; §3's "even the deterministic SVGs never reach the PDF" gap is a symptom of the same loose coupling. Treat 4–10 as a reasonable planning range for this manifest, not a guarantee.

What providers and executables really constrain

providers maps a provider name to the data classes it may receive. Only three provider names exist (anthropic, openai, primary_source_hosts) and each has a fixed set of permitted classes; an unknown provider or an undeclared class is rejected when the record is constructed. At run time, authorize_transmission() is called before the child process exists and refuses if the provider is absent from the map or any requested data class is not in its list — alongside expiry, run scope, curriculum digest and output-root checks. An empty providers map authorizes nothing, which is why the fixture in §12 works for CLI-shape tests and would fail the moment a model job dispatched.

What happens if the authorization expires mid-run, between activations? Because the expiry check runs before every child process, not once at bootstrap, a long --all run or a wide fan-out can outlive a short authorization window (the worked example above is 24 hours). AuthorizationDenied (egress.py:170) is an EgressError, not a tp.TransportError — and _dispatch's only exception handler catches tp.TransportError specifically (model_nodes.py:1249), so an expiry raised inside execute() is not caught there, is not routed through D91, and does not become a structured, resumable refusal like every other authorization check in this section. It propagates uncaught to run_curriculum.py's top-level handler ("never let an unhandled fault look like anything but a failure", line 975), which converts any uncaught exception into non-resumable SYSTEM_FAILURE, exit 20 — the same terminal class as a crash, with an egress_denied receipt already appended to the evidence log (egress.py:751-761) as the only trace of what actually happened. An operator authorizing a run that might outlast the window should set expires_at_utc comfortably past the run's expected duration; there is no graceful mid-run re-authorization path. Added in v29: this is not a mid-run-specific mechanism — the same AuthorizationDenied/uncaught/exit-20 path fires identically on the very first dispatch of a run, for example a providers map missing the entry a job actually needs. There is no lighter-weight or resumable case for "denied before any product work happened"; every authorization denial, whenever it occurs, is the same non-resumable SYSTEM_FAILURE requiring a fresh output root.

executables is an optional list of {name, path}. D01 SHA-256s each path that exists and stores it as frozen_executable_identities; D03 re-probes the installed binary and fails the run with cause identity if either the path or the hash differs. It pins the model CLIs by content — so a claude or codex upgrade mid-run is refused rather than silently accepted. An empty list disables the pin entirely (no entry, no possible mismatch). observed

Verified gaps
  • The sandbox constrains the model child by port, not by host — and nothing records which host it actually reached. Its network rule allows outbound TCP to any host on 443 and 80 and UDP on 53. The code says so itself and records it as a non-required capability facet named subprocess_network_scope (transport.py:1058-1066). A compromised or misbehaving CLI child can reach any host on those ports; the elaborate parent-side allowlist does not apply to it. render_sandbox_profile() (transport.py:677-720) emits a plain macOS Seatbelt allow/deny rule — (allow network-outbound (remote tcp "*:443") ...) — with no logging directive, and macOS sandbox-exec has no built-in connection log this system reads from. There is no proxy in front of the child either (confirmed by grep: no HTTP_PROXY/http_proxy setting anywhere in the worker environment). So the honest answer is: no record — receipt, log, or connection metadata — exists anywhere for what a sandboxed model child actually connected to. .evidence/egress_receipts.jsonl only covers the parent process's own EgressGuard-patched sockets (source-fetch, never the model CLI children). If a compromised child exfiltrated to a wrong host on 443, this system would have no trace of it. observed
  • M01's WebSearch is outside every control described above. It executes inside the Claude child, so neither EgressGuard nor RetrievalPolicy sees it. Only the locators it returns are re-checked. Granting it also forces that activation to --permission-mode bypassPermissions.

D06B fetches a candidate through SourceRetriever, persists the bytes (nodes/sources.py:480-484), projects them to text with extract_verified_staged_text() (transport.py:1652-1684) and stages that file for an M01 INTERPRET activation and nothing else (nodes/sources.py:486-487,577-581). None of that is an injection control. Visible page prose — exactly where an injected instruction would sit — passes through verbatim; there is no filter, escaping, delimiter or instruction-defense anywhere (a repo-wide grep for injection/untrusted/adversarial language returns nothing in src/, meta_prompt/ or policy/), and the M01 prompt never tells the worker that staged text is data rather than instruction. 11Observability

The design intent is unusually strong: six hash-chained evidence logs (events, activations, routes, executions, checkpoints, index), each append-only, flock-protected, fsync'd, schema-validated, and able to distinguish a tampered record from a deleted one from a torn append.

Blind spots — read this before you rely on anything above
  • EvidenceStore.append() is never called from src/. The store is constructed at graph.py:227 and injected into every node's RuntimeContext as evidence_service, and no node body uses it. Five of the six logs have no writer anywhere; the sixth has one writer called only from tests. evidence/*.jsonl is never created at runtime. observed
  • Consequently evidence_index_entries is always empty, so D98's log_high_water_mark ceiling is checked against nothing, and write_audit_report() never runs.
  • No logging framework at all. grep for import logging, prometheus, opentelemetry, statsd, datadog, sentry across src/ returns zero matches. No levels, no handlers, no diagnostic log file. Console output is 15 print() sites.
  • No metrics, traces, spans, dashboards, alerts, health endpoint or SLO. Nothing is exported anywhere.
  • No timing anywhere. No node duration, no model-call latency. Timestamps exist only as time.time_ns() inside ledger payloads.
  • The legacy ExecutionLogger — the one thing in the repo shaped like an operational log — carries no run id, no episode id and no time of day, only a date. It is also unreachable from langgraph_factory.
  • Episode leases are opened and never closed. close_episode() has no caller in src/, so every run leaves an open lease and every --resume is forced down the orphan-recovery branch, which is read-only and terminal-only — it writes INTERRUPTED (exit 10) and stops, never retrying the paused work. What an operator actually has. Two things: the terminal JSON printed on stdout (kind, exit code, resumability, heads, validation results) and .evidence/egress_receipts.jsonl, which records every allowed and denied network attempt with its reason. Reading the checkpoint DB. <output_root>/.langgraph/checkpoints.sqlite3 is a stock LangGraph SqliteSaver database — two tables, checkpoints(thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint, metadata) and writes(thread_id, checkpoint_ns, checkpoint_id, task_id, idx, channel, type, value) (schema from the installed langgraph.checkpoint.sqlite package, not code this repo owns). Which episode is furthest along, in plain SQL — checkpoint_id is a lexicographically sortable ID, so MAX() per thread finds the latest step:

sqlite3 <output_root>/.langgraph/checkpoints.sqlite3 \
  "SELECT thread_id, MAX(checkpoint_id) FROM checkpoints GROUP BY thread_id;"

thread_id is <run_id>:episode:<ordinal> (or <run_id>:recover:<ordinal> for an orphan-recovery episode) — see Terms and naming. The checkpoint and metadata columns are opaque serialized blobs; decoding the actual state (which node ran, the channel values D02 through D98 wrote) needs the checkpointer's own API, not raw SQL:

python3 -c "
from langgraph.checkpoint.sqlite import SqliteSaver
import sqlite3
conn = sqlite3.connect('<output_root>/.langgraph/checkpoints.sqlite3')
saver = SqliteSaver(conn)
tup = saver.get_tuple({'configurable': {'thread_id': '<run_id>:episode:000001'}})
print(sorted(tup.checkpoint['channel_values'].keys()))   # which state channels are populated

"

    Plan capacity around this: the 9 invocations do not share work. Each sink's output root is a fresh, independent episode with an empty artifact-heads channel — nothing is carried over from another sink's output root, even when both closures include the same unit id. A unit that is a prerequisite of two different sinks (for example, an early unit shared by both L26's and L35's closures) gets authored, admitted and accepted independently, from scratch, with its own full model cost inside each sink's output root — there is no cross-root cache or artifact-sharing mechanism anywhere in the engine. Content generation runs through the claude/codex subscription CLIs as subprocesses (transport.py); no seed, temperature or other sampling control is set or exposed anywhere in the transport layer this guide inspected. A unit shared by two sinks is therefore authored twice by a live model with no stated determinism guarantee between the runs — the two accepted copies can differ in wording, structure, or even which admissible content the model chose to include, while both independently pass every deterministic gate. The engine gives no reconciliation step and no "pick the canonical copy" rule; manually concatenating PDFs across sink output roots means an operator must decide, unassisted, which of two valid but possibly-divergent copies of a shared unit ships. inferred: no test or trace in this repository exercises building the same unit twice to compare outputs; this is a structural consequence of the sink strategy plus the absence of any sampling control, not an observed divergence

  • Added in v28 — if you deliberately need to abort a run (for example, M04's unbounded visual fan-out has spawned far more sandboxed children than expected and is burning subscription quota), SIGKILL is the only real option, and it is honest to say what it does and does not do. kill -9 <pid> on the top-level curriculum-factory-run-curriculum process ends that process immediately — but every model/render/inspection child was spawned with start_new_session=True (transport.py:1778), which puts each child in its own new process group, detached from the parent's. SIGKILL on the parent does not propagate to any child already running; each survives exactly as if the parent had crashed on its own (§10's orphaned-child finding applies identically here — no watchdog, no reaping, runs until it exits on its own). Triage

  1. Read the terminal JSON on stdout first. It carries the kind, the failing node, the safe artifact heads and the validation rejections. It is more informative than anything on disk.
  2. If the kind is SYSTEM_FAILURE with node: "D98_WRITE_TERMINAL" and cause: "integrity", another node proposed a terminal that D98's independent re-derivation rejected; the rejected_candidate_kind and the rejection list name what did not hold. Escalate — this is a correctness fault, not an environment fault.
  3. Check .evidence/egress_receipts.jsonl for denials. A host_not_pinned or unauthorized_socket_no_active_retrieval entry usually means the retrieval profile does not list a host the run needed.
  4. For a crash with no terminal (killed process, power loss), the run left an open lease. Start a fresh output root instead — see §5's traced walkthrough.
Recovery has no backup and no rollback There is no restore procedure, because there is no backup: nothing copies the output root, and the only rollback primitive in the system is git, which does not cover generated output. Artifact history is preserved by construction (every version is retained; only the head pointer moves), so a bad head can in principle be reasoned about from the version records — but no code exists to move a head backwards. Treat the output root as the single copy of the run and back it up yourself before intervening. observed

Is a plain file copy of a live output root safe? Not while a process is writing to it — check first. The checkpoint DB runs in WAL mode (persistence.py:184-185,510), which means its on-disk state spans three files (checkpoints.sqlite3, -wal, -shm); a plain cp of just the main file while a writer is active can miss committed data still sitting in the WAL, and copying the three files non-atomically risks a torn, inconsistent set. There is no online-backup API call (sqlite3's own .backup/VACUUM INTO) anywhere in this codebase to work around that. The one liveness check the system does give you is the execution lock itself: flock on .langgraph/execution.lock is held for the process's entire lifetime (persistence.py:394-401, "one writer per root"), so `flock -n .langgraph/execution.lock -c true` (exit 0 = lock free = no writer running, safe to copy the whole directory as a normal file tree; nonzero = a process is still writing, do not copy yet) is a real, mechanical safety check before backing anything up — not one the guide is inventing, since it is the same primitive ExecutionLock.acquire() itself uses. inferred: the lock-check command itself was not run against a live process during this guide's inspection; the WAL/torn-copy risk and the lock's lifetime are each directly evidenced in code
