Curriculum Factory repository refactor

Align the product identity, repository name, Python package layout, directory purposes, generated-output lifecycle, documentation, and automated verification.

GoalsIdentitySourceOutputsDirectoriesDeliverablesAcceptance

1. Goals

  • Use Curriculum Factory consistently as the human-facing product name.
  • Rename the repository and local checkout to a consistent repository slug.
  • Move production Python code into a conventional installable src layout.
  • Replace the broad current source organization with responsibility-based package boundaries.
  • Classify every top-level directory by owner, reader, and lifecycle.
  • Keep generated run output separate from tracked fixtures and retained evidence.
  • Remove obsolete directories and run artifacts only after their consumers and retention needs are resolved.
  • Make installation, imports, tests, commands, and documentation work from a fresh clone.

3. Python source layout

Target source rootsrc/ contains installable source. curriculum_factory/ is the Python namespace. Do not place application modules directly under src/.
src/
└── curriculum_factory/
    ├── __init__.py
    ├── cli.py
    ├── orchestration/
    ├── routing/
    ├── retrieval/
    ├── rendering/
    ├── validation/
    └── persistence/

The current runtime/ package combines these responsibilities. Move it with behavioral equivalence first. Update imports, entry points, module commands, mocks, fixtures, documentation, and every repository-root calculation based on __file__. Split modules by responsibility after the package move is verified.

Add the minimum packaging configuration needed to install the distribution and run tests against the installed package. Tests must not pass merely because the repository root was inserted into sys.path.

Keep policy/, schemas/, curricula/, docs/, and outputs/ outside src/. Add another top-level Python package only for an independently reusable or deployable component.

4. Output lifecycle

Keep outputs/ as the ignored runtime write boundary.It should be empty between runs. Tests, fixtures, research evidence, and audit evidence must not depend on durable files stored there.

The current code validates output paths beneath ENGINE/outputs/. Controllers and graph code use that validation, tests create run directories there, policy and meta-prompt contracts name outputs/<run>/, and .gitignore excludes generated children. Preserve this containment behavior.

5. Repository inventory and directory decisions

Record the following before moving files:

  • current and target value for each identity in §2;
  • every top-level directory, its owner or reader, tracked and ignored state, lifecycle, and disposition;
  • all imports, module commands, and entry points rooted at runtime;
  • all __file__-based root traversal and absolute checkout paths;
  • all live references to old product names, repository names, package names, source paths, and output runs;
  • existing and missing packaging, installation, build, and test configuration;
  • producers and consumers of questionable directories, including PSIM/ and specs/; and
  • identifiers that must remain unchanged for compatibility or historical accuracy.

Classify each directory as production source, repository contract, domain input, generated runtime data, cache or scratch data, test fixture, retained evidence, active documentation, or deprecated history. Do not rename or delete a directory while its classification is unresolved.

6. Deliverables

  1. Migration inventory: current state, consumers, lifecycle classifications, target paths, and exceptions.
  2. Execution plan: ordered phases, dependencies, rollback points, authorization boundaries, and validation after each phase.
  3. Execution prompt: exact scope, phase order, permitted mutations, stop conditions, test commands, and completion evidence.
  4. Executable tests: automated checks covering the acceptance criteria in §7.
  5. Exceptions inventory: retained legacy identifiers or paths, rationale, consumer, and removal condition where applicable.
  6. Migration report: final identity map, directory dispositions, changes, test results, removed outputs, retained evidence, exceptions, and pending external renames.

7. Acceptance criteria and tests

  1. Installed imports: production code imports as curriculum_factory from the installed src-layout package without repository-root or ad hoc sys.path assistance.
  2. CLI behavior: documented entry points and module commands resolve and preserve their expected arguments and exit behavior.
  3. Root resolution: production code finds policies, schemas, curricula, and the output boundary correctly from its deeper source location.
  4. Output containment: a run directory below outputs/ is accepted; a path outside it is rejected before any artifact is written.
  5. Fixture independence: tests, skills, research, issues, and audits do not require durable evidence from ignored outputs/.
  6. Empty-output resilience: the full suite passes with no generated children under outputs/.
  7. Reference integrity: live code, automation, and documentation contain no stale identity, checkout, import, or source-path references except recorded exceptions.
  8. Documentation integrity: documented paths resolve and documented commands execute in their stated environment.
  9. Fresh-clone reproducibility: required fixtures are tracked or produced through a documented deterministic setup step.
  10. Regression coverage: the full existing test suite and repository gates pass. Tests are not weakened to accommodate the move.
  11. Change scope: the final working tree contains only intended refactor changes plus recorded pre-existing user changes. Rename detection confirms tracked moves.
  12. External identity: after authorization, the Git remote and local checkout use curriculum_factory, and documented clone instructions match.
