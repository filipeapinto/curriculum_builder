Curriculum Factory repository refactor

This document defines the intent, boundaries, required artifacts, acceptance criteria, and evidence for a coordinated repository-identity and layout refactor. It is the upstream source from which an execution prompt and executable tests must be written.

StatusIdentitySourceOutputsInventoryDeliverablesTestsConclusions

1. Status and authority

This specification does not execute the refactor.It must remain independent of any prompt, plan, script, or test suite derived from it. Derived artifacts may cite this specification; this specification must not require or cite the prompt that implements it.

The words must, must not, required, and complete are normative. Observed repository facts are starting evidence and must be rechecked immediately before implementation.

2. Intent and scope

The repository currently expresses several identities and lifecycle concepts inconsistently. The refactor must align the human product name, Git repository identity, local checkout name, Python packaging and import namespace, production-source placement, machine identifiers, documentation, and generated-artifact lifecycle.

The scope includes names and paths throughout production code, tests, policies, schemas, curricula, skills, research, governance, documentation, automation, and scripts. It also includes classification of every top-level directory. It does not authorize deletion based only on age, an unfamiliar name, or an assumption that generated data is reproducible.

The implementation must apply values by semantic role rather than global substitution. Schema $id values, serialized names, external URLs, and network identifiers such as User-Agent strings are compatibility-sensitive and require an explicit keep/change decision recorded in an exceptions inventory.

Renaming the remote repository or the local checkout is an external or parent-directory operation. The derived execution prompt must require explicit authorization immediately before those operations and place them after the in-repository migration is validated.

4. Python source architecture

Required foundation: src/curriculum_factory/.src/ identifies installable source. curriculum_factory is the stable Python namespace. Python modules must not be placed directly under src/.

The current runtime/ package combines orchestration, routing, retrieval, rendering, validation, persistence, and command-line responsibilities. The target architecture should make those responsibilities visible below the product namespace:

src/
└── curriculum_factory/
    ├── __init__.py
    ├── cli.py
    ├── orchestration/
    ├── routing/
    ├── retrieval/
    ├── rendering/
    ├── validation/
    └── persistence/

The migration must be staged. First establish packaging and move production code with behavioral equivalence; update imports, CLI entry points, module commands, mocks, fixtures, documentation, and every repository-root calculation based on __file__. Responsibility-based module splitting may follow only after the move passes equivalence tests. A compatibility layer is permitted only when a confirmed consumer requires it, and it must have a documented removal condition.

policy/, schemas/, curricula/, docs/, and outputs/ remain outside src/. They are contracts, domain inputs, human documentation, or generated artifacts rather than Python source. A second top-level package below src/ is justified only by an independently reusable or deployable component.

5. Generated output and durable evidence

Retain outputs/; remove its role as permanent storage.The directory remains the ignored runtime write boundary and should be empty between runs. Durable fixtures, audits, and cited evidence must live in tracked, purpose-named locations.

The starting repository proves the boundary is active: output-path validation constrains writes beneath ENGINE/outputs/; controller and graph code call that validation; tests create run directories there; policy and meta-prompt contracts name outputs/<run>/; and .gitignore excludes the subtree.

6. Required discovery inventory

Before producing a move plan, the implementing agent must record:

  • current and target values for every identity in §3;
  • every top-level directory, its reader or owner, tracked/ignored state, lifecycle classification, and proposed disposition;
  • all production imports, module commands, and entry points rooted at runtime;
  • all __file__-based root traversal and every absolute checkout path;
  • all live forms of the old product, repository, source-path, package, and output-run names;
  • existing and missing packaging, build, test, and installation configuration;
  • producers and consumers of every output child and questionable directory; and
  • compatibility-sensitive identifiers and justified exceptions.

UNKNOWN is allowed only when the inventory identifies the evidence needed to resolve it. No directory with an unresolved lifecycle classification may be deleted or renamed.

7. Required derived artifacts

An agent implementing this specification must create a reviewable package before changing production layout:

  1. Migration inventory: evidence and dispositions required by §6.
  2. Execution plan: ordered, reversible phases with dependencies, compatibility decisions, rollback points, and explicit authorization boundaries.
  3. Execution prompt: a self-contained agent prompt derived from this specification. It must name exact phases, permitted mutations, stop conditions, test commands, and completion evidence. It must not weaken or replace this specification.
  4. Executable test suite: tests that fail against relevant parts of the pre-refactor state and prove the acceptance criteria after migration.
  5. Exceptions inventory: every intentional old identifier or path, its consumer, compatibility rationale, and removal condition where applicable.
  6. Final migration report: identity map, directory disposition, changes, test evidence, retained exceptions, removed generated material, and external operations still awaiting authorization.

The execution prompt and tests are outputs derived from this specification; neither is an authority for changing its intent.

8. Minimum executable acceptance tests

The derived tests must use stable assertions rather than merely searching for a preferred phrase. At minimum they must prove:

  1. Installed import isolation: the application imports as curriculum_factory from an installed src-layout build without relying on the repository root or ad hoc sys.path insertion.
  2. CLI equivalence: documented entry points and module commands resolve and preserve expected argument behavior.
  3. Repository-root resolution: policies, schemas, curricula, and output boundaries resolve correctly after the deeper source path.
  4. Output containment: a run-named directory below outputs/ is accepted; a path outside it is rejected before artifact creation.
  5. Fixture independence: tests and active research/skill fixtures do not read durable evidence from ignored outputs/.
  6. Empty-output resilience: the full test suite passes when generated children under outputs/ are absent.
  7. Reference integrity: live code, automation, and documentation contain no stale source, checkout, or identity reference except reviewed exceptions.
  8. Documentation integrity: documented repository paths resolve and documented commands execute in their stated environment.
  9. Fresh-clone reproducibility: every required fixture is tracked or generated through a documented deterministic setup step.
  10. Scope integrity: the final working-tree delta contains only intended refactor changes plus recorded pre-existing user changes; tracked moves are reviewed with rename detection.

The full pre-existing test suite and gate harness must also pass. A test may not be weakened merely to accommodate the new layout; changed assertions require a documented change in intended behavior.

9. Normative conclusions

  1. This work is a coordinated identity, packaging, source-layout, lifecycle, and reference migration—not a rebrand search-and-replace.
  2. src/curriculum_factory/ is the required Python foundation. Multiple responsibilities belong beneath that namespace unless they become independently reusable or deployable products.
  3. The current broad runtime package is a migration source, not the permanent target architecture. Behavioral equivalence precedes subsystem decomposition.
  4. outputs/ remains the generated-write boundary and is disposable between runs. Durable fixtures and evidence must move outside it.
  5. arduino_kit_run_v2 cannot simply be deleted; required evidence must be minimized, tracked, and all consumers migrated first. Other runs remain candidates until rescanned and proven unnecessary.
  6. A fresh clone must be sufficient to install, test, and understand the repository without hidden ignored-state dependencies.
  7. The execution prompt and executable tests must be written from this specification and must trace their requirements back to its sections.
  8. Remote and checkout-directory renames occur only after internal validation and explicit authorization.
