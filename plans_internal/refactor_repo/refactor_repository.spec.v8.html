Curriculum Factory repository refactor

Align product and repository identity, adopt an installable Python source layout, classify directories by lifecycle, and separate disposable run output from durable fixtures and evidence.

GoalsIdentitySchema IDsSourceCodemodsOutputsInventoryPhasesPrompt setDeliverablesTestsExternal steps

1. Goals

  • Use Curriculum Factory consistently as the human-facing product name.
  • Adopt consistent repository, distribution, and Python-package names.
  • Move production Python code into an installable src layout without combining that move with an unsupported subsystem redesign.
  • Classify every top-level directory by owner, reader, and lifecycle.
  • Keep generated run output separate from tracked fixtures and retained evidence.
  • Make installation, imports, tests, commands, and documentation work from a fresh clone.

3. Schema identifier rule

Treat a schema $id as a versioned contract identifier, not branding text.

  1. Preserve the existing $id when the schema keeps the same filename version and semantic contract, even if the URI contains the old repository name.
  2. Do not rewrite a published or referenced $id in place solely for naming consistency.
  3. Use the new canonical namespace when creating a new schema version. Update all corresponding $ref values, registries, fixtures, and documentation in the same change.
  4. An existing identifier may change only when repository-wide reference analysis proves it has no consumer and the migration records the old-to-new mapping. If consumer absence cannot be proven, preserve it.
  5. Tests must validate both reference resolution and the recorded identifier decision for every live schema.

4. Python source migration

Source-move targetAfter the packaging skeleton exists, move the current production package beneath src/curriculum_factory/ while preserving its module boundaries and behavior. Do not require a responsibility-based split in the same phase.
src/
└── curriculum_factory/
    ├── __init__.py
    ├── capabilities.py
    ├── checkpoint.py
    ├── controller.py
    ├── io.py
    ├── logger.py
    ├── run_curriculum.py
    ├── session_bridge.py
    ├── langgraph_factory/
    └── … remaining current runtime modules

The packaging-skeleton phase must add pyproject.toml with a declared build backend, distribution metadata, src-only package discovery, and explicit console entry points. It must prove that the skeleton builds before production files move.

The following source-move phase updates imports, module commands, mocks, fixtures, documentation, and every repository-root calculation based on __file__. Tests must run against the installed distribution rather than repository-root path injection.

Classify every non-Python resource used by production code:

  • Resources shipped inside the distribution must be declared as package data, included in both wheel and sdist, and read through importlib.resources or an equivalent loader that does not assume an ordinary filesystem path.
  • Repository-owned policy, schemas, curricula, and output directories that remain outside the distribution must be reached through an explicit application data-root or repository-root input. Production code must not infer that root by counting Path(__file__).parents.

Later decomposition

Subsystem decomposition is a separate decision. Propose a subpackage only when the inventory demonstrates all of the following:

  • a cohesive responsibility shared by multiple modules;
  • a stable boundary with identifiable callers and dependencies;
  • lower coupling or clearer ownership than the current placement;
  • no import cycle introduced by the move; and
  • focused tests that can verify the boundary.

Names such as orchestration, routing, retrieval, rendering, validation, and persistence are candidates to evaluate, not prescribed directories. Any decomposition requires its own target tree and evidence in the execution plan.

Test-tree decision

Do not rename tests/runtime/ to tests/curriculum_factory/: a test directory matching the installed package name can become an import-shadowing candidate under path-based collection or accidental package initialization. After installed-package parity is established, classify the current tests by scope, shared fixtures, execution cost, environment dependencies, and CI lane. Then either:

  • retain tests/runtime/ when “runtime” remains an accurate test-domain label and the directory is not importable as a top-level package; or
  • move tests into evidence-supported, non-package-mirroring groups such as tests/unit/, tests/integration/, and tests/acceptance/.

If tests move, update discovery configuration, imports, fixture paths, scripts, documentation, internal path assertions, and direct CI references—including .github/workflows/plan26-lock-drift.yml—in the test-organization phase. Do not combine that move with packaging or production-source movement.

Keep policy/, schemas/, curricula/, docs/, and outputs/ outside src/.

5. Mechanical transformation controls

Use syntax-aware transformation for Python import and qualified-name changes. LibCST is the default unless the execution plan demonstrates an equivalent parser-based tool. Use parser-based updates for TOML, JSON, and YAML. Restrict regular expressions to discovery and narrowly bounded prose or literal substitutions.

Every codemod must provide:

  • before-and-after fixtures covering aliases, multiline imports, qualified names, comments, strings, dynamic or ambiguous references, and already-migrated input;
  • a dry-run mode that emits a reviewable diff without writing;
  • deterministic output and a recorded tool/version;
  • an idempotence test proving a second application produces no change;
  • explicit non-targets and a failure or warning for constructs that cannot be transformed safely; and
  • postconditions for residual old references and unexpected new references.

Documentation meaning, shell commands, external URLs, public identifiers, and dynamically constructed paths require human review even when a mechanical transform can edit them.

6. Output lifecycle and fixture migration

Keep outputs/ as the ignored runtime write boundary.It should be empty between runs. Durable tests, fixtures, research evidence, and audit evidence must not depend on files stored there.

At execution time, enumerate every child of outputs/ and record its size, producer, tracked and untracked consumers, reproducibility, evidence value, and proposed disposition. Do not copy point-in-time counts or sizes from this specification into the plan as current facts.

Fixture inclusion rule

A migrated run fixture must contain a machine-readable manifest. Every retained file must have:

  • its fixture-relative path and SHA-256 digest;
  • at least one named active consumer;
  • the assertion, citation, or behavior that requires the file;
  • whether exact bytes are required or a generated equivalent is acceptable; and
  • the source run and migration date.

No file may remain in the fixture without a manifest entry and active consumer. Every consumer must resolve to a retained file or a documented generator. Tests must enforce both directions of this relationship. This consumer-closure rule defines “minimal”; no arbitrary file-count or byte cap applies.

Disposition rules

  • Move exact historical bytes only when a test assertion or active evidence citation depends on them.
  • Generate test-local data when the test checks behavior rather than historical content.
  • Move retained non-test evidence to a tracked evidence or archive location instead of disguising it as a test fixture.
  • Remove an output run only after all consumers are migrated, replaced by generators, retired, or shown to be historical-only.
  • After migration, deleting all generated children beneath outputs/ must not break tests or active repository references.

7. Required inventory and baseline

Create a read-only, schema-versioned inventory tool for this refactor. It must emit both a human-readable report and timestamped machine-readable data, run without modifying the repository, and return a nonzero exit status when collection is incomplete. Run it immediately before planning and again before destructive cleanup. Every report must record its schema version, timestamp, repository commit, dirty state, tool versions, omissions, collection failures, and command/configuration used.

The inventory must combine version-control state, lexical search, syntax-aware Python analysis, structured-file parsing, runtime observations, declared dependencies, and the installed environment. Include a pip inspect report or an equivalent versioned environment inventory without treating installed state as a substitute for declared dependencies. Record:

  • the current value and target value for each identity in §2;
  • every top-level directory, its owner or reader, tracked and ignored state, lifecycle, and disposition;
  • all imports, module commands, and entry points rooted at runtime;
  • all __file__-based root traversal and absolute checkout paths;
  • all live references to old identity, package, source-path, and output-run names;
  • packaging, installation, build, and test configuration;
  • producers and consumers of every output child and questionable directory, including specs/; and
  • the package/import status, scope, execution cost, environment needs, CI lane, and every direct reference for each subtree beneath tests/;
  • schema-ID and other compatibility-sensitive decisions.

Classify each directory as production source, repository contract, domain input, generated runtime data, cache or scratch data, test fixture, retained evidence, active documentation, or deprecated history. Do not rename or delete an unresolved directory.

Behavioral baseline

Before implementation, capture tests and gates, documented commands, import origins, CLI help and invalid-input exit behavior, schema resolution, output containment, and representative public artifacts or semantic digests. Record existing failures separately. Where behavior is intended to remain equivalent, define the normalization rules for nondeterministic fields before comparing baseline and candidate results.

8. Phase and rollback structure

Use independently reviewable and revertible phases:

  1. inventory tooling and behavioral baseline;
  2. packaging skeleton;
  3. mechanical source move and import rewrite;
  4. resource and repository-root repair;
  5. fixture and retained-evidence migration;
  6. schema compatibility and reference closure;
  7. clean-room release verification;
  8. evidence-based test-tree organization, if required;
  9. optional subsystem decomposition; and
  10. authorized external rename.

Do not mix broad formatting churn, fixture cleanup, or subsystem redesign into the source-move phase. Record the baseline commit and verification result at every checkpoint. Define a Git rollback for each repository phase and a separate reversal or recovery procedure for non-Git state such as remote names, integrations, registries, Pages, and published identifiers. Use clean linked worktrees or equivalent isolated checkouts for baseline and candidate verification without disturbing the user’s dirty worktree.

Execution-prompt decomposition

The phases above define planning and rollback boundaries; they are not execution prompts. After the inventory and execution plan are complete, translate each phase into as many bounded prompts as its evidenced work requires. Do not create one omnibus prompt for the repository refactor, and do not assume that one phase equals one prompt.

Each execution prompt must:

  • have one principal objective and a narrowly defined mutation boundary;
  • state its prerequisites, permitted files or subsystems, explicit non-targets, and required inputs;
  • define executable acceptance checks, required evidence, stop conditions, and rollback procedure;
  • produce a reviewable checkpoint that can be accepted or reverted independently;
  • avoid combining discovery, planning, broad migration, cleanup, and optional redesign unless the execution plan proves they form one atomic change; and
  • identify successor prompts that are unblocked by its completion without pre-authorizing their mutations.

The execution plan must include a prompt manifest that assigns every planned change and acceptance criterion to exactly one primary prompt, records cross-prompt dependencies, and demonstrates complete coverage without overlapping mutation ownership. Prompt count is an output of this decomposition and must not be fixed before the inventory establishes the actual change surface.

9. Deliverables

  1. Inventory tool and reports: reproducible read-only collection plus timestamped findings, classifications, consumers, and proposed dispositions in human- and machine-readable forms.
  2. Execution plan: ordered phases, target tree for each phase, dependencies, rollback points, authorization boundaries, and validation commands.
  3. Execution prompt set and manifest: bounded prompts derived from the execution plan, with exact ordering and dependencies, mutation ownership, non-targets, stop conditions, test commands, completion evidence, rollback instructions, and traceability to every planned change and acceptance criterion.
  4. Executable tests: automated checks covering §8.
  5. Fixture manifests: bidirectional consumer closure for every retained run-derived file.
  6. Exceptions inventory: retained legacy identifiers or paths with rationale and removal conditions.
  7. Codemods and tests: version-pinned transformations, fixtures, dry-run output, idempotence evidence, and residual-reference postconditions.
  8. Rollback map: reversal procedure and validation checkpoint for every repository and external phase.
  9. Migration report: final identities, directory dispositions, changes, test results, removed outputs, retained evidence, exceptions, and pending external operations.

10. Executable acceptance tests

  1. Installed imports: production code imports as curriculum_factory from the installed src-layout distribution without repository-root or ad hoc sys.path assistance.
  2. CLI behavior: documented entry points and module commands preserve expected arguments and exit behavior.
  3. Root resolution: production code finds policies, schemas, curricula, and the output boundary from the new package location.
  4. Distribution artifacts: wheel and sdist build successfully; their file lists and metadata are inspected; the wheel installs into a fresh environment; imports, CLI, and packaged-resource smoke tests pass from outside the checkout.
  5. Module origin: imported production modules resolve from the clean installed distribution, not the checkout or test tree.
  6. Test-tree decision: the inventory records whether tests/runtime/ remains accurate or maps every moved test to an evidence-supported test category; discovery, CI, scripts, fixtures, and path assertions agree with the selected layout.
  7. Shadowing rejection: from the repository root, test directories, and an external working directory, curriculum_factory resolves only to the installed distribution; neither runtime nor a test-tree path can resolve as the production package. Tests fail if a test directory becomes an importable top-level curriculum_factory package.
  8. Output containment: a run directory beneath outputs/ is accepted; an external path is rejected before artifact creation.
  9. Fixture closure: every retained fixture file has a valid manifest entry and active consumer; every declared fixture dependency resolves.
  10. Ignored-state independence: no test or active evidence reference requires durable files beneath ignored outputs/.
  11. Empty-output resilience: the full suite passes with no generated children beneath outputs/.
  12. Schema identity: live $id and $ref values resolve and match the recorded preserve-or-version decision.
  13. Reference integrity: live code, automation, and documentation contain no stale identities or paths except recorded exceptions.
  14. Documentation integrity: documented paths resolve and documented commands execute in their stated environment.
  15. Fresh-clone reproducibility: required fixtures are tracked or produced through documented deterministic setup.
  16. Clean-room verification: release tests pass in a clean checkout containing no ignored or untracked local material and provisioned only through documented dependencies.
  17. Behavioral differential: intended-equivalent CLI and representative outputs match the recorded baseline after applying only predeclared normalization of nondeterministic fields.
  18. Codemod safety: transformation fixtures pass, dry-run output is reviewable, a second application is empty, and residual-reference postconditions pass.
  19. Regression and scope: the existing tests and gates pass, no test is weakened to accommodate the move, and the final delta contains only intended changes plus recorded pre-existing work.
  20. Inventory reproducibility: the inventory tool completes from a fresh clone, does not change the working tree, produces schema-valid machine-readable output, and reports unresolved collection failures as failures rather than empty results.

11. External completion steps

Before requesting authorization, inventory clone URLs, badges, GitHub Pages and custom domains, webhooks, deploy keys, packages and containers, integrations, branch protection, environments, secrets and variables, dependency automation, deployment systems, reusable workflows, Marketplace publication, and every GitHub Actions uses: owner/repository@ref consumer. GitHub Actions references to a renamed action repository do not receive the normal repository redirect and require an explicit compatibility plan. Confirm that the old repository name will not be reused while redirects are needed.

After all executable acceptance tests pass, request authorization to rename the remote repository and local checkout to curriculum_factory. Update origin, clone documentation, downstream remotes, and affected integrations. Exercise clone, fetch, and push plus every applicable integration, then record observed results and rollback status in the migration report. These are completion steps, not automated acceptance tests.
