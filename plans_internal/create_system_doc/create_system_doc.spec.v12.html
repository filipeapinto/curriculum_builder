Graph-system documentation skill

One reusable skill creates or updates detailed architecture and operations documentation for graph-based AI systems. Documentation depth is mandatory. Workflow bureaucracy is not.

PurposeWorkflowEvidenceContentVisualsUpdatesQualityAssuranceOutputs

Purpose and governing principle

Create a trustworthy, detailed system guide.The guide explains the system boundary, architecture, graph behavior, runtime contracts, deployment, security, configuration, observability, operation, failure, and recovery at the level supported by inspected evidence.

The skill serves design reviewers, maintainers, and authorized operators. It must provide enough detail for them to understand the system and perform their permitted tasks without reconstructing it from the repository.

Minimum sufficient process: use the least expensive workflow that satisfies the content and quality requirements below. Add a control only when it mitigates an identified consequence, disclosure risk, or audit requirement.

This specification does not require separate plan, create, and update skills; canonical JSON handoff artifacts; exhaustive claim records; graph manifests; or human approval of non-destructive drafting. Those controls remain available under higher assurance when justified.

Single-skill staged workflow

The skill performs these stages internally. A stage may use deterministic scripts or model reasoning, but it does not require a persisted artifact merely to hand work to the next stage.

StageRequired actionCompletion condition
1. FrameIdentify the requested system, audience, deliverable, permitted sources, output location, disclosure constraints, and whether this is creation or update.The task boundary is unambiguous. Ask only for missing information that would materially change or endanger the result.
2. InspectRead the relevant code, prompts, graph definitions, schemas, configuration, deployment material, tests, traces, policies, and runbooks. Follow dependencies needed to explain behavior.Relevant evidence has been inspected or its absence is recorded.
3. ModelReconstruct the architecture, execution paths, state, interfaces, dependencies, controls, failure behavior, and operational procedures. Resolve conflicts where evidence permits.Every material assertion is supported, qualified, or marked unknown.
4. WriteCreate the guide and only those diagrams or tables that materially improve understanding.The content requirements applicable to the system are covered.
5. VerifyCheck factual grounding, completeness, secrets, links, output integrity, accessibility, and rendered readability. Repair bounded failures.Required checks pass or the deliverable clearly records remaining gaps.
6. DeliverWrite a new file freely within the authorized location. Before overwriting an existing deliverable or publishing externally, present a concise change and risk summary and obtain approval.The user receives the deliverable plus a compact verification summary.

Use deterministic code for file discovery, hashing, diffs, schema parsing, link checking, secret scanning, and retry counters. Do not spend model tokens narrating bookkeeping that code can perform.

Evidence discipline

Documentation detail must come from evidence, not plausible completion. The skill maintains a lightweight source register containing source path or identifier, version or freshness when available, and scope inspected. This register may live in the document or compact run summary.

Evidence labelMeaningRequired treatment
DeclaredA design, configuration, policy, prompt, schema, or runbook states the behavior.Do not imply that the behavior executed successfully.
ObservedA trace, test, log, or other execution evidence demonstrates the behavior.Name the observation scope, version or time, and important unexercised paths.
InferredThe conclusion follows from inspected evidence but is not directly stated or executed.State the reasoning and avoid presenting it as observed fact.
Unknown or conflictingEvidence is absent, insufficient, stale, or contradictory.Preserve the uncertainty and explain its effect on readers or operations.

Apply labels where they matter: at a section, table row, diagram element, or important claim. Exhaustive sentence-level claim IDs are not required by default. Never expose secrets, credentials, private endpoints, restricted data, or disallowed implementation detail.

The following standard preserves v11’s information depth. A concern may be marked not applicable only with a reason. Missing evidence is documented as a gap, not silently omitted.

Do not infer formal nodes or edges from narrative order alone, treat declared behavior as proof of execution, invent generic security controls, or conceal missing evidence behind polished prose.

Visuals chosen for reader value

Use a diagram when relationships, flow, boundaries, or state changes are materially clearer visually. Use prose or a table when they are clearer. A diagram is not mandatory merely because the system contains a graph.

  • For a complex system, begin the substantive guide with a readable architecture overview.
  • Add focused graph, data-flow, deployment, security-boundary, configuration-impact, or recovery views only when they answer distinct reader questions.
  • Every visual has a title, takeaway, scope, evidence status, and text or tabular equivalent.
  • No visual may invent a component, edge, control, parameter effect, execution result, or confidence level.
  • Inspect every generated visual for clipping, overlap, unreadable labels, broken arrows, misleading layout, and accessibility. No meaning may depend on color alone.
  • Any capable renderer may be used. A repository-local renderer is an implementation option, not a normative dependency.

Efficient updates

When updating an existing guide, compare current sources with the sources or versions recorded previously. Identify affected sections and visuals, then update only those areas unless structural change makes full regeneration safer or cheaper.

  • Preserve unaffected, still-correct material.
  • Recheck dependencies of changed evidence.
  • Rerender only affected visuals.
  • Show the user a concise semantic diff before overwriting or publishing.
  • Do not preserve claims or visuals whose supporting evidence is stale or contradicted.

Automatic repair is limited to two attempts for the same failure. Stop earlier when output is unchanged or oscillates. Report unresolved failures instead of consuming tokens indefinitely.

Conditional assurance escalation

The default workflow above is complete. Additional controls are activated only when the user requests them or when the intended action has a concrete consequence that requires them.

TriggerAddDo not add automatically
Shared design review or operational dependencyPersisted source register, important-claim traceability, named reader scenarios, and structured gap list.Sentence-level claim records or canonical artifacts.
Overwrite, external publication, or sensitive disclosureHuman approval of concise diff, disclosure findings, and known risks.Approval before harmless drafting.
Regulated, contractual, safety-critical, or independently audited outputFull claim-level provenance, canonical digests, immutable approval records, independent review, complete render records, and applicable conformance fixtures.Assumption that these controls benefit unrelated low-risk work.
Large or resumable multi-session jobCompact persisted checkpoints sufficient to resume without rereading everything.Separate skills or expansive schemas unless interoperability requires them.

If escalation is proposed, state the triggering risk and the added control. Complexity without a named risk or requirement is non-conforming.

Required outputs and conformance

A successful run produces:

  1. The requested detailed architecture and operations guide.
  2. Any useful diagrams and their accessible equivalents.
  3. A compact verification summary listing sources inspected, freshness, checks performed, unresolved gaps, and whether approval is needed for the next action.

No JSON artifact is mandatory in the default workflow. The compact summary may be embedded in the guide, returned to the user, or saved beside the deliverable when continued maintenance requires it.

An implementation conforms to v12 when it produces the required detailed content, preserves evidence honesty, passes the applicable quality gates, uses bounded repair, and adds assurance controls only for stated risks or requirements.

Acceptance ruleA reader must receive the same depth of system information expected by v11, with less mandatory process. Simplification that removes architecture, runtime, deployment, security, operational, or evidence detail does not conform.
Version 12 replaces the mandatory three-skill and artifact-control architecture of v11 with one staged skill and conditional assurance. Version 11 remains a reference library for maximum-assurance controls, not the default implementation contract.
