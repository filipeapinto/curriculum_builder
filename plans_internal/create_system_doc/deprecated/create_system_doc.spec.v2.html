Graph-system documentation skill family

This specification defines a model-agnostic skill series that turns verified evidence about a graph-based LLM system into engaging, accurate architecture and operations documentation. It complements the graph-doc-* document-creation graph: that family governs general document production; this family supplies the system-specific fact model, views, controls, and verification needed to document an executable graph system.

Purpose and boundary

Give a reader a self-contained, trustworthy operating understanding of the system.They can see its architecture, graph behavior, interfaces, deployment, security controls, configuration, and recovery procedures without hunting through implementation specifications.

This documentation does not replace source specifications, schemas, policies, code, or run evidence; those remain authoritative. It is the verified reader-facing guide to them: concise enough to use during design review or operations, and traceable enough to resolve detail at the source.

A conforming skill may run in Codex, GPT/ChatGPT, Claude, Grok, or another platform. It defines the required documentation result, not a model, package, tool, runtime, cloud provider, or graph framework.

This is the output and conformance specification for the graph-system-documentation-* family. It does not redefine general request intake, document-goal elicitation, document graph compilation, or generic document rendering already owned by graph-doc-*. An implementation may invoke those skills, consume their validated artifacts, or expose equivalent schema-valid handoffs.

Skill family and decision ownership

The family is a staged graph, not a single prompt. Implementations may combine mechanical stages, but they must preserve the decision boundaries and auditable artifacts below. A stage must not silently make a decision owned by another stage.

An orchestrator or compiler sequences these stages, validates every handoff, records retries, and stops on a blocking result. It may route work; it does not absorb the stages’ decision ownership.

Artifact contracts and terminal states

Every JSON handoff must be schema-valid, versioned, content-addressed, and linked to its producing stage and inputs. Identifiers for sources, claims, components, routes, fields, controls, views, and findings must remain stable across downstream artifacts. Prose is never the only handoff when a downstream stage must test or transform the result.

Contract ruleRequirement
Claim granularityEvidence class, source references, scope, freshness, conflict state, disclosure state, and confidence attach to an individual claim. A visual or section may summarize but may not replace claim-level status.
Evidence precedenceThe intake or governing policy defines authority by claim type. When sources disagree and no rule resolves them, preserve the conflict and prevent an unqualified claim.
TraceabilityEach published factual element maps to one or more eligible claim identifiers; each required concern maps to a section, view, explicit not-applicable disposition, or verified gap.
Change controlA source, scope, disclosure, schema, or fact-model change invalidates dependent artifacts by digest and triggers regeneration from the earliest affected stage.

Each stage terminates as complete, complete_with_gaps, or blocked. The artifact records reasons, unresolved items, and the earliest stage able to resolve them. Only outputs permitted by the intake’s completion and disclosure rules may proceed to publication.

Visualization-led reader journey

  1. Begin with architecture. The first substantive element is a readable system map showing components, graph flow, data movement, deployment/trust boundaries, and key external dependencies.
  2. Show evidence class. Each visual exposes the claim-level distinction between declared, observed, inferred, and unknown; a visual may contain more than one class. Observed claims name run IDs, time/version scope, sampling limits, covered paths, and unexercised declared paths.
  3. Use focused views. Follow the overview with graph, schema/data-flow, configuration-impact, deployment, security-boundary, and failure/recovery views when they clarify relationships. Use tables where they are clearer.
  4. Make visuals inspectable. Show a title, takeaway, scope, evidence/freshness status, source references, and a legend where needed. Provide a prose or tabular equivalent; use semantic SVG title and desc where applicable. No meaning may depend on color alone.
  5. Keep visuals honest. A renderer arranges verified facts; it does not invent components, links, controls, parameter effects, execution outcomes, or confidence.

HTML is preferred when it improves visual navigation or exploration. It must have a static, no-JavaScript baseline; external assets are not required for comprehension.

Operations guide and verification record

The documentation must let an authorized operator determine the current state, perform routine work, and respond safely to common failures without reading source specifications first.

Operational needRequired documentation
OperatePrerequisites, authorized roles, safe run modes, start/stop or trigger procedure, expected outputs, and prohibited actions.
ObserveHealth signals, dashboards/logs/traces, run/correlation identifiers, alerts, success/failure criteria, and ownership.
RecoverFailure triage, retry/repair/resume rules, rollback/restore, escalation, and when not to retry.
Verify scopeSources inspected, source versions/digests, verification time, excluded scope, unavailable checks, unresolved conflicts, and known risks.

Quality gates

  1. Self-contained for readers: an authorized reader can understand architecture, deployment, security posture, configuration, operation, and recovery without consulting source specifications first.
  2. Accurate and bounded: claims, contract entries, and visual labels trace to inspected evidence; partial coverage is never presented as complete.
  3. Security-aware: controls and gaps are explicit; secrets and restricted details are protected.
  4. Visualization-led: the architecture overview precedes explanatory prose; each added visual answers a clear reader question rather than decorating or repeating content.
  5. Accessible and offline-readable: use semantic structure, adequate contrast, keyboard-operable interaction, text alternatives, and no required CDN, remote asset, or JavaScript.
  6. Rendered QA: inspect desktop and narrow output; verify readable, unclipped labels, non-overlapping edges and legends, working links, and visual-to-fact-model traceability.
  7. Fresh and safe: show verification time and source version/digest; clearly mark unavailable or stale checks; write versioned outputs only in an approved location.
  8. Contract-valid: validate every stage artifact against its declared schema and reject broken identifiers, invalid digests, missing dispositions, or publication-ineligible claims.
  9. Pipeline-traceable: record the producing skill and version, input artifact digests, stage status, validation result, and any retry or human approval required for publication.
