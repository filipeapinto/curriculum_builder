Graph-system documentation skill family

This specification defines a vendor-neutral skill series that turns verified evidence about a graph-based LLM system into engaging, accurate architecture and operations documentation. It can interoperate with a general document-creation graph, including graph-doc-*, through the interfaces defined here; no external skill family is required for conformance.

Purpose and boundary

Give a reader a self-contained, trustworthy operating understanding of the system.They can see its architecture, graph behavior, interfaces, deployment, security controls, configuration, and recovery procedures without hunting through implementation specifications.

This documentation does not replace source specifications, schemas, policies, code, or run evidence; those remain authoritative. It is the verified reader-facing guide to them: concise enough to use during design review or operations, and traceable enough to resolve detail at the source.

A conforming family can be implemented for Codex, GPT/ChatGPT, Claude, Grok, or another platform. Conformance assumes a host can read sources and persist addressable artifacts; the storage mechanism, model, package, runtime, cloud provider, graph framework, and renderer remain implementation choices.

This is the output and conformance specification for graph-system-documentation-*. A general document pipeline may provide intake and rendering, but a conforming implementation must accept and emit the interfaces below directly or through a documented lossless adapter.

Skill family and decision ownership

The family is a staged graph, not a single prompt. Implementations may combine mechanical stages, but they must preserve the decision boundaries and auditable artifacts below. A stage must not silently make a decision owned by another stage.

Logical stageOwned decisionsRequired outputMust not do

graph-system-documentation-model-extractEvidence-backed components, routes, state, dependencies, deployment, controls, operations, and source-linked claims.system_fact_model.v1.jsonInvent missing topology or promote declared behavior to observed behavior.

An orchestrator or compiler sequences these stages, validates every handoff, records retries, and stops on a blocking result. It may route work; it does not absorb the stages’ decision ownership. Combining stages in one process does not remove their separate logical contracts.

An implementation may add only schema-permitted extensions and may not remove, rename, or reinterpret required fields. Contract ruleRequirement
Claim granularityEvidence class, source references, scope, freshness, conflict state, disclosure state, and confidence attach to an individual claim. A visual or section may summarize but may not replace claim-level status.
Evidence precedenceThe intake or governing policy defines authority by claim type. When sources disagree and no rule resolves them, preserve the conflict and prevent an unqualified claim.
TraceabilityEach published factual element maps to one or more eligible claim identifiers; each required concern maps to a section, view, explicit not-applicable disposition, or verified gap.
Change controlA source, scope, disclosure, schema, or fact-model change invalidates dependent artifacts by digest and triggers regeneration from the earliest affected stage.

Each stage terminates as complete, complete_with_gaps, or blocked. The artifact records reasons, unresolved items, and the earliest stage able to resolve them. Only outputs permitted by the intake’s completion and disclosure rules may proceed to publication.

Required run configuration and reference status

The six choices identified by the supporting assessment are required intake decisions, not universal constants. Before evidence inventory begins, the intake must resolve or explicitly block on: authoritative source roots and authority rules; first deliverable; renderer policy; output location and overwrite policy; required host/package targets; and a freshness command or deterministic freshness rule. This preserves comparability without imposing one repository layout or renderer on every implementation.

Repository-specific upgrade information is non-normative and lives in the v3-to-v4 migration note. No repository filename or existing prompt is part of this portable contract.

Automatic repair is bounded to two attempts for the same cause key at the same owning stage. The cause key is the RFC 8785 digest of {stage, gate_or_validator_id, error_code, subject_id}; free-text messages are excluded. A third occurrence stops as blocked. A relevant changed subject digest starts a new cause key. Repeated no-change output, a two-state digest oscillation, or failed disclosure also stops the run.

Visualization-led reader journey

  1. Begin with architecture. The first substantive element is a readable system map showing components, graph flow, data movement, deployment/trust boundaries, and key external dependencies.
  2. Show evidence class. Each visual exposes the claim-level distinction between declared, observed, inferred, and unknown; a visual may contain more than one class. Observed claims name run IDs, time/version scope, sampling limits, covered paths, and unexercised declared paths.
  3. Use focused views. Follow the overview with graph, schema/data-flow, configuration-impact, deployment, security-boundary, and failure/recovery views when they clarify relationships. Use tables where they are clearer.
  4. Make visuals inspectable. Show a title, takeaway, scope, evidence/freshness status, source references, and a legend where needed. Provide a prose or tabular equivalent; use semantic SVG title and desc where applicable. No meaning may depend on color alone.
  5. Keep visuals honest. A renderer arranges verified facts; it does not invent components, links, controls, parameter effects, execution outcomes, or confidence.

HTML is preferred when it improves visual navigation or exploration. It must have a static, no-JavaScript baseline; external assets are not required for comprehension.

Operations guide and verification record

The documentation must let an authorized operator determine the current state, perform routine work, and respond safely to common failures without reading source specifications first.

Conformance procedure and quality gates

Conformance is adjudicated per completed run, not by vendor assertion. The verifier records a pass, fail, or not-applicable result for every gate. A required gate passes only by the procedure below; any failure blocks an unqualified publication decision. Human judgments require a named evaluator independent of the rendering stage and a recorded rationale.

GateOwnerRequired check and pass condition
Reader sufficiencyVerifyA named representative reader completes the intake’s scenario checklist using only the deliverable; every required answer is correct and locatable, or the completion policy records an accepted gap.
Accuracy and boundsAdjudicate + verifyEvery factual element resolves to an eligible claim ID; every claim resolves to inspected source IDs; no incomplete coverage is labeled complete.
Security and disclosureGoal-define + verifyAutomated secret/restricted-pattern scan passes and the named disclosure approver accepts every exception against the intake policy.
Visual purposePlan + verifyEvery view has a reader question, takeaway, source claim IDs, and text equivalent; duplicate views without a distinct question fail.
Accessibility and offline useRender + verifyAutomated WCAG 2.2 AA checks pass where testable; keyboard, text-equivalent, no-color-only, and disconnected/no-JavaScript checks pass by recorded inspection.
Rendered qualityRender + verifyAt the intake-declared desktop and narrow viewports, recorded renders contain no clipped labels, unintended overlap, unreadable legends, or broken internal/source links.
Freshness and locationInventory + verifyThe configured freshness command/rule passes against current source digests and every output resolves beneath the intake-approved location without an unauthorized overwrite.
Contract validityEvery producer + verifyEvery artifact validates against its named schema and the normative fields here; identifiers, digests, dispositions, and publication eligibility pass referential checks.
Pipeline traceabilityOrchestrator + verifyThe run record identifies producer versions, input/output digests, stage statuses, retries, approvals, and terminal decision with no missing or unclosed stage attempt.

A family is run-conformant only when all required gates pass. It is implementation-conformant only when it passes the four normative cases and exact expected outcomes in fixtures/v4/conformance_cases.v1.json. Vendors may add tests but may not replace these cases. Equivalent vendor-specific artifacts require a published, deterministic, round-trip-lossless mapping to this specification.
