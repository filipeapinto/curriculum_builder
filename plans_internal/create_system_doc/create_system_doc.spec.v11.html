Graph-system documentation skill family

This specification defines three skills that plan, create, and update system documentation for graph-based LLM systems. The skills encode the documentation standard and require human approval before creating or changing the document.

PurposeSkill familyArtifactsConfigurationArchitectureDeploymentSecurityContractsVisualizationOperationsConformance

Purpose and boundary

Create the system’s architecture and operations documentation.It explains the system boundary, graph behavior, interfaces, deployment, security, configuration, observability, operation, and recovery.

The document is complete enough for design review and authorized operation. Every factual statement is supported by inspected system evidence, and every unknown, conflict, or unverified behavior is labeled.

This repository implementation requires Python 3, persistent files, and .claude/skills/graph-doc-graph-visualize. Models and graph frameworks remain implementation choices. The approved renderer_policy selects the local skill’s backend.

This is the output and conformance specification for graph-system-documentation-plan, graph-system-documentation-create, and graph-system-documentation-update. There is no separate goal-definition skill: the plan skill applies this specification’s documentation purpose and quality rules to the system, repository, audience information, and constraints supplied by the caller.

Three-skill workflow and decision ownership

Evidence inventory, system modeling, claim adjudication, rendering, and verification are internal work performed by the three skills.

SkillResponsibilityRequired outputBoundary
graph-system-documentation-planInspect permitted sources; model the system; adjudicate claims; plan the document; and produce an approved nodes[] plus typed edges[] visualization manifest for every documented graph.system_documentation_plan.v1.json, ending in explicit human approval status.Must not create, overwrite, or update the documentation deliverable.
graph-system-documentation-createConsume an approved plan; invoke the repository-local .claude/skills/graph-doc-graph-visualize skill; inspect and visually review its render; create the document; preserve claim traceability; and run conformance checks.Versioned document plus system_documentation_build.v1.json.Must not proceed from an unapproved or digest-mismatched plan, alter the visualization manifest, or expand scope.
graph-system-documentation-updateIdentify affected claims and views; obtain approval for the change set; rerender every affected graph with the repository-local .claude/skills/graph-doc-graph-visualize skill; update the document; and reverify it.Updated versioned document plus system_documentation_update.v1.json.Must not treat regeneration as approval, preserve a stale graph render, or publish when the approved change set and actual diff diverge.

The lifecycle is plan → human plan approval → create → human reader acceptance → publish. Updates follow update impact plan → human approval → update → human reader acceptance → publish. Plan approval and reader acceptance record the human evaluator, artifact digest, decision, time, and rationale. A changed digest invalidates the decision.

Claim granularityEach claim records its evidence class, sources, scope, freshness, conflicts, disclosure status, and confidence. Sections and visuals retain those claim links.
Evidence precedenceThe approved plan defines authority by claim type. Unresolved source conflicts remain explicit and block an unqualified claim.
TraceabilityEach published factual element maps to one or more eligible claim identifiers; each required concern maps to a section, view, explicit not-applicable disposition, or verified gap.

Each skill ends as complete, complete_with_gaps, or blocked. Use blocked when no safe valid artifact can be produced. Use complete_with_gaps when the artifact is valid but a finding blocks approval or publication. Skills set approval.eligibility; only a human sets approval to approved or rejected. A self-blocked plan remains pending.

Required run configuration and reference status

The plan records authoritative sources and precedence, the deliverable, renderer policy, output location, overwrite policy, supported hosts, and an executable freshness check. A command check records executable, arguments, and expected exit code. A digest comparison records SHA-256 and its operands.

This is a repository contract. The local skill path, schemas, fixtures, and output locations named here are normative.

Automatic repair is bounded to two attempts for the same cause key at the same owning stage. The cause key is the RFC 8785 digest of {stage, gate_or_validator_id, error_code, subject_id}; free-text messages are excluded. A third occurrence stops as blocked. A relevant changed subject digest starts a new cause key. Repeated no-change output, a two-state digest oscillation, or failed disclosure also stops the run.

Architecture and graph

The documentation must explain the system boundary, major components, external dependencies, trust boundaries, and data movement before presenting component-level detail.

Architecture concernRequired documentationTypical evidence
System boundaryUsers and actors, entry/exit interfaces, owned responsibilities, external systems, dependencies, and excluded scope.Architecture, API definitions, integration configuration, policy.
Graph behaviorEntries, nodes or steps, directed edges or handoffs, branches, loops, joins, failure paths, terminals, and external boundaries.Prompts, graph definitions, routing configuration, traces, tests.
Graph formWhether behavior is prompt-orchestrated or framework-defined, and what that evidence proves.Orchestrator prompts, component prompts, framework graph/runtime, code, traces.
DependenciesModels, tools, APIs, data stores, queues, identity providers, and their required availability or fallback behavior.Configuration, deployment manifests, code, runbooks, SLOs.

Do not infer formal nodes or edges solely from a prompt sequence, or treat a declared path as proof that it executed. If routing semantics are not evidenced, document a sequence or workflow rather than a graph.

Visualization-led reader journey

Every documented graph is rendered with .claude/skills/graph-doc-graph-visualize.The plan supplies the approved nodes and typed edges. Create and update render that manifest without changing it, run the skill’s inspect_layout.py, open the rendered image for visual review, and record the results.
  1. Begin with architecture. The first substantive element is a readable system map showing components, graph flow, data movement, deployment/trust boundaries, and key external dependencies.
  2. Show evidence class. Each visual exposes the claim-level distinction between declared, observed, inferred, and unknown; a visual may contain more than one class. Observed claims name run IDs, time/version scope, sampling limits, covered paths, and unexercised declared paths.
  3. Use focused views. Follow the overview with graph, schema/data-flow, configuration-impact, deployment, security-boundary, and failure/recovery views when they clarify relationships. Use tables where they are clearer.
  4. Make visuals inspectable. Show a title, takeaway, scope, evidence/freshness status, source references, and a legend where needed. Provide a prose or tabular equivalent; use semantic SVG title and desc where applicable. No meaning may depend on color alone.
  5. Keep visuals honest. A renderer arranges verified facts; it does not invent components, links, controls, parameter effects, execution outcomes, or confidence.

HTML is preferred when it improves visual navigation or exploration. It must have a static, no-JavaScript baseline; external assets are not required for comprehension.

The native graph artifact is SVG; PNG is permitted when required by the delivery format. Renderer failure, a blocking inspection finding, an unreviewed render, or a manifest/render digest mismatch blocks publication. Visual review records pass, fail, or not_performed; the last uses null reviewer fields and a reason. A named human performs completed visual reviews.

Operations guide and verification record

The documentation must let an authorized operator determine system state, perform routine work, and respond safely to common failures.

RecoverFailure triage, retry/repair/resume rules, rollback/restore, escalation, and when not to retry.

Conformance procedure and quality gates

Every run records pass, fail, or not-applicable for each gate. A failed required gate blocks publication. Human checks record the evaluator and rationale.

GateOwnerRequired check and pass condition
Reader sufficiencyHuman reader after create/updateA named reader completes the approved plan’s scenario checklist using only the deliverable. The build/update verification records evaluator, time, rationale, and each scenario result. Publication waits for acceptance.
Accuracy and boundsPlan + create/updateEvery factual element resolves to an eligible claim ID; every claim resolves to inspected source IDs; no incomplete coverage is labeled complete.
Security and disclosurePlan + create/updateAutomated secret/restricted-pattern scan passes and the named disclosure approver accepts every exception against the approved plan.
Visual purposePlan + create/updateEvery view has a reader question, takeaway, source claim IDs, and text equivalent; duplicate views without a distinct question fail.
Accessibility and offline useCreate/updateAutomated WCAG 2.2 AA checks pass where testable; keyboard, text-equivalent, no-color-only, and disconnected/no-JavaScript checks pass by recorded inspection.
Rendered qualityCreate/updateEvery graph render passes .claude/skills/graph-doc-graph-visualize’s artifact check and layout inspector, then receives a recorded visual review. At each approved viewport, the document has no clipped labels, unintended overlap, unreadable legends, or broken links.
Freshness and locationPlan + create/updateThe configured freshness command/rule passes against current source digests and every output resolves beneath the plan-approved location without an unauthorized overwrite.
Contract validityPlan/create/updateEvery artifact validates against its named schema and the normative fields here; identifiers, digests, dispositions, and publication eligibility pass referential checks.
Workflow traceabilityCreate/updateThe run record identifies skill versions, input/output digests, approval, retries, actual diff, and terminal decision with no missing or unclosed attempt.

A plan records awaiting_plan_approval or block. A build/update records awaiting_reader_acceptance, publish, publish_with_accepted_gaps, or block. An implementation conforms when it produces the expected results for every case in fixtures/v11/conformance_cases.v5.json; the fixture’s JSON-pointer map defines how each expected value is read from the artifact.
