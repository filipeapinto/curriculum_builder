Controlling Token Use in Long-Running Codex Tasks

How to keep a long-running task within an explicit token ceiling—without assuming that parallel agents, external tools, or account limits are automatically included.

Recommended: one budgeted goal in the main thread; do not spawn subagents.

This is the clearest native way to bound a long-running task. Create the goal before substantive work, keep all model activity in the same thread, check usage during execution, and stop optional work before the hard ceiling.

  • Use the goal’s token accounting as the task-level control.
  • Stop starting optional work at 80% and reserve the remainder for integration, validation, and final delivery.
  • Track paid tools and other non-token charges separately.

The final 20% remains available for integration, correction, validation, and delivery of the required output.

Key concepts in plain language

These words describe different layers of execution. Treating them as synonyms makes token accounting unreliable.

Conversation unit

Thread

A stored conversation history with its own thread ID. Turns happen inside a thread. A new thread, a forked thread, and a subagent thread are separate accounting boundaries unless the product explicitly says otherwise.

Work unit

Turn

One user instruction and the resulting model/tool activity inside a thread. A thread normally contains multiple turns.

Budgeted objective

Goal

A persisted objective attached to one thread. Goal state can carry a token budget, tokens used, elapsed time, and completion status.

History branch

Fork

A new thread created by copying the stored history of an existing thread, optionally only through a selected turn. It begins with inherited conversational context but receives a new thread ID.

Spawned agent

Subagent

An agent spawned to handle a specific task. It performs model and tool work in its own agent thread, then returns its result to the main agent.

Descendant execution

Spawned agent thread

The agent thread in which a subagent works. It is a spawned descendant of the main thread. Spawning one or several subagents creates one or several spawned agent threads.

Session
The broader running interaction or orchestration container. It may contain a primary thread and spawned descendant threads. Sharing a session does not prove that those threads share one token budget.
Tool call
An operation requested by an agent, such as searching, running a command, or calling an MCP connector. A tool call is not automatically a new thread. A tool may, however, invoke external metered services whose cost is not covered by the thread’s model-token counter.
Context
The information available to the model for a turn: instructions, conversation history, selected files, tool results, and other injected material. More context can increase input-token consumption.
Aggregate ledger
A task-owned record that adds together usage from the main thread, every separately budgeted child thread, retries, evaluators, and externally metered services.

Thread fork and subagent spawn are different

Read each diagram from left to right. A solid arrow means work continues or is created. A dashed arrow means a result returns to the primary thread.

Thread fork ≠ subagent spawn. thread/fork copies stored thread history into a new thread ID. Spawning starts a subagent in a spawned agent thread. Spawning does not imply that thread/fork copied the main thread’s stored history.

Does spawning a subagent fork the main thread? The documentation does not establish that equivalence. thread/fork is the formal history-copying operation. A subagent works in its own spawned agent thread.

Exact instructions for a 100,000-token task

These are the literal instructions for the example task: “Add CSV import to an application, test it, document it, and deliver the finished change.” The owner authorizes at most 100,000 model tokens for the entire task.

Allocation is not consumption. An allocation is the most a thread is allowed to use. Actual usage may be lower. The controller must record actual usage and must never create allocations whose combined maximum exceeds 100,000.
100,000ONE THREAD

Example 1 · Continue in the same thread

Exact user instruction to the primary agent

Create and pursue this goal in this thread only:

Objective: Add CSV import to the application, test it, document it, and deliver the finished change.
Token ceiling: 100,000 tokens.
Do not fork this thread. Do not spawn subagents. Do not move work into another chat or thread.
At 80,000 tokens, stop optional exploration and reserve the remaining budget for integration, test fixes, validation, and final delivery.
Check goal usage during execution. Stop before the ceiling is exceeded.

Required runtime action: attach a 100,000-token goal to Thread A before substantive execution. The text alone states policy; the runtime goal supplies accounting.

The primary agent inspects the code, implements CSV import, runs tests, fixes failures, writes documentation, and delivers the result—all in Thread A.

Thread A · 100k

Thread A maximum 100,000 = task maximum 100,000

Stop example: at 80,000 tokens, the agent stops optional exploration. The remaining 20,000 is reserved for fixing tests, validating the change, and delivering the final answer.

Why this is easiest: there is only one thread to meter and no child usage to add manually.

Example 2 · Start a new, unrelated thread

Exact instruction in Thread A

Continue the CSV-import goal in this thread. Do not treat activity in unrelated chats as part of this task.

Exact instruction entered in a new Thread B

Plan a five-day vacation itinerary for Lisbon. This is a separate task. Do not use, modify, or charge work to the CSV-import task or its token allocation.

Thread A owns the CSV-import task. The user separately starts Thread B to ask for a vacation itinerary. Thread B did not come from the CSV task and is not part of its authorization.

Key point: merely starting another thread does not make it a child of the CSV task. If Thread B is later used to help with CSV import, it must first receive an allocation from the CSV task’s 100,000-token total.

Example 3 · Fork to explore an alternative

Exact user instruction to the controller

Keep the CSV implementation in Thread A, with a maximum allocation of 70,000 tokens.
Create one fork from the current thread history to evaluate streaming CSV parsing versus loading the whole file into memory.
Give the forked Thread B a maximum allocation of 30,000 tokens.
Thread B must not edit implementation files. It must return a recommendation, evidence, risks, and its actual token usage.
Do not create any additional threads.
Stop the entire task when combined actual usage approaches 100,000 tokens.

Exact instruction placed in forked Thread B

Using the copied conversation history, compare two CSV-import designs:
1. Stream rows incrementally.
2. Load the complete file into memory.

Evaluate memory safety, error reporting, implementation complexity, and fit with the existing code.
Do not edit files. Return one recommendation with supporting evidence.
Your hard ceiling is 30,000 tokens. Report actual usage when complete.

Required runtime action: explicitly fork Thread A, creating a new Thread B ID; assign 70,000 to A and 30,000 to B; aggregate both usage totals.

Thread A has already discussed the CSV design. The agent deliberately forks that history into Thread B to explore whether streaming parsing is safer than loading the whole file into memory.

Original A · 70kFork B · 30k

70,000 original + 30,000 fork = 100,000 authorized

Actual-usage example: Thread A uses 52,000 and the fork uses 18,000. Aggregate task usage is 70,000—not 52,000.

Key point: the fork begins with copied history, but it is still a new thread ID. Copied context may itself increase the fork’s input-token consumption.

75k + 25kONE SUBAGENT

Example 4 · Spawn one testing subagent

Exact user instruction to the primary agent

Complete the CSV-import task with a 100,000-token total ceiling.
Reserve at most 75,000 tokens for the primary thread.
Spawn exactly one read-only testing subagent with at most 25,000 tokens.
Wait for the subagent, incorporate its findings, and report combined actual usage.
Do not spawn any other agents.

Exact task sent to the testing subagent

You are the read-only testing subagent for the CSV-import task.

Inspect the existing import tests and implementation interfaces.
Run the relevant tests.
Identify missing cases for malformed rows, encoding, empty files, duplicate headers, large files, and partial failure.
Do not edit any file.
Return: tests run, observed results, missing cases, and prioritized recommendations.
Hard token ceiling: 25,000. Stop before exceeding it and report actual usage.

Required runtime action: spawn one child agent thread with its own 25,000-token allocation; retain 75,000 for the controller; record both actual totals.

The primary agent keeps implementation and integration. It spawns one subagent with the bounded assignment: “Inspect existing import tests, run them, and report missing edge cases. Do not edit files.”

Controller · 75kTester · 25k

75,000 controller + 25,000 tester = 100,000 authorized

Actual-usage example: the controller uses 60,000 and the tester uses 12,000. The task has consumed 72,000. The tester’s 12,000 must not disappear from the total just because it returned only a short summary.

Key point: spawning is delegation. It does not mean the parent history was forked. The subagent receives the bounded context needed for its assignment.

40k + 3×20kTHREE SUBAGENTS

Example 5 · Spawn three subagents

Exact user instruction to the controller

Complete the CSV-import task within 100,000 total tokens.
Spawn exactly three read-only subagents:
- Agent A: map the existing import architecture — ceiling 20,000.
- Agent B: analyze security and data-validation risks — ceiling 20,000.
- Agent C: identify test gaps — ceiling 20,000.

Reserve 40,000 tokens for the controller to coordinate, implement, integrate, validate, and deliver.
Run only work that is independent in parallel. Wait for all three agents.
Do not allow any subagent to spawn descendants.
Aggregate actual usage across the controller and all three agents.
The sum must not exceed 100,000 tokens.

Exact task sent to Agent A

Map the current import architecture. Identify entry points, parsers, validation, persistence, error handling, and tests. Read only; do not edit. Return file paths and a concise flow. Ceiling: 20,000 tokens.

Exact task sent to Agent B

Analyze CSV-import security and validation risks: formula injection, oversized input, encoding, delimiter ambiguity, malformed rows, and authorization boundaries. Read only; do not edit. Return prioritized risks and controls. Ceiling: 20,000 tokens.

Exact task sent to Agent C

Inspect CSV-import tests and identify missing behavioral and failure cases. Run relevant tests if safe. Read only; do not edit. Return a prioritized test matrix. Ceiling: 20,000 tokens.

Required runtime action: create three child agent threads with 20,000-token allocations and retain 40,000 for the controller. Reject any fourth spawn because no allocation exists for it.

The controller coordinates the work. Subagent A maps the import code, Subagent B examines security risks, and Subagent C identifies test gaps. The controller waits for all three results, implements the change, integrates the findings, and delivers the output.

Controller · 40kA · 20kB · 20kC · 20k

40,000 controller + 20,000 A + 20,000 B + 20,000 C = 100,000 authorized

Actual-usage example: controller 31,000 + A 9,000 + B 14,000 + C 11,000 = 65,000 aggregate tokens consumed.

Key point: each subagent runs in a spawned agent thread. None of those threads should be called a thread fork unless thread/fork actually copied stored history. Every spawned agent thread needs a ceiling before execution.

90k + $10EXTERNAL TOOL

Example 6 · Use an externally metered service

Exact user instruction to the primary agent

Complete the CSV-import task within these two independent ceilings:
- Codex model tokens: 100,000 maximum.
- External document-processing service: $10 maximum.

Track the two budgets separately.
Before each external call, confirm that its maximum possible charge fits inside the remaining $10.
Do not treat external charges as Codex tokens.
Stop using the external service when its remaining spend cannot cover the next call.
Report final token usage and final external spend separately.

Exact controller rule before an external call

Preflight check:
1. Read current Codex goal usage.
2. Read external spend to date.
3. Determine the next call's maximum possible external charge.
4. Refuse the call if spend-to-date plus maximum charge exceeds $10.
5. After the call, record its actual charge in the external-spend ledger.

Required runtime action: use the Codex goal for tokens and a separate monetary ledger for the service. Both gates must pass independently.

The agent uses 90,000 Codex model tokens and calls a separate paid document-processing service. That service reports dollars, not Codex tokens.

Codex tokens · 90kExternal · $10

Token ledger: 90,000 / 100,000 · Spend ledger: $10 / separately authorized dollar cap

Key point: do not convert the $10 into imaginary Codex tokens or assume the goal tracks it. Keep separate ledgers and require both limits to pass.

The control boundary

A Codex goal is associated with a thread. That makes it useful for controlling work inside that thread, but it should not be treated as a universal meter for forks, subagent threads, or external services connected to the same larger task.

1 · AuthorizeSet an explicit objective, definition of done, and token ceiling before the task begins.
→
2 · ExecuteKeep planning, implementation, integration, and validation inside the same budgeted thread.
→
3 · StopQuery usage, stop optional work at 80%, finish the required output, and do not exceed the authorized ceiling.
Important boundary: a fork receives a new thread identity, and a subagent performs work in its own agent thread. No official source examined establishes that child or parallel-thread usage automatically rolls into the parent goal. External model calls and separately priced tools also require their own accounting.

What is known—and what is not

Documented

Goal accounting exists

Codex goal state can include a token budget, tokens used, and elapsed-time usage, and it is associated with a thread ID.

Conservative inference

Thread scope matters

Because forks receive new thread IDs, parent accounting cannot safely be assumed to include forked, spawned, or parallel execution.

Not established

Automatic descendant roll-up

The public documentation examined does not state that spawned-agent-thread or external-tool usage is automatically aggregated into the main thread’s goal.

Three workable strategies

Recommended

A · Single budgeted goal

Use the main thread for planning, inspection, execution, integration, validation, and delivery. Do not spawn subagents; monitor the goal’s remaining budget.

More administration

B · Partitioned subagent spawning

Give the main thread and every spawned agent thread explicit allocations whose sum cannot exceed the task ceiling. Record every thread’s final usage in one ledger.

Most exact

C · API request controller

Count each request, cap its output, reject unaffordable calls before sending them, and add reported usage—including retries and evaluators—to a shared ledger.

Controls that are not enough

ControlWhy it is insufficient
A YAML or Markdown ceilingIt records policy but does not mechanically stop model execution.
Tokens or requests per minuteRate limits control throughput, not the total consumption of a long task.

Account exhaustionIt is a broad backstop, not a dependable per-task allocation.
A smaller modelIt may reduce consumption, but it does not impose a hard ceiling.

Apply this to any long-running task

A token ceiling written in a prompt, plan, Markdown file, or YAML file is only a policy statement. It becomes an operational control when it is connected to runtime accounting and an explicit stop rule.

Required execution decision: bind the task to one budgeted goal in the main thread and do not spawn subagents, or explicitly allocate budget to every spawned agent thread and maintain an aggregate ledger.

Start-of-run checklist

  1. Record the objective and authorized ceiling.
  2. Create the goal before substantive model work.
  3. Choose one-thread or explicitly partitioned execution.
  4. Reserve 20% for integration, validation, correction, and delivery.
  5. Record externally metered tools separately.
  6. Include retries, evaluators, and child workers in accounting.
  7. Stop if usage cannot be retrieved.
  8. Record final usage and terminal status.
