Controlling Token Use in Long-Running Codex Tasks

How to keep a long-running task within an explicit token ceiling—without assuming that parallel agents, external tools, or account limits are automatically included.

Recommended: one budgeted goal, one Codex thread, no fan-out.

This is the clearest native way to bound a long-running task. Create the goal before substantive work, keep all model activity in the same thread, check usage during execution, and stop optional work before the hard ceiling.

  • Use the goal’s token accounting as the task-level control.
  • Stop starting optional work at 80% and reserve the remainder for integration, validation, and final delivery.
  • Track paid tools and other non-token charges separately.

Key concepts in plain language

These words describe different layers of execution. Treating them as synonyms makes token accounting unreliable.

Conversation unit

Thread

A stored conversation history with its own thread ID. Turns happen inside a thread. A new thread, a forked thread, and a subagent thread are separate accounting boundaries unless the product explicitly says otherwise.

Work unit

Turn

One user instruction and the resulting model/tool activity inside a thread. A thread normally contains multiple turns.

Budgeted objective

Goal

A persisted objective attached to one thread. Goal state can carry a token budget, tokens used, elapsed time, and completion status.

History branch

Fork

A new thread created by copying the stored history of an existing thread, optionally only through a selected turn. It begins with inherited conversational context but receives a new thread ID.

Delegated worker

Subagent

A separate agent started for a bounded task. It performs its own model and tool work in its own agent thread, then returns a result or summary to the main agent.

Workflow shape

Fan-out

A one-to-many orchestration pattern: the main agent delegates several independent tasks, often to several subagents, and later combines their results. Fan-out describes the pattern, not a specific thread API operation.

Session
The broader running interaction or orchestration container. It may contain a primary thread and spawned descendant threads. Sharing a session does not prove that those threads share one token budget.
Tool call
An operation requested by an agent, such as searching, running a command, or calling an MCP connector. A tool call is not automatically a new thread. A tool may, however, invoke external metered services whose cost is not covered by the thread’s model-token counter.
Context
The information available to the model for a turn: instructions, conversation history, selected files, tool results, and other injected material. More context can increase input-token consumption.
Aggregate ledger
A task-owned record that adds together usage from the main thread, every separately budgeted child thread, retries, evaluators, and externally metered services.

Fork ≠ fan-out. A fork is one explicit way to branch one thread’s history into another thread. Fan-out is the broader pattern of distributing work to multiple lanes. A fan-out may spawn several subagents without using thread/fork at all.

Fork example

“Take our conversation through the architecture decision and explore PostgreSQL in one branch while leaving the original intact.”

One parent history → one new branch with copied history.

Single-subagent example

“Delegate a read-only dependency scan to one specialist and return its findings here.”

One primary thread → one bounded worker thread → one returned summary.

Fan-out example

“Use separate agents for security, test coverage, and documentation, then synthesize all three.”

One controller → three worker threads → one combined result.

Does the agent fork automatically? Do not assume so. The documented App Server operation is an explicit thread/fork request. Documented local subagent behavior is triggered by a direct delegation request or applicable project/skill instruction; supported proactive modes are a separate product behavior. Spawning a subagent creates a worker thread, but that should not be casually described as “forking” unless stored parent history was actually copied through the fork operation.

The control boundary

A Codex goal is associated with a thread. That makes it useful for controlling work inside that thread, but it should not be treated as a universal meter for forks, subagent threads, or external services connected to the same larger task.

1 · AuthorizeSet an explicit objective, definition of done, and token ceiling before the task begins.
→
2 · ExecuteKeep planning, implementation, integration, and validation inside the same budgeted thread.
→
3 · StopQuery usage, stop optional work at 80%, finish the required output, and do not exceed the authorized ceiling.
Important boundary: a fork receives a new thread identity, and a subagent performs work in its own agent thread. No official source examined establishes that child or parallel-thread usage automatically rolls into the parent goal. External model calls and separately priced tools also require their own accounting.

What is known—and what is not

Documented

Goal accounting exists

Codex goal state can include a token budget, tokens used, and elapsed-time usage, and it is associated with a thread ID.

Conservative inference

Thread scope matters

Because forks receive new thread IDs, parent accounting cannot safely be assumed to include forked, spawned, or parallel execution.

Not established

Automatic fan-out roll-up

The public documentation examined does not state that subagent or external-tool token usage is automatically aggregated into a root goal.

Three workable strategies

Recommended

A · Single budgeted goal

Use one thread for planning, inspection, execution, integration, validation, and delivery. Disable fan-out and monitor the goal’s remaining budget.

More administration

B · Partitioned fan-out

Give the controller and every child explicit allocations whose sum cannot exceed the overall ceiling. Record each child’s final usage in one ledger.

Most exact

C · API request controller

Count each request, cap its output, reject unaffordable calls before sending them, and add reported usage—including retries and evaluators—to a shared ledger.

Apply this to any long-running task

A token ceiling written in a prompt, plan, Markdown file, or YAML file is only a policy statement. It becomes an operational control when it is connected to runtime accounting and an explicit stop rule.

Required execution decision: bind the task to one budgeted Codex goal and keep fan-out disabled, or execute it through a controlled API/SDK path. If child lanes are necessary, authorize each child allocation before it starts and include every lane in the aggregate ledger.

Start-of-run checklist

  1. Record the objective and authorized ceiling.
  2. Create the goal before substantive model work.
  3. Choose one-thread or explicitly partitioned execution.
  4. Reserve 20% for integration, validation, correction, and delivery.
  5. Record externally metered tools separately.
  6. Include retries, evaluators, and child workers in accounting.
  7. Stop if usage cannot be retrieved.
  8. Record final usage and terminal status.
