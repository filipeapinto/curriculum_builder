Current state: requirements only.No directory, plugin, command, or installer is in scope until the requirements and ownership model are approved.

HTML can improve human review of architecture explainers, reports, and diagrams. This document adds the necessary constraint: the project should not make “HTML everywhere” its policy. Structured graph/runtime data remains authoritative; HTML is a reader-facing derivative where visual organization improves review.

Assessment baseline

The research conclusion remains: no external skill is a complete answer for this repository’s runtime documentation. A generic HTML-artifact skill can improve presentation, but cannot by itself stop documentation drift. The eventual workflow must derive or validate operational claims against graph definitions, schemas, route policy, and run evidence.

Proposed purpose

Eventually provide a repeatable way to produce an accessible, self-contained HTML explanation of this repository’s curriculum runtime from checked repository facts. A request such as “explain the runtime,” “make a graph walkthrough,” or “prepare a release-status explainer” should result in a readable artifact whose claims point to the graph/config/schema/evidence inputs that support them.

Claude and Codex: what the eventual skill must mean

One shared skill source is feasible. Both products support an Agent Skills-style folder built around a SKILL.md instruction file and optional resources. The portable core must use only ordinary files, semantic HTML/SVG, and shell-independent instructions. It must not assume a specific browser, model, connected service, or plugin marketplace.

Draft requirements to debate

  1. Purpose-based trigger. Use the workflow only when a human needs to compare, navigate, inspect, or interact with complex information. Keep concise notes, contracts, and agent inputs in the format best suited to them.
  2. Checked factual input. Gather graph facts, schema names, route policy, run evidence, and cited paths through a deterministic extractor or an explicit validation step before presenting them.
  3. Traceable claims. Label each operational claim with a source path, version/hash where available, and a freshness or verification status.
  4. Static-first HTML. Deliver one self-contained HTML file using semantic structure. JavaScript, animation, external fonts, CDNs, and remote images are optional additions only when justified and accompanied by a readable fallback.
  5. Accessible visuals. Provide text equivalents for diagrams, do not encode meaning by color alone, preserve keyboard/focus behavior where interaction exists, and check contrast and rendered legibility.
  6. Failure paths are visible. Include retries, repair loops, blocked/unavailable outcomes, and evidence gaps whenever they are part of the documented flow; do not diagram only the happy path.
  7. Separation of roles. A diagram-design capability may be used to render a visual from an approved brief, but it must not infer authoritative runtime data or be responsible for documentation verification.
  8. Safe artifact handling. Write only to a declared documentation/output location, avoid silently overwriting accepted artifacts, and make temporary one-off editors explicitly disposable.
  9. Verification before publication. Check source links, source identifiers, missing/duplicate diagram labels, no-JavaScript readability, and the rendered artifact before calling the result current.
