SOTA Research Plan: Documenting LLM-Execution Failure

Research current mature practices for recording, reconstructing, explaining, and learning from failed or wasteful LLM execution, then determine what this repository should adopt.

1. Research question and intended decision

Primary research questionWhich mature mechanisms should this repository adopt or adapt to make failed, wasteful, or falsely successful LLM executions observable, explainable, reproducible, and useful for governing the next execution?

Intended decision: select an evidence-supported, proportionate set of repository controls for execution identity, traces, resource telemetry, provenance, durable state, retries, evaluation, incident learning, and human authority.

2. Scope and evidence boundary

IN SCOPE

External mechanisms

Standards, primary research, official implementation documentation, mature open-source implementations and tests, and documented engineering practice relevant to the research question.

IN SCOPE

Repository incident

The graph-system documentation work, related skill revisions, available artifacts, Git history, governance records, and attributed human statements.

BOUNDARY

Claims remain claims

The reported 20% weekly-usage impact remains attributed and unverified unless provider or account telemetry is supplied. Repository evidence cannot establish missing token usage, prompts, or acceptance decisions.

Excluded: generic model-quality research without execution evidence, unsourced summaries, pure marketing claims, inaccessible full text, duplicate reports, and mechanisms that cannot link observations to a run or artifact.

3. Research method

Use an evidence mapping study across the whole question, followed by focused systematic reviews of three clusters: trace/resource telemetry; provenance/durability; and evaluation/incident governance. Conduct the repository incident reconstruction independently of external conclusions, then compare the evidence streams.

External review

Freeze queries and retrieval records; deduplicate; screen; appraise by evidence class; extract mechanisms and limitations; report selection with PRISMA 2020.

Incident reconstruction

Build an evidence-linked matrix of events, actors, inputs, operations, outputs, resource evidence, status, confidence, unknowns, and competing explanations.

Comparative synthesis

Build mechanism-by-failure-mode and mechanism-by-repository-fit matrices. Separate evidence strength from repository applicability and implementation cost.

The following is the authoritative textual equivalent of the research dependency graph.

4 · CompareMap mechanisms to failures and repository fit.
5 · ChallengeIndependent reviewer tests evidence and causal language.
6 · VerifyDeterministic checks precede human acceptance.

Failed challenge returns to comparison or extraction. Failed verification returns to the responsible artifact. A material scope, method, budget, eligibility, authority, output, or acceptance change returns to $sota-plan-create as version 8.

7. Evidence selection, appraisal, and synthesis

Search and selection

  • Official standards and specifications
  • Scholarly indexes and primary research
  • Official documentation tied to inspectable implementations
  • Mature open-source source code and tests
  • Documented incident and engineering practice

Quality appraisal

  • Authority
  • Mechanism specificity
  • Inspectability and reproducibility
  • Evidence of testing or use
  • Disclosed limitations
  • Recency and stability

Required synthesis discipline

  • Synthesize within evidence class first
  • Rate evidence strength separately from applicability
  • Link recommendations to stable findings
  • Retain contradictions and missing evidence
  • State implementation cost and residual risk
