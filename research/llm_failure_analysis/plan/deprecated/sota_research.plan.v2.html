1. Method: systematic review with an engineering evidence layer

This is not an open-ended “research fan-out.” It is a protocol-led systematic literature review (SLR), adapted for software-engineering evidence and augmented by repository incident forensics. PRISMA 2020 governs transparent reporting of identification, screening, eligibility, and inclusion; Kitchenham-style software-engineering SLR practice governs protocol formation, study selection, quality assessment, extraction, and synthesis.

STREAM A · EXTERNAL

Systematic evidence review

Search standards, primary research, official documentation, mature implementations, and incident reports using a registered search and selection protocol.

STREAM B · INTERNAL

Repository case reconstruction

Reconstruct the graph-documentation incident from immutable artifacts, usage evidence, prompts, traces, logs, commits, and human testimony—with uncertainty labeled.

JOIN · SYNTHESIS

Mechanism-to-failure fit

Judge each mature mechanism against the observed failure modes and the repository’s operating constraints before proposing adoption.

Protocol principle: the review question, inclusion/exclusion rules, quality instrument, extraction form, synthesis method, and stopping/budget rules are approved before the full search begins. Deviations are versioned and justified.

2. Primary research question

RQ1 · The organizing questionWhich mature mechanisms should this repository adopt or adapt to make failed, wasteful, or falsely successful LLM executions observable, explainable, reproducible, and convertible into enforceable governance for the next run?

Operational definitions to be fixed in Phase 0

“Failure,” “wasteful,” “false success,” “observable,” “explainable,” “reproducible,” “mechanism,” and “governance” are protocol terms, not keywords. Phase 0 must define each term against repository examples before search strings or specialist roles are finalized.

Secondary questions are derived—not guessed

The preliminary map may justify secondary questions about execution records, causal reconstruction, cost control, learning, privacy, or governance. It may also show that logs and traces belong to one observability question. No secondary question is frozen before Phase 0.

Family-creation rule: do not create seven thin wrapper skills merely because seven names are listed. Phase 0 must compare cohesive one-skill, core-plus-helpers, and explicit-family architectures. A capability becomes a separate skill only if it has a stable contract, independent reuse, distinct inputs/outputs, and a testable boundary.

6. Team creation is governed, not hard-coded

V1’s eleven-agent roster was unjustified. V2 proposes no fixed research headcount. sota-team-create derives roles only after the protocol and pilot map exist.

Required team parameters

  • Approved research and secondary questions
  • Evidence domains and estimated volume
  • Required expertise and independence
  • Artifact dependencies and parallelizable work
  • Model/tool capability and cost profile
  • Maximum handoffs and fan-out
  • Conflict-of-interest and correlated-error controls

Default minimal topology

  1. One protocol/research lead
  2. One or more reviewers only when evidence volume warrants parallel screening
  3. One repository case analyst
  4. One independent challenger
  5. One synthesis owner

Roles may be combined when independence is preserved. Additional roles require a written marginal-value justification.

7. Budget and stopping rules come from preliminary evidence

A token ceiling chosen before knowing source volume is theater; an unbounded research loop is negligence. Phase 0 uses pilot measurements to construct a hybrid envelope.

Measured inputs

Candidate yield per query, duplicate rate, screening time, extraction size, model-call cost, repository volume, and unresolved-domain count.

Authorized envelope

Hard ceilings for calls, tokens, elapsed time, retries, sources, and concurrent workers; softer allocations by phase.

Stopping logic

Protocol completion, theoretical/source saturation, no-new-mechanism threshold, repeated failure fingerprint, budget threshold, or human escalation.

9. Preliminary methodological anchors

  • PRISMA 2020 statement and official flow templates — reporting the search and selection process.
  • Kitchenham and Charters, Guidelines for performing Systematic Literature Reviews in Software Engineering — protocol-led software-engineering evidence synthesis and preliminary mapping.
  • OMG BPMN 2.0.2 — standardized process-model vocabulary.
  • OpenTelemetry general semantic conventions — a preliminary research target for the later failure-observability SOTA, not a conclusion of this plan.

These sources justify the planning method and notation only. They are not the evidence base for the eventual LLM failure-analysis conclusions.

10. Approval boundary and recommended sequence

Recommendation: perfect and approve this protocol first; then use it as the requirements artifact for creating the Codex SOTA skill family. Building the family now would fossilize assumptions that Phase 0 exists to test.

Approval of this document would authorize Phase 0 only: incident reconnaissance, preliminary mapping, review-type selection, and production of the full SLR protocol, derived team, derived graph, and evidence-based budget. Full SOTA execution and skill-family implementation would each return to separate human gates.
