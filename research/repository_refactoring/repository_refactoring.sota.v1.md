# Repository refactoring: state of the art and application to Curriculum Factory

**Research date:** 15 August 2026  
**Scope:** safe repository identity changes; Python `src`-layout/package migration; large-scale codemods; dependency and reference inventories; generated-output/fixture separation; JSON Schema identifier compatibility; verification and rollback.

## Executive conclusion

The 2026 state of the art is not a single refactoring tool. It is a controlled migration system:

1. establish a machine-readable baseline and classify every discovered reference;
2. separate contract decisions from mechanical edits;
3. make small, reversible phases with explicit invariants;
4. use syntax-aware codemods for source and format-aware transforms for structured files;
5. test the installed distribution, built wheel, CLI, schemas, documentation, and a clean checkout;
6. retain compatibility where an identifier or public entry point is already a contract; and
7. remove generated material only after producer/consumer closure is proved.

For this repository, `src/curriculum_factory/` is the correct phase-one destination, but the current module boundaries should initially remain intact. The package move, internal subsystem redesign, generated-output cleanup, and remote repository rename should be distinct phases. The most important local hazards are the existing `runtime`/`tests/runtime` import-name collision, repository-root calculations derived from `__file__`, direct script commands, durable tests that read ignored `outputs/`, and schema `$id` values that encode the former identity.

## Methodology

This is a targeted evidence synthesis, not a popularity survey.

- Searches were run on 15 August 2026 for current official guidance in Python packaging, pytest, Git/GitHub, JSON Schema, and syntax-aware codemod systems.
- Primary sources were preferred: PyPA specifications/guides, Python and pytest documentation, Git and GitHub documentation, JSON Schema project documentation, and original tool documentation for LibCST and ast-grep.
- Claims were accepted only when a primary source described the relevant behavior or interface. Tool recommendations below are bounded by what those sources establish; no benchmark claim is made.
- Repository-specific recommendations were checked against the current checkout using read-only searches of `runtime/`, `tests/`, `schemas/`, policy, plans, issues, documentation, and output references. These observations are deliberately qualitative: counts and sizes go stale and must be regenerated by the execution inventory.
- “State of the art” here means the strongest currently documented engineering practice available by the research date, not the newest tool or an assertion that one workflow fits every repository.

## Findings

### 1. Inventory must be multi-layered and reproducible

A text search alone is necessary but insufficient. A reliable inventory combines:

- version-control truth: tracked, ignored, untracked, submodule, worktree, and dirty-state data;
- lexical references: names, paths, commands, URLs, User-Agent strings, CI configuration, documentation, and absolute checkout paths;
- syntax-aware Python references: imports, qualified names, string annotations, dynamic imports, entry points, mocks, and subprocess commands;
- structured references: JSON Schema `$id`/`$ref`, TOML entry points and package discovery, YAML policies, manifests, and workflow `uses:` values;
- runtime observations: imported module origins, CLI behavior, output producers, and files actually opened in representative tests/runs; and
- dependency state: declared dependencies plus the installed environment.

`pip inspect` provides a stable-versioned JSON report of installed distributions and environment metadata, so it is useful evidence but not a substitute for the repository's declared dependency inventory ([pip inspect JSON specification](https://pip.pypa.io/en/stable/reference/inspect-report/)). The inventory should record its own schema version, timestamp, repository commit, dirty state, tool versions, omissions, and collection failures. An incomplete collector must fail rather than serialize an apparently valid empty set.

The inventory also needs a classification step. A match can be a live production dependency, test-only dependency, historical record, generated artifact, public compatibility contract, or intentional exception. Blindly eliminating every old string destroys evidence and contracts.

### 2. Python `src` layout is an isolation mechanism, not cosmetic organization

PyPA defines `src` layout as putting importable code under `src/`; its central benefit is preventing the repository root and tooling files from becoming accidentally importable, thereby exposing packaging omissions and differences between editable and regular installs ([PyPA: src layout vs flat layout](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)). The current PyPA packaging tutorial uses `src/<package>/` with `pyproject.toml` and recommends a regular package with `__init__.py` for newcomers ([Packaging Python Projects](https://packaging.python.org/en/latest/tutorials/packaging-projects/)).

pytest likewise recommends installing the project, supports tests outside application code, and recommends `--import-mode=importlib` for new projects. It explicitly explains that this mode avoids changing `sys.path`, while installed-package tests can exercise either a regular or editable install ([pytest good integration practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)).

Therefore the relevant acceptance condition is not merely “files exist under `src/`.” It is:

- a declared build backend and project metadata in `pyproject.toml`;
- production packages discovered only from `src`;
- tests passing against an installed distribution without repository-root or `PYTHONPATH` assistance;
- a wheel built and installed into a clean environment, followed by import/CLI/resource smoke tests; and
- inspection of wheel/sdist contents so missing schemas, templates, or package data cannot hide behind an editable install.

Distribution and import names are related but deliberately use different normalizations: `curriculum-factory` is appropriate distribution metadata, while `curriculum_factory` is the import package. Console commands belong in `[project.scripts]`, whose values are importable object references ([PyPA `pyproject.toml` specification](https://packaging.python.org/en/latest/specifications/pyproject-toml/#entry-points); [PyPA executable scripts guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#creating-executable-scripts)).

Package-associated non-Python resources should be accessed through `importlib.resources`, which works even when resources are not ordinary files (for example, under a zip importer), rather than by assuming a fixed number of `Path(__file__).parents` hops ([Python `importlib.resources`](https://docs.python.org/3/library/importlib.resources.html)). Repository-owned policy, curricula, schemas, and runtime output may remain outside the wheel, but then their root must be an explicit configuration/input contract—not inferred from the installed module's physical location.

### 3. Preserve behavior before redesigning subsystem boundaries

A source-root migration changes import identity, packaging, invocation, resource discovery, test collection, mocks, and tooling simultaneously. Adding a domain decomposition in the same phase makes failures hard to attribute. The safe phase-one mapping is therefore behavioral: move the current production modules under `src/curriculum_factory/`, update references, and preserve their internal boundaries. Only after parity should modules move into domain subpackages, supported by coupling/import-cycle analysis and boundary tests.

This is especially important here because `tests/runtime/` is itself a Python package while production code is currently imported as `runtime`. The checkout contains historical analysis of path-order-dependent shadowing. Installed `curriculum_factory` imports plus pytest's importlib mode remove the ambiguous identity instead of preserving a fragile `sys.path` ordering trick.

### 4. Large changes should use tested, idempotent, syntax-aware codemods

Regex replacement remains suitable for exhaustively locating literal names and for narrowly constrained prose changes. It is unsafe as the primary Python refactoring engine because imports, aliases, comments, strings, qualified names, and formatting have different semantics.

LibCST parses Python while preserving formatting details and provides qualified-name/scope metadata, multi-pass codemods, parallel execution, unified-diff output, and automatic import addition/removal ([LibCST overview](https://libcst.readthedocs.io/en/latest/); [LibCST codemods](https://libcst.readthedocs.io/en/latest/codemods.html)). For this Python-heavy migration, it is the strongest default for import and qualified-name rewrites. ast-grep is a useful polyglot complement for structural search/rewrite in languages and configurations it supports; its official guidance provides rule tests with positive/negative cases and snapshot verification ([ast-grep rule testing](https://ast-grep.github.io/guide/test-rule.html); [ast-grep rewrite model](https://ast-grep.github.io/guide/project/lint-rule.html)).

Every codemod used in the migration should have:

- before/after fixtures including aliasing, multiline imports, comments, strings, and already-migrated code;
- dry-run/diff output;
- deterministic ordering and a recorded tool version;
- idempotence (`transform(transform(tree)) == transform(tree)`);
- explicit non-targets and warnings for ambiguous constructs; and
- postconditions that search for residual old references and unexpected new references.

Use parser-based TOML/JSON/YAML modification rather than regex for structured files. Human review remains mandatory for documentation semantics, external URLs, public identifiers, shell commands, and code that computes paths dynamically.

### 5. Generated output, fixtures, evidence, and caches have different contracts

The lifecycle boundary should be based on purpose, not merely whether Git currently tracks a file:

| Class | Expected treatment |
|---|---|
| Runtime output | ignored, disposable, recreated per run, contained under a configured output root |
| Test fixture | tracked, minimal by consumer closure, immutable or deterministically generated, checksummed when exact bytes matter |
| Retained evidence | tracked in an evidence/archive location, provenance and retention reason recorded |
| Cache/scratch | ignored, safe to evict, never required for correctness |
| Domain input/contract | tracked and versioned; changes receive compatibility review |

GitHub describes dependency caches as reusable material whose absence causes recreation, not correctness failure; cache hits and eviction are explicitly non-guaranteed behavior ([GitHub Actions dependency caching](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching)). The same principle applies locally: ignored outputs and caches cannot secretly be prerequisites for a fresh-clone test.

“Minimal fixture” is best defined relationally, not by an arbitrary byte cap. Each retained file needs an active consumer and a stated assertion/evidence purpose; every consumer must resolve to a retained file or deterministic generator. Exact historical bytes deserve a digest and provenance. Behavior-only tests should generate data under pytest's temporary directory facilities, not copy whole production runs ([pytest temporary paths](https://pytest.org/en/8.0.x/how-to/tmp_path.html)).

For this repository, `outputs/` remains a valid contained runtime write boundary, but current tests that read named children there violate the durable-fixture distinction. Move only consumer-closed content into tracked fixtures or evidence, generate the rest per test, then prove the full suite passes when `outputs/` has no generated children.

### 6. JSON Schema `$id` is a resolution and compatibility identifier

JSON Schema documents are identified by non-relative URIs. `$id` establishes a base URI, and `$ref` values resolve against that base; implementations may use the resulting URI to retrieve a schema from an internal registry ([JSON Schema modular schemas](https://json-schema.org/understanding-json-schema/structuring)). Consequently, an `$id` containing an old repository name is not ordinary stale branding.

The safe rule is:

- preserve the `$id` when the same schema version and semantic contract remain live;
- inventory internal and external references/registrations before any change;
- introduce the new namespace with a new schema version when the contract changes or a deliberate identifier migration is required;
- update `$ref`, registries, test fixtures, and documentation atomically; and
- where consumers may still resolve the old ID, retain an alias/registry mapping or publish an explicit compatibility transition.

The repository uses many `example.invalid/curriculum_builder/...` IDs and mostly fragment-local `$ref` values. The reserved domain signals that these are identifiers rather than fetchable production URLs, but it does not make them safe to rewrite: registries and tests may key on the exact URI. Each live schema therefore needs a recorded preserve/version/migrate decision and resolution tests.

### 7. Repository rename is an external compatibility event

GitHub redirects web and Git traffic after a repository rename and recommends updating clone remotes, but GitHub Pages URLs are exceptional. More importantly, calls to an action hosted in a renamed repository are **not** redirected; GitHub recommends a new repository/action and archiving the old one for that case. Reusing the old repository name also breaks redirects ([GitHub: renaming a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)).

Therefore, before renaming the remote, inventory:

- clone URLs, badges, Pages/custom-domain configuration, webhooks, deploy keys, package/container references, integrations, and external documentation;
- GitHub Actions `uses: owner/repository@ref` consumers, reusable workflows, and marketplace/action publication;
- branch protection, environments, secrets/variables, dependency automation, and deployment systems; and
- downstream automation or humans whose remotes should be updated.

The local checkout name and remote rename are operational completion steps after repository-internal tests pass. They are not machine-verifiable solely from a source checkout and require owner authorization.

### 8. Verification should be layered, fresh, and differential

The strongest verification matrix is broader than the existing unit suite:

1. **Static:** syntax/compile, formatter/linter/type checks, import graph/cycle policy, structured-file parsing, schema resolution, stale-reference allowlist.
2. **Codemod:** transformation fixtures, dry-run review, idempotence, and zero unexpected residuals.
3. **Package:** build wheel and sdist; inspect their file lists and metadata; install the wheel into a new environment; assert module origins come from that environment.
4. **Behavior:** unit/integration/gate tests; CLI help, invalid-input, exit-code, and representative-run parity; resource/config root behavior from outside the repository directory.
5. **Lifecycle:** run with empty `outputs/`; reject paths outside the output boundary before writes; validate fixture manifests and digests.
6. **Clean-room:** checkout the candidate commit without ignored/untracked local material, provision only documented dependencies, and repeat the release gates.
7. **Differential:** compare baseline/candidate public outputs where equivalence is intended, normalizing only explicitly nondeterministic fields.
8. **External:** after authorization, rename the remote, update `origin`, exercise clone/fetch/push and relevant integrations, and record results.

### 9. Rollback is designed through commit structure

Git worktrees allow isolated linked working trees, including disposable detached worktrees, without disturbing the main checkout ([Git worktree documentation](https://git-scm.com/docs/git-worktree.html)). Use one clean worktree for baseline capture and another for clean-room candidate verification. Do not use a worktree as a substitute for preserving the user's existing dirty changes.

Make phases independently reviewable and revertible: inventory/tooling; packaging skeleton; mechanical move/import rewrite; path/resource repair; fixture migration; stale-reference cleanup; later decomposition; external rename. Avoid mixing formatting churn or subsystem redesign into the move commit. Record the exact baseline commit and test results at each checkpoint. For merged work, `git revert` creates new commits that reverse earlier changes, preserving history ([Git revert documentation](https://git-scm.com/docs/git-revert.html)). A rollback plan must also cover non-Git state such as a remote rename, registries, Pages, secrets, or published schema identifiers.

## Recommended migration protocol for this repository

### Phase 0 — freeze decisions and collect evidence

Create a read-only, schema-versioned inventory tool. Emit JSON plus a human report. Record commit/dirty state and tool versions. Inventory all top-level directories, `runtime` imports/commands, root calculations, output producers/consumers, schema identifiers/references, identity strings, package/dependency state, CI/external repository references, and absolute paths. Treat unresolved collection as failure.

Capture a behavioral baseline: tests/gates, documented commands, import origins, CLI exit codes, representative artifacts or semantic digests, and output-containment behavior. Record known failures separately; do not silently turn them into the new baseline.

### Phase 1 — establish packaging without redesign

Add `pyproject.toml`, build metadata, `src/curriculum_factory/__init__.py`, and explicit console entry points. Move production files while preserving current internal module boundaries. Use a tested LibCST codemod for Python imports and format-aware edits elsewhere. Update mocks and subprocess commands. Configure tests to use installed `curriculum_factory`, preferably pytest importlib mode; do not add repository-root path injection to make failures disappear.

Replace production `__file__` parent traversal with either package-resource access or an explicit repository/data-root input, depending on whether the target is shipped with the distribution. Verify from a current working directory outside the checkout.

### Phase 2 — separate durable inputs from generated runs

Trace producers and consumers of each `outputs/` child. Generate behavior-only data under temporary test directories. Move exact bytes only when active assertions or evidence citations require them, with a manifest containing path, digest, source, consumer, assertion, and reproduction policy. Move research evidence to an evidence/archive location. Then test with an empty generated-output boundary.

### Phase 3 — compatibility and reference closure

Apply the explicit schema-ID decision rule. Resolve every live `$ref` using the same registry/loading mechanism as production. Classify remaining legacy identity strings rather than demanding an indiscriminate zero count. Each allowed remainder needs location, consumer, rationale, owner, and removal condition.

### Phase 4 — clean-room release verification

Build and inspect sdist/wheel; install the wheel in a fresh environment; run imports, CLI, schemas, and full tests without ignored/untracked files. Rerun the inventory and compare it to the planned target. Verify the inventory itself is read-only by checking working-tree state before and after.

### Phase 5 — optional architecture work and external rename

Only after phase-one parity should a separate proposal split modules into domain subpackages, supported by cohesion, dependency direction, cycle, ownership, and focused-test evidence. After all local gates pass, obtain authorization for the GitHub and checkout rename, execute the external checklist, update downstream consumers/remotes, and record observed results.

## Concrete acceptance evidence

The final migration report should include, at minimum:

- inventory schema/version, timestamp, commit, dirty state, tool versions, and unresolved items;
- old-to-new identity/import/entry-point mappings and intentional exceptions;
- wheel and sdist file inventories plus clean-environment install evidence;
- installed module origins proving no root-path shadowing;
- test/gate/CLI results and baseline differential results;
- schema registry and `$id`/`$ref` resolution results;
- per-output disposition and fixture consumer-closure validation;
- proof that tests pass with empty generated outputs and outside the repository CWD;
- clean-checkout result with no dependence on ignored/untracked files; and
- phase commits, rollback procedure, and pending/observed external operations.
