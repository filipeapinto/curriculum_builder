Can Codex Invoke Claude for an Independent QA Gate?

A state-of-the-art research plan for determining whether a Codex-led intensive workflow can obtain a bounded, auditable, genuinely separate Claude verdict without weakening sandbox, provenance, or human-control guarantees.

1. Question and intended decision

Primary research questionCan Codex safely and reliably invoke Claude as a separate QA authority for repository artifacts, and, if so, which invocation architecture and assurance controls produce a high-quality, auditable gate during intensive Codex prompting?

The intended decision is one of four outcomes: adopt a supported design; pilot with constraints; defer pending missing capability or evidence; or reject cross-vendor invocation and use a same-provider formal gate. “The claude executable is present” is local planning context, not proof of support, independence, reliability, or fitness.

DECISION A

Invocation feasibility

Determine supported local CLI, SDK/API, subprocess, MCP/plugin, or hosted-review routes and their authentication and session semantics.

DECISION B

Assurance strength

Determine whether separation of vendor/model/session/prompt/state materially improves review and how it can be measured.

DECISION C

Operational design

Specify the minimal secure protocol, evidence record, failure states, cost controls, and fallback behavior worth implementing.

2. Scope, exclusions, assumptions, and evidence boundary

In scope

  • Codex initiating a non-interactive Claude review of versioned local artifacts and explicit criteria.
  • Claude CLI, documented API/SDK, subprocess and supported integration mechanisms.
  • Structured verdicts; identity/session witnesses; immutable inputs; least-privilege read or isolated execution; retries, timeouts, spend, and non-convergence.
  • Comparison against strong same-model/same-vendor formal gates so a second vendor is not presumed necessary.
  • Code, document, research, and configuration artifacts, with modality-specific limitations.

Out of scope

  • Implementing or operating a production gate during this research.
  • Bypassing workspace policy, authentication, subscriptions, terms, approval controls, or sandbox restrictions.
  • Claiming cryptographic independence against an adversary who controls the host.
  • Unbounded autonomous fix/review loops or allowing the reviewer to edit the authoritative artifact or QA record.
  • Treating vendor diversity alone as evidence of correctness.

Assumptions to test: a local Claude Code CLI currently exists and advertises non-interactive output, JSON Schema, session, permission, tool, and budget controls; those observed help strings may change and do not establish runtime access. The existing .claude/skills/qa-gate-codex-run/ is evidence of a Claude→Codex design and reusable protocol concepts, but its Claude-specific Codex-plugin bridge is not evidence for the reverse route.

Evidence boundary: execution may inspect repository artifacts, installed-tool metadata, official vendor documentation, primary specifications/research, and bounded empirical pilot outputs created under this protocol. Credentials, private prompt histories outside the approved test corpus, user home-session contents, and production/customer data are excluded. Local observations and external claims remain separately labeled.

4. Research method

Research questions

  1. Which officially supported mechanisms permit a Codex-controlled process to request and receive a Claude result?
  2. What authentication, licensing, rate, sandbox, prompt-loading, persistence, telemetry, and billing semantics attach to each?
  3. Can the route enforce a stable artifact/criteria binding, structured verdict, tool restrictions, timeout, cost ceiling, and durable witness?
  4. What does empirical evidence say about reviewer independence and error correlation across same-model, same-vendor, and cross-vendor gates?
  5. Which architecture has the best assurance/cost/latency/maintenance tradeoff, and when must the gate return QA_ERROR rather than pass or fail?

Search and evidence procedure

After approval, `$sota-evidence-review` will search official Anthropic and OpenAI/Codex documentation, primary API/CLI specifications, peer-reviewed or original evaluation research, and mature open-source implementations with tests. Query families will combine: Claude Code CLI/API/SDK non-interactive structured output JSON schema permissions tools session resume cost budget; Codex subprocess external model MCP agent interoperability; LLM-as-judge self-evaluation bias correlated error cross-model debate reviewer independence; and AI code review gate provenance tamper evidence sandbox. Exact queries, sources, dates, result counts, and retrieval URLs are logged before screening.

Eligibility

  • Primary official documentation current at retrieval, standards/specifications, original empirical studies, or implementation repositories with inspectable code/tests.
  • Directly addresses one research question and exposes enough method/version context to appraise.
  • English; no date floor for foundational judge-reliability work, but current integration claims must be verified against current official sources.

Exclusions

  • SEO summaries, unsupported tutorials, marketing claims without technical evidence, duplicate reports, inaccessible claims, or generic “multi-agent” discussion without gate relevance.
  • Results that require prohibited credential access or destructive testing.
  • Benchmarks whose reference answers, sampling, or judge setup cannot be determined.

Appraisal, extraction, and synthesis

Each included item receives source-class-specific appraisal: authority/version/recency for documentation; design/sample/reference standard/reproducibility/conflicts for studies; maturity/tests/security posture/maintenance for implementations. Extraction uses stable IDs for supported route, constraints, security properties, structured-output semantics, session/provenance features, measured quality, cost/latency, failure modes, and applicability. Claims retain source IDs and confidence; contradictions remain visible. Synthesis uses an evidence matrix and a weighted decision table whose weights are human-approved before scoring: assurance 30%, security 25%, operational reliability 20%, evidence strength 15%, and cost/maintenance 10%. Sensitivity analysis varies each weight ±10 percentage points; no recommendation rests only on the weighted total.

Empirical benchmark, conditional on second approval

Compare at least three conditions on the same frozen, versioned corpus: (1) Codex formal self-family gate with fresh context and deterministic checks; (2) independent Codex session/model-family gate; (3) Claude cross-vendor gate through each feasible route. Seeded artifacts include known blocker, major, non-defect trap, ambiguous criterion, grounding conflict, malicious instruction in artifact, schema violation, timeout, and unavailable-reviewer cases. Human-adjudicated labels are the reference. Measure blocker recall, false-block rate, verdict/schema validity, evidence traceability, repeatability, latency, cost, and fail-state correctness. The review agent never fixes artifacts.

9. Feasibility, security, and assurance gates

Before any Claude call

  • Officially supported route and compatible license/auth identified.
  • Owner approves cost and credential use.
  • Synthetic corpus only; secret/canary scan clean.
  • Reviewer tool allowlist is empty/read-only unless isolated execution is essential.
  • Working directory is an isolated copy outside authoritative QA records.

Required protocol properties

  • Artifact, criteria, grounds, schema, prompt, model and settings bound by digest.
  • Machine-validated verdict with PASS/FAIL/ERROR separated.
  • Session/turn/process witness and exact request/response receipt.
  • Reviewer cannot author fixes, move versions, or write the verdict ledger.
  • Unavailable, malformed, timed-out, over-budget, or unverifiable review fails closed as QA_ERROR.

Threats to validity

  • Shared training data and prompts may correlate errors despite vendor diversity.
  • CLI presence may hide unavailable auth or unsupported automation.
  • Artifact prompt injection may influence reviewer.
  • Human labels and seeded corpus may bias measured quality.
  • Vendor/version drift can invalidate implementation findings.

Mitigations include blinded condition labels, frozen prompts, negative controls, prompt-injection cases, dual human adjudication for a stratified sample, exact version capture, repeated trials, sensitivity analysis, and an expiry/revalidation recommendation. The study must distinguish process independence (separate invocation/context), model-family diversity, vendor diversity, and host integrity; none implies the others.

11. Acceptance rules

A recommendation is acceptable only if all of the following hold:

  1. Every research question has evidence or an explicit, decision-relevant unknown; current integration claims are supported by current official sources.
  2. At least one same-model formal gate and every feasible Claude route are compared under identical frozen criteria, or the report explains why safe benchmarking was prohibited.
  3. No route is labeled “independent” without separate ratings for process, context, model family, vendor, and host integrity.
  4. Security gates, PASS/FAIL/ERROR semantics, immutable artifact binding, structured output, cost/timeout limits, and fail-closed behavior are specified and tested where feasible.
  5. Reported benchmark metrics link to raw run IDs and human reference labels; uncertainty and corpus limits are explicit.
  6. All blocker/major challenge findings are resolved or surfaced to the human owner; deterministic verification passes with no missing required artifact or silent check failure.
  7. The recommendation states support horizon/revalidation triggers and does not require undocumented internals. If no route meets the bar, reject/defer is a successful research outcome.
