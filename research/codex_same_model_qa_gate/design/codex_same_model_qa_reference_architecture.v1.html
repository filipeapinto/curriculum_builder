Architecture contract and evidence status

No production authorization, selection, or superiority claim. This architecture is only an unexecuted candidate pattern selected for future testing by coverage rationale: it lists more named control categories on paper. The evaluation has zero operations, corpus labels/oracles are not independently adjudicated, and telemetry feasibility is unproven. See challenge dispositions and the bounded review.

NON-WAIVABLE BASE

Observable checks first

Every material criterion is mapped to deterministic, executable, inspectable, model-reviewed, or human-authority evidence. Applicable deterministic failure cannot be waived.

BOUNDED MODEL ROLE

Evidence, not trust root

Same-model sessions inspect untrusted artifacts in frozen contexts and return criterion-linked evidence. They may fail or abstain; any pass is bounded by tier and calibration.

EXPLICIT AUTHORITY

Risk owns the route

Disagreement, insufficiency, material injection, unavailable execution, provenance gaps, or high consequences route to the named human or external authority. Silence never approves.

Invariants

  1. Artifact, criteria, configuration, evidence, and verdict identities are versioned and digest-bound.
  2. Artifact content is data, not instruction; generated checks run only in the bounded execution zone.
  3. A deterministic failure yields FAIL; repair creates a new lineage and a new run.
  4. Missing, unparseable, misbound, or incomplete raw data yields INVALID, never pass.
  5. Unresolved material uncertainty yields ABSTAIN and an authority route.
  6. Fresh contexts and samples are “procedurally separated,” never “independent” without a qualifier.
  7. Hashes establish equality to recorded bytes; only an independently administered trust service may add separate provenance authority, and neither establishes semantic truth.
  8. Budget and telemetry interlocks execute before scheduling, not after a call.

Textual equivalent: a criteria owner freezes the artifact, acceptance criteria, assurance tier, and configuration. Preflight verifies all identities, accounting, sandbox, and authority prerequisites. Applicable deterministic checks run before model review; a failure terminates that lineage. Only unresolved semantic criteria reach procedurally separated same-model sessions. A deterministic aggregator applies frozen rules. Pass is merely tier-eligible; fail blocks; abstain routes to authority; invalid repairs infrastructure and reruns without entering effectiveness denominators. Audit verification checks the complete record. Human acceptance and production release remain separate decisions.

Required logical schemas

These are technology-neutral field contracts. Concrete serialization may vary, but no field may be silently omitted when applicable. Every record declares schema, schema_version, record_id, created_at_utc, responsible_role, and run_id.

CRITERIA

Criterion record

  • criterion_id, text, rationale, materiality/severity
  • artifact/tier/policy IDs and digests
  • oracle type: deterministic, executable, inspectable, model-evidence, human
  • expected evidence kind and acceptable locators
  • pass/fail/abstain rule; applicability predicate
  • owner, waiver policy (never for deterministic result), version lineage
FINDING

Finding record

  • finding_id, criterion ID, category, severity
  • statement, observed/attributed/inferred classification
  • evidence IDs and exact locators; evidence digest
  • author role/session, confidence, status
  • contradiction/alternative/unknown fields
  • disposition, disposer authority, superseding finding
VERDICT

Verdict record

  • operation/case/variant/repeat/run IDs
  • artifact, criteria, prompt, tool/config digests
  • model/version/effort/session/turn/seed when applicable
  • pass|fail|abstain|invalid; finding/evidence IDs
  • start/end UTC, calls, input/output tokens, cost, tool transcript/raw/scorer digests
  • aggregation and authority state; schema-validation result
EVIDENCE

Evidence record

  • evidence_id, criterion/finding IDs, kind
  • source path/URL, locator, observed value, command/tool
  • source/tool/version/input/output digests and exit state
  • raw vs derived classification and transformation
  • access boundary, redactions, uncertainty, limitations
  • supersession rather than overwrite
LINEAGE

Lineage record

  • artifact ID/version/digest and parent digest
  • criteria, grounding, configuration, scorer, policy digests
  • creator identity/session and UTC
  • chain predecessor/event type and verification state
  • optional signer/subject/attestation/policy fields
  • explicit assurance class: local change detection vs external provenance
ABSTENTION

Abstention/escalation record

  • abstention_id, verdict and unmet criterion IDs
  • reason: insufficient, contradictory, unavailable execution, disagreement, risk, budget, provenance
  • attempted evidence and unavailable evidence
  • risk/consequence tier and named authority
  • packet digest, response target, timeout behavior
  • human disposition and rationale; no automatic approval
BUDGET / EVENT

Accounting and event record

  • operation/session/turn/model IDs; purpose and status
  • calls, tokens in/out, cost, start/end, retries
  • warning/hard-stop state before and after scheduling
  • changed retry condition and original operation
  • unavailable-measure route and authority event
  • append-only sequence and prior-event digest
CHALLENGE / ACCEPTANCE

Decision record

  • challenge or decision ID and targeted finding/recommendation
  • accepted, corrected, rejected-with-reason, or unresolved
  • materiality: false pass, sufficiency, security, feasibility, assurance
  • responsible role and evidence links
  • verification result and human acceptance state
  • implementation authority as a separate explicit field

Adoption gates

Adoption is a later human decision. It is prohibited until every gate below is evidenced; passing them authorizes only the scope stated by the human owner.

  1. Accounting gate: BLK-CSMQG-EVAL-001 is closed with approved, pre-scheduling call/token/cost/session telemetry.
  2. Feasibility gate: a concrete telemetry source and interlock pass PT-CSMQG-016, or an approved revised protocol records infeasibility.
  3. Oracle gate: independent corpus-label/oracle QA passes PT-CSMQG-015 before any comparative operation.
  4. Evaluation gate: all six variants receive reproducible raw records and deterministic scoring; false-pass, false-block, abstention, reproducibility, evidence quality, coverage/mutation, latency, resources, attack surface, and escalation are reported with valid denominators and uncertainty.
  5. Disqualifier gate: candidate cannot waive deterministic failure, emit unverifiable verdicts, lack authority routing, exceed budgets, expose labels, or violate sandbox policy.
  6. Threshold gate: the human owner predeclares tier-specific acceptable false-pass/false-block/abstention and operational thresholds; the 60-case design is not used for an unpowered close-winner claim.
  7. Local gap gate: source-derived requirements for schema, grounding, postmortem witness, live transport/resume, sandbox, plugin/model identity, and declared-eval behavior receive live proving records.
  8. Baseline/human gate: deterministic-plus-human/shadow alternatives and human workload, capacity, consistency, timeout, and decision quality are measured or explicitly justified.
  9. Test-spec gate: every PT concept satisfies PT-CSMQG-018 before its result can support adoption.
  10. Evidence gate: bounded-review and six access gaps are expanded or explicitly accepted; no unsupported completeness claim remains.
  11. Challenge gate: every procedurally separate challenge is dispositioned; unresolved material false-pass, sufficiency, security, feasibility, or assurance issues block. CH-CSMQG-003, -005, -007, and -010 are currently unresolved.
  12. Verification gate: required files, IDs, counts, links, schemas, rendering, integrity, budget, and challenge dispositions pass deterministic verification.
  13. Human gate: the repository owner explicitly accepts residual risk, tier scope, response capacity, adoption stage, and rollback authority.
  14. Staged pilot: shadow mode precedes enforcement; decisions are compared to the current human/deterministic process without production authority.

Rollback contract

Immediate triggers

  • Any false pass above the owner’s predeclared tier threshold, or any critical seeded/real fault passed.
  • Deterministic failure waived or prior pass reused after artifact/criteria change.
  • Telemetry, raw records, scorer binding, or budget accounting incomplete.
  • Prompt injection, label leakage, sandbox escape, secret/network/host exposure.
  • Model/version/effort drift or material deviation without approval.
  • Human escalation timeout treated as approval.
  • Unresolved material challenge, failed verification, or provenance breach.

Rollback actions

  1. Disable model-derived pass authority and return to the last verified deterministic + human process.
  2. Quarantine affected gate versions, decisions, artifacts, credentials, and evidence; preserve records append-only.
  3. Identify the first affected lineage and invalidate downstream pass applicability.
  4. Notify the repository owner and security/domain authority where relevant.
  5. Re-run affected artifacts under the last accepted policy or require manual review.
  6. Perform root-cause analysis; add a proving test and versioned remediation.
  7. Resume only after challenge, verification, and explicit human reauthorization.

Recovery objective: rollback is fail-safe, not evidence erasure. The system preserves the failed gate’s raw records and makes affected decisions visible. Re-adoption begins in shadow mode and cannot silently inherit the prior acceptance.
