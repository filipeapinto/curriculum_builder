curriculum_factory · implementation decision review

Should we build the graph-system documentation skill family?

The proposed capability would inspect an existing graph-based LLM system and produce trustworthy architecture and operations documentation for designers, reviewers, and operators.

Decision under reviewWhether the current proposed implementation still matches that original capability—and merits the cost of building it.

The concern arose after repeated Codex and Claude revisions made the design substantially more elaborate than the initiating reader outcome.

01 · The initiative

What is being considered for implementation

Inside curriculum_factory, the create_system_doc initiative explores a reusable AI-assisted capability for documenting complex graph-based LLM systems. Those systems may contain prompts, model-selected routes, tools, state schemas, external services, deployment infrastructure, security controls, and operational recovery procedures. Understanding them currently requires reading many technical sources.

THE PROBLEM

System knowledge is fragmented

Architecture, code, prompts, schemas, policy, deployment configuration, traces, and runbooks each contain only part of the operating picture.

THE PROPOSED CAPABILITY

Evidence-driven documentation creation

An AI-assisted workflow inspects permitted sources, separates observed facts from inference and unknowns, and creates an integrated guide.

THE HUMAN VALUE

Faster trustworthy understanding

A designer, reviewer, or authorized operator can understand architecture, deployment, security, behavior, and recovery without reconstructing the system from scratch.

Repository location: plans_internal/create_system_doc/. The folder contains the evolving specification, artifact schemas, conformance fixtures, and deprecated predecessor versions.
02 · Desired outcome

What should exist after the capability runs

The earliest specification frames success primarily through the reader: produce engaging, accurate architecture and operations documentation for graph-based LLM systems. The reader should understand how the system is built, deployed, secured, observed, and operated without first reading its source specifications.

SOURCE SYSTEM

Evidence distributed across the repository

Prompts, code, state models, configuration, infrastructure, policies, tests, traces, and operational records.

→
DOCUMENTATION CAPABILITY

Inspect, verify, organize, explain

Determine what is declared, observed, inferred, conflicting, stale, unavailable, restricted, or unknown.

→
READER DELIVERABLE

Architecture and operations guide

System boundary, graph behavior, interfaces, data, deployment, security, configuration, observability, operation, failure, and recovery.

Earliest formal articulation: create_system_doc specification v1. This is the baseline outcome against which later implementation machinery must be understood.
03 · The implementation problem

A reader outcome does not specify how to build the capability

To make the outcome implementable, the project had to answer real design questions: How is evidence collected? Who decides scope? How are claims traced? What happens when sources conflict? How are diagrams generated? When may the workflow write or publish? How are updates performed safely? What artifacts allow one stage to verify another?

The central review question is therefore not “should there be design detail?” It is whether the particular answers accumulated in the current design remain proportional to, and authorized by, the desired capability.
04 · How the design evolved

Eleven versions progressively answered those design questions

v1
Reader-facing documentation standard

Defines architecture, deployment, security, runtime contracts, visuals, operations, and quality. It is model-agnostic and keeps source evidence authoritative.

v2
A staged skill family is introduced

Adds goal definition, evidence inventory, structured artifacts, stable identifiers, content addressing, and pipeline traceability; positions the family alongside general graph-doc-* production skills.

v3–v4
Standalone conformance becomes possible

Adds run configuration, adapter/interoperability rules, schemas, terminal states, and explicit conformance procedures.

v5
The workflow consolidates into three skills

Plan, create, and update become the explicit architecture. The plan stage absorbs documentation-goal behavior and requires human approval.

v6–v9
Artifact and rendering controls harden

Schemas and fixtures evolve; provenance, repair, publication, verification, and graph visualization become increasingly repository-specific.

v10–v11
The current contract stabilizes

The latest iterations refine schema, review-state, fixture lookup, and rendering verification rather than redefining the reader outcome.

What the history reveals: the important transformation is from “produce this trustworthy guide” to “build this particular three-skill artifact system.” The version files show the transformation. They do not contain the full human/agent conversation that explains whether every architectural commitment was explicitly chosen.

06 · Why the implementation was paused

The design became ready before owner comprehension did

After repeated Codex and Claude generation and reciprocal review, the current specification became detailed enough to implement. At the same time, the owner reported no longer holding a complete mental model of it and feared spending time and money building something different from the initial intent.

1

Recognition problem

Does the owner recognize the three-skill artifact system as the capability they wanted—or only the reader-facing outcome?

2

Authorization problem

Which later commitments were deliberate owner choices, and which were reasonable agent proposals that became inherited premises?

3

Investment problem

Is current confidence sufficient to fund implementation, or should the project buy cheaper information first?

This is the trigger: not “version 11 exists,” but “an implementation-ready architecture exists without a matching owner-level mental model and authorization record.”

08 · Reasoning

Why a bounded review precedes implementation

  1. The project addresses a real documentation problem and has a clear reader-facing value proposition.
  2. Implementation requires design choices; the specification series legitimately became more concrete.
  3. Those choices accumulated into a substantial three-skill product with schemas, fixtures, local rendering, approvals, and maintenance obligations.
  4. The owner currently recognizes the original problem but cannot confidently recognize or authorize the complete accumulated solution.
  5. Research shows that repeated LLM review does not by itself resolve that gap, even when it improves internal rigor.
  6. The current design has strong controls after it is accepted, but those controls do not establish that it should be accepted.
  7. A focused comparison of intended capability and current product is cheaper and more reversible than implementation.
Bounded conclusion: pause the full build. Do not conclude that the current specification is wrong, and do not discard it.
09 · Decision procedure

Compare capability intent to implementation consequences

01 · INITIAL CAPABILITY

Reconstruct the problem and outcome

Use original prompts if recoverable plus v1. Describe users, source evidence, desired guide, quality, and non-goals.
02 · PRESENT INTENT

Fresh owner statement

Define acceptable workflow complexity, dependencies, maintenance, cost, authority, and output—before showing the current design.
03 · CURRENT PRODUCT

Translate the active specification

List actual skills, files, schemas, fixtures, renderer, approvals, writes, recurring work, and implementation cost.
04 · DISPOSITION

Decide the deltas

Explicitly adopt, reject, replace, or defer each material difference; then approve one reversible slice or redesign.
FindingAction
The current product matches initial and present intent.Run a budget-capped vertical implementation slice.
The documentation outcome matches, but the machinery does not.Retain the documentation standard and redesign the workflow.
The desired outcome intentionally changed.Record the present intent as authority and reassess the design against it.
The design contains unrecognized scope or dependencies.Demote them to proposals and compare lower-cost alternatives.
The expected value no longer supports implementation.Stop without treating prior iteration effort as justification to continue.
10 · Case conclusion

The decision in one paragraph

The project is considering a reusable AI-assisted capability that turns fragmented evidence about graph-based LLM systems into trustworthy architecture and operations documentation. Eleven specification versions transformed that reader-facing goal into a concrete three-skill repository product. The current endpoint is detailed and strongly controlled, but the owner cannot presently verify that its accumulated architecture still represents the intended capability. Because recursive LLM review and co-evolving tests do not independently establish intent fidelity, the appropriate next step is a bounded comparison of initial outcome, present owner intent, and current implementation consequences before authorizing a build.
