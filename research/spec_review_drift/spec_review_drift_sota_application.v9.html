Documentation proportionality review · application v9

Are we spending more effort controlling the document than creating it?

The project is a documentation tool. Its safeguards should improve the resulting guide without consuming most of the tokens, time, and human attention.

Revised conclusionThe full v11 control system is not proportionate as the mandatory default for every documentation job.

Keep its strongest controls, but activate the expensive ones only when the document’s risk and audience justify them.

01 · The job to be done

Create useful documentation—not another operational system

The tool should inspect a graph-based AI system and produce a trustworthy architecture and operations guide. Some structure is necessary because the source material is complex and AI-generated documents can contain mistakes. But the documentation workflow is not the system being documented. Its internal governance should remain smaller than the evidence and deliverable it exists to process.

Value-producing work

What readers actually need

  • Inspect relevant sources.
  • Explain architecture and behavior.
  • Mark facts, uncertainty, and conflicts.
  • Create useful diagrams.
  • Check accuracy and readability.
  • Update the guide when the system changes.
vs.
Control-plane work

What v11 additionally requires

  • Three skill-specific artifact lifecycles.
  • Canonical digest computation.
  • Large structured plan/build/update records.
  • Claim and view mappings.
  • Graph manifests and render records.
  • Multiple approval, issue, gate, and publication states.
02 · Observable static burden

The contract is already large before any system evidence is loaded

Together, the current specification, schema, and fixtures contain about 45,000 characters before the workflow reads a repository, records a source, creates a claim, or writes documentation. Loading all of that verbatim would be roughly on the order of ten thousand-plus tokens, depending on the tokenizer. A real run would then add source evidence and potentially large plan, build, update, claim, graph, issue, and verification arrays.

Important limit: this is not a measured per-run token bill. Implementations can load references selectively and use deterministic code for validation. The static size nevertheless demonstrates that the mandatory contract surface is substantial and deserves an explicit token/cost design.

05 · Proposed assurance profiles

Match documentation controls to documentation risk

The research supports proportional controls, but the exact profiles below are a design proposal to validate. They are not an established standard.

CORE · DEFAULT

Ordinary internal documentation

  • One reusable skill with internal plan, create, and update stages—or equivalent orchestration.
  • Compact run header.
  • Source register.
  • Section-level evidence labels.
  • Useful diagrams only.
  • Automated links, secret, and rendering checks.
  • Short verification summary.
ASSURED · OPT-IN

Shared operational or design-review documentation

  • Persisted approved plan.
  • Important-claim traceability.
  • Change-impact record.
  • Named reader scenarios.
  • Human approval before overwrite/publish.
  • Visual review for critical diagrams.
  • Structured issues and accepted gaps.
MAXIMUM · EXCEPTION

Sensitive, regulated, or high-consequence documentation

  • Full claim-level evidence.
  • Canonical artifacts and digests.
  • Strict disclosure approval.
  • Full conformance fixture suite.
  • Independent review lanes.
  • Complete render and publication records.
  • Current v11-style workflow where justified.
Key change: v11’s controls become a maximum assurance capability rather than the unavoidable cost of every documentation run.
06 · Evidence-derived recommendation

Prototype the default profile before implementing the full control plane

  1. Preserve v11. It is valuable as a comprehensive assurance specification and source of controls.
  2. Do not implement every v11 artifact as mandatory for every run. The static contract and potentially unbounded record arrays create material token and maintenance overhead.
  3. Define a compact default profile. Keep evidence honesty, source freshness, security, bounded retries, rendering checks, and publish approval.
  4. Make higher assurance explicit. Activate claim-level traceability, full artifact digests, reader acceptance records, and extensive fixtures when audience or consequence requires them.
  5. Use deterministic code for bookkeeping. Digests, schema validation, dependency lookup, counters, secret scanning, and file comparisons should not consume model reasoning tokens.
  6. Measure one real run. Record tokens spent on source understanding, document creation, validation, and governance separately. Adjust the profiles from observed value and cost.
Final answer: yes, the current mandatory design is a token beast for ordinary documentation. The research supports a simpler effective default and bounded context—not removing assurance. Keep the full system as an opt-in high-assurance mode until real measurements justify making more of it standard.
