01 · What is being evaluated

A reusable tool for documenting graph-based AI systems

The project owner intentionally chose to build a reusable documentation capability that can inspect different graph-based AI systems and create trustworthy architecture and operations guides. That product decision is not under review. The current technical proposal—create_system_doc specification version 11—implements the idea using three skills, structured JSON records, evidence and claim tracking, a graph renderer, automated checks, and human approvals.

Question evaluated here: which parts of the current technical proposal are supported by the research, which are only partially supported, and which require project-specific evidence before implementation?
02 · Research claim register

The reusable findings used in this application

These IDs make the application auditable. Each claim is summarized from the SOTA report and linked to its underlying evidence.

R-01

Repeated AI revision is not automatically reliable

Repeated model-mediated transformation can improve an artifact or distort it. Fidelity must be checked against evidence outside the revision loop.

Telephone-game study · iterative information distortion · counterevidence: Self-Refine

R-02

AI reviewers are not necessarily independent

Models may share errors, conform to prior views, or favor related model outputs. Reviewer count alone is not confidence.

correlated errors · persona inconstancy · preference leakage

R-03

Tests validate only what they encode

A grader or fixture derived from the current design can confirm internal consistency while missing a displaced objective or broken task.

OpenAI coding-eval audit · judge position bias

R-04

External evidence improves correction

Self-review becomes more reliable when critics use objective execution, grounded sources, held-out examples, or expert labels.

TACL self-correction review · external-feedback evidence

R-05

Independent-first review reduces contamination

Reviewers should form findings before seeing other verdicts, authorship, or favored conclusions; disagreement should remain visible.

independent adjudication example · conformity evidence

R-06

Bound actions and iteration

Permissions, approvals, budgets, stopping rules, and reversible execution reduce the consequence of mistakes during uncertain agent work.

GitHub hooks · OpenAI human approval · Anthropic agent patterns

R-07

Preserve versions and provenance

Original evidence, interpretations, decisions, outputs, and changes should remain distinguishable and reconstructable.

NIST lineage guidance · structured handoffs

R-08

Long context and summaries can lose influence or detail

Important information may remain present but become less influential; compaction is a lossy transformation whose target matters.

context engineering · long-context evidence

R-09

No research establishes one ideal architecture

The evidence supports layered controls, not a universal number of agents, files, schemas, approvals, or workflow stages.

architecture depends on task structure · debate boundary conditions

04 · Gaps derived from the matrix

Only four recommendations follow from the mapped evidence

GAP 1

Preserve the owner’s request outside the AI revision loop

Create a read-only source containing the intended users, outcome, genericity decision, non-goals, and material constraints. Plans may interpret it but may not silently replace it.

Trace: R-01 + R-07 + R-08 → v11 plan/request handling is not explicitly protected from transformation.
GAP 2

Add held-out real-world scenarios

Keep the existing conformance fixtures. Add scenarios sourced independently from the current specification that test whether readers receive accurate, useful documentation across different graph systems.

Trace: R-03 + R-04 → current fixtures prove contract behavior but not independent user value.
GAP 3

Independently review material specification changes

Have reviewers first compare a proposed change with the protected owner decisions and held-out scenarios without seeing prior reviewer verdicts. Preserve disagreements for human disposition.

Trace: R-02 + R-05 → reciprocal review is not automatically independent.
GAP 4

Validate architecture choices empirically

Test the current three-skill design, schema, and renderer interface on representative systems. The purpose is to establish their value—not to prove that a simpler design is preferable.

Trace: R-09 → research does not determine workflow count, schema size, or backend choice.

06 · Evidence-derived conclusion

What should happen next

  1. Keep v11 as the leading implementation candidate. It already contains several controls directly aligned with the research.
  2. Do not infer validity from repeated Codex/Claude review. Reassess material choices against protected owner decisions and independent scenarios.
  3. Add the four mapped controls: protected intent source, held-out scenarios, independent-first change review, and empirical architecture validation.
  4. Run bounded trials of the current design. Use real systems to measure accuracy, reader usefulness, portability, cost, and maintenance.
  5. Change v11 only where those trials produce evidence. The result may be simpler, equally complex, or more complex; the SOTA does not predetermine the answer.
Final recommendation: validate and strengthen v11 using the mapped research controls. Do not replace it with a simpler specification merely because it appears complex.
