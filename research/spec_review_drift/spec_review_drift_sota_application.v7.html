Should we build this AI documentation tool?

The tool would study a complex AI system and create a clear guide explaining how that system works, how it is deployed, how it is secured, and how people operate it.

Short answerThe idea is sound. The current design may be more complicated and less portable than necessary.

Before building everything, test the design on two real examples and confirm which parts genuinely improve the result.

01 · The basic idea

Turn scattered technical information into one trustworthy guide

Modern AI systems can be difficult to understand. Their behavior may be spread across prompts, computer code, routing rules, tools, data structures, external services, security policies, deployment files, tests, and system logs. A person may have to inspect all of those sources before they can answer basic questions about how the system works.

BEFORE

Information is scattered

Important facts live in many different files and tools. Some sources may be incomplete, outdated, or contradictory.

→
THE PROPOSED TOOL

Inspect and explain

The tool finds relevant evidence, checks what each source proves, identifies uncertainty, and organizes the findings for a reader.

→
AFTER

One useful system guide

The reader sees the system’s architecture, behavior, deployment, security, configuration, monitoring, operation, failures, and recovery.

In this repository, the project is called create_system_doc. Its files are located in plans_internal/create_system_doc/.
02 · Why the idea became reusable

The same documentation problem exists across many AI systems

During the design process, the project owner recognized that this should not be a one-time solution for a single system. Many systems built as connected steps, tools, decisions, and data flows have the same documentation problem. The owner therefore chose to make the solution reusable.

WHAT “GRAPH-BASED” MEANS

A system made of connected steps

One step may call a model, another may use a tool, and another may choose which step runs next. The connections form a workflow or graph.

WHAT “GENERIC” MEANS

Not tied to one application

The tool should work with different repositories, model providers, graph frameworks, and system designs.

WHAT “SKILL” MEANS HERE

A reusable set of instructions and tools

Instead of producing one document once, the capability can be used again whenever another system needs documentation.

This was an intentional project decision. The move from a one-time documentation idea to a reusable tool was triggered by the owner. It is not evidence that AI reviewers changed the project without permission.
03 · What has already been decided

The purpose of the tool is clear

Decided

Build a reusable documentation tool

It should work across different systems built from connected AI steps, tools, and data flows.

Decided

Make the documentation trustworthy

The guide must distinguish verified facts from assumptions, conflicts, missing evidence, and unknown behavior.

Decided

Serve real readers

The result should help designers, reviewers, maintainers, and authorized operators understand the system.

Decided

Support change over time

When the underlying system changes, its documentation should be updated safely instead of becoming stale.

04 · How the proposed solution grew

The project added machinery to make the tool reliable

The earliest document mainly described the guide readers should receive. Later versions tried to define a dependable process for producing that guide. Eleven versions now exist. The latest version proposes a complete workflow rather than a single AI prompt.

Later learning

The current proposal is create_system_doc specification version 11. The number simply means it is the eleventh iteration. It is relevant because it is the current design that would be built.
05 · What the current design would build

More than a document generator

If implemented as written, the project would create three coordinated AI skills and a set of machine-readable records that allow their work to be checked.

06 · What is actually uncertain

The goal is clear; the amount and shape of machinery are not

The concern is no longer whether the project should create a reusable tool. That decision is settled. The concern is whether the current design is the simplest, most portable, and most affordable way to do it well.

  1. Must there be exactly three skills?

    Planning, creation, and updating are real needs. They might still be separate stages inside one skill rather than three independently maintained skills.

  2. How much structured data is necessary?

    Machine-readable records improve reliability, but a very large schema may make small documentation jobs expensive and difficult to maintain.

  3. Is the design truly reusable?

    A reusable tool should not be unnecessarily tied to one AI provider, programming language, renderer, repository layout, or document format.

  4. Do all projects need the same controls?

    A public high-risk operations guide may need strict approvals. A small internal development guide may not need the full publication process.

  5. Will the extra machinery improve the guide?

    Every additional artifact, check, and approval should produce measurable gains in accuracy, safety, maintainability, or reader understanding.

  6. What will it cost to maintain?

    The project must account for implementation effort, model usage, human review, schema updates, fixture maintenance, and platform changes.

07 · What the research tells us

Repeated AI review can improve a design, but it cannot prove the design is right

The reusable research report, spec_review_drift.sota.v3.html, examined academic studies and current industry practice. Its findings are useful here, but they do not show that the current proposal is wrong.

Research findingMeaning for this project
Repeated AI rewriting may improve or distort an artifact.Eleven iterations are evidence of effort, not automatic proof that every added mechanism is necessary.
Two AI reviewers may share assumptions and blind spots.Codex and Claude reviewing the same evolving design does not replace testing that design on real systems.
Tests created from a design prove compliance with that design.The current automated tests are valuable, but they cannot prove that the chosen architecture is the best or simplest one.
Human review works only when the decision is understandable.The project should present a small set of architectural choices and real trade-offs rather than ask someone to approve hundreds of detailed rules at once.
Real-world evidence is stronger than additional debate.The next step should be small working trials, not another unbounded round of specification rewriting.
Plain conclusion: the research supports testing and simplifying the proposed implementation. It does not challenge the decision to build a reusable documentation tool.
08 · Recommended next step

Test the current design before building all of it

TEST 1

Use a small system

Document a simple graph-based AI system. Measure whether the full three-skill process adds useful reliability or mostly overhead.

TEST 2

Use a complex system

Document a system with branches, tools, state, deployment, security, and failure handling. See which controls become essential.

COMPARE

Run a simpler alternative

Compare the current design with one reusable skill containing clear planning, creation, and update stages plus a replaceable diagram tool.

MeasureQuestion
Reader usefulnessCan the intended reader correctly understand and use the resulting guide?
AccuracyAre factual claims supported, and are uncertainty and conflicts clearly marked?
PortabilityCan the tool work across different repositories, models, graph frameworks, and renderers?
CostHow much model usage, human review, runtime, and maintenance does each approach require?
RecoveryCan a failed or interrupted run resume safely without corrupting the guide?
Update qualityCan the tool update changed sections without damaging correct existing content?
Decision rule: keep the parts of the current design that measurably improve accuracy, safety, portability, maintainability, or reader understanding. Simplify or replace the parts that add cost without producing enough value.
09 · Final answer

What should happen now?

  1. Continue with the goal of building a reusable AI tool for documenting graph-based systems.
  2. Do not treat the move toward a reusable tool as accidental scope drift; it was an intentional decision.
  3. Do not immediately implement every detail in the current specification.
  4. Test the current three-skill design and a simpler alternative on one small and one complex system.
  5. Use the results to decide the final architecture before investing in the full implementation.

Recommendation: proceed with a limited prototype and comparison. The project idea is clear and worthwhile. The remaining task is to prove which implementation structure delivers that value without unnecessary complexity or platform dependence.
