Prompt Governance

How a "prompt" is authored, validated, executed and made restartable in curriculum_builder. Document version 2 — additive successor to v1 (governance.v1.html, retained byte-unchanged). v1 conflated "prompt" into only two categories and stated the meta-prompt as simply out of scope; v2 corrects that with a full artifact taxonomy (§1) — Plan, Meta-prompt and Prompt are three distinct artifacts, and the first two are upstream sources that produce the third, not unrelated siblings. 1. Artifact taxonomy: Plan, Meta-prompt, Prompt

This repo has three distinct artifact kinds that get loosely called "a prompt" in conversation. They are not interchangeable, and two of them exist specifically to produce the third. Only the third — Prompt — is what the rest of this document (the GOAL/TEST/LOOP shape, prompt.schema.v1/v2.json, the governance hook, the execution log) actually governs.

plans/<slug>/*.plan.v<N>.md		 A standalone description of a body of work — goal, QA'd design, ordered test plan — authored directly or via the plan-create skill's "plan-to-prompt pipeline." Not itself executed by an agent as a task. yes — by design. The plan-create skill's own description: it "writes an implementation plan … writes an ordered execution test plan, writes a Claude Code GOAL/TEST/LOOP implementation prompt." Concrete example: plans/19_curriculum_factory_production_loop_closure/curriculum_factory_production_loop_closure.plan.v1.yaml is the source plan; its prompts/P0_baseline_contract_freeze.prompt.v1.md through P6 are the Prompts it produced, one per phase. no — the plan document itself has no GOAL/TEST/LOOP shape and isn't executed as a task.
Meta-prompt

Checked by tests/check_meta_prompt.py, not by this document's schema. yes — by design. Its own §Companions requires and dispatches further prompt assets at runtime (e.g. meta_prompt/assets/model_selector_prompt.v1.md, "the selector's own prompt, read by the selector call") and a body of work implementing or repairing what it governs is itself turned into bounded phase Prompts the same way a Plan is (see plans/19_curriculum_factory_production_loop_closure/, whose phases implement production behavior the meta-prompt's contract requires). no — it is a standing contract read and re-executed indefinitely, not a bounded task with a stopping condition.
Prompt
prompts/<task>/*.prompt.v<N>.md, plans/<slug>/prompts/*.prompt.v<N>.md		 A one-off, bounded, GOAL/TEST/LOOP execution task, produced by a Plan or by work a meta-prompt's contract requires, run by Claude Code, expected to be idempotent and restart-safe. — yes — this document, §2–§8
The practical rule: if you're deciding whether something needs a GOAL, a TESTS array and a LOOP with a stopping condition, ask whether it is the thing being executed as a bounded task (a Prompt) or the thing that decided a task was needed (a Plan or the meta-prompt). Only the former is in scope below.

2. The GOAL/TEST/LOOP shape, and why

Every Prompt has three sections: GOAL (a concrete end state, not a topic), TESTS (one or more executable checks with a checkable expected result — never "looks right"), and LOOP (the steps taken each iteration, plus how the loop knows to stop).

This is not a house invention. Research conducted August 2026 (research/prompt_schemas/prompt_schema_state_of_the_art.v1.md) found the field independently converged on the same three-part shape in June 2026 under the name "loop engineering" — a loop specification is "a trigger, a goal, a verification step, a stopping rule and a memory." No external body publishes a machine-checkable schema for it, which is why this repo authors its own (§3). Each individual TEST follows the EARS pattern (WHEN [condition], THE SYSTEM SHALL [expected behavior]), the closest published precedent for making a single acceptance criterion unambiguous.

3. The prompt schema

schemas/prompt.schema.v1.json and schemas/prompt.schema.v2.json validate the structured form of a Prompt — a JSON object a parser would extract from the markdown — the same relationship execution_log.schema.v2.json has to the logger's JSONL output rather than to free text. Versioning follows the same convention as every other schema in schemas/, and this document follows it too: additive only, older versions retained byte-unchanged so anything already validated against them keeps validating.

v1 fields

FieldTypeRule
titlestring≥ 10 chars, includes the version.
goalstring≥ 20 chars — a concrete, testable end state.
testsarray of {description?, check, expected}≥ 1 item. check is an exact executable condition, never "go discover a check yourself."
loopobject {steps, stopping_condition, escalation?}stopping_condition is required — an explicit success/failure exit, not an open-ended loop.
authorized_pathsarray of stringOptional scope boundary; mirrors execution_log.schema.v2.json's act.authorized_paths.

v2 additions

Research into restart behaviour (research/prompt_restart_strategies/prompt_restart_strategies_state_of_the_art.v1.md) found this repo already has the right durable-journal primitive in execution_log.schema.v2.json's ACT/EXEC pairing and computed unclosed_starts — structurally identical to what Temporal, Restate, Inngest and LangGraph use for crash recovery — but nothing told a Prompt to actually use it. v2 closes that, plus adds required execution binding:

FieldTypeRule
modelenuminherit / haiku / sonnet / opus / fable. Never a non-Claude model id — see §4.
agentobject {execution_path, subagent_type?, reasoning?}execution_path ∈ claude_code_direct / claude_code_subagent / codex_plugin. subagent_type required when execution_path is claude_code_subagent.
loop.resume_checkstring≥ 20 chars. States how the loop distinguishes a closed ACT (reuse result), an unclosed ACT (resume that one step), and no log at all (genuine fresh start).
loop.retry_policyobject {auto_retry?, requires_fix?}Optional. Arrays of execution_log.schema.v2.json failure_type values, split into "safe to blindly retry" vs "needs a real fix first."

4. Model and agent binding

This environment has exactly two live subscriptions and no billed API key for anything, anywhere — confirmed empty: GEMINI_API_KEY, GOOGLE_API_KEY, ANTHROPIC_API_KEY, OPENAI_API_KEY. That is a standing constraint on this whole repo, not just Prompts, and agent.execution_path's enum is deliberately closed to match it:

  • claude_code_direct — content-generation and task-execution Prompts run as Claude Code itself, in the calling session, under the Claude subscription. This is the default for everything this document governs.
  • claude_code_subagent — delegated to a subagent via the Agent tool. Requires naming subagent_type, and if that's general-purpose or Explore, .claude/governance/subagent_cost.md additionally requires pinning a cheap model — general-purpose subagent calls alone previously accounted for 34% of total usage on work that was mechanical search, not reasoning.
  • codex_plugin — QA gates, review and judge steps only, invoked through the installed codex plugin under the ChatGPT Pro subscription. Never used for content-generation Prompts.
There is no fourth option. A Prompt that wants to "call Gemini" or any other API-billed model is not a configuration this schema can express — that has caused real, repeated frustration in this repo's history and is intentionally unrepresentable now, not just discouraged.

5. Restart and resumability

Every Prompt run through runtime.logger.ExecutionLogger gets an append-only, schema-validated execution_log.jsonl: one record per .start() (status started, result pending) and one per .complete() or .fail() that closes it. audit() computes unclosed_starts — every started id with no matching close — which is exactly a crashed/interrupted step.

A v2-conformant Prompt's loop.resume_check must say, concretely:

  1. Does execution/execution_log.jsonl already exist for this task instance? If not: fresh start, run steps from the top.
  2. If it exists: read every record. For each id that is closed (an ACT completion/skip, or an EXEC), treat that step as done — reuse its recorded result/what_failed rather than re-running it.
  3. For any id in unclosed_starts: that is the interrupted step. Resume from that step, not from step 1.
  4. Only auto-retry a failed step if its failure_type is infrastructure-shaped (tool-error) and the step is provably idempotent — re-running apply_rebrand.sh's case-preserving substitution against already-rebranded text is a no-op, which is what makes it safe to blindly re-run on resume. A wrong-output or bad-input failure needs a diagnosis and a fix, never a blind retry.

6. Enforcement: the governance hook

.claude/hooks/check_prompt_governance.sh is a PreToolUse hook, wired in .claude/settings.json, that runs on every Write/Edit to a file matching *.prompt(.v<N>)?.md — which today means it also fires on Plan-produced phase prompts and would fire on any meta-prompt-derived one, since the hook matches on filename pattern, not on which artifact in §1 produced the file. It currently enforces exactly one rule and blocks the write (exit 2) on violation:

A general-purpose or Explore subagent delegation inside a prompt file must have a model: override within 5 lines, or the write is rejected. It is a text-window heuristic, not a parser — false positives are possible, and it prints the offending line.

It does not yet validate against prompt.schema.v1.json/v2.json at all. A Prompt can currently be written with no GOAL, zero TESTS, no resume_check, or an unrepresentable model, and nothing blocks it except this document and human review. See §8.

7. Worked example: prompts/rebrand_system

The rebrand-to-"Curriculum Factory" task is the first Prompt built end to end against this system, and is the concrete case every rule above was derived from or tested against. It was authored directly rather than produced by a Plan or the meta-prompt, which §1 also allows — the taxonomy states what can produce a Prompt, not that every Prompt must have one of those two upstream sources.

FileRole
rebrand_curriculum_factory.prompt.v1.mdThe GOAL/TEST/LOOP prompt itself.
assets/find_old_name_references.shCode-derived discovery — every target file/path is found by git grep/test -e, never left to agent judgment.
assets/apply_rebrand.shIdempotent, case-preserving phrase substitution — the concrete example cited in §5 for why blind retry is safe here.
assets/run_rebrand_with_log.pyEntrypoint. Runs both scripts above, runs all five acceptance TESTS, and logs every step via ExecutionLogger.

This prompt predates prompt.schema.v2.json and is not yet updated to declare model, agent, or loop.resume_check — see §8.

8. Known gaps

GapStatus
No markdown → JSON extractor exists to turn a Prompt file into the object prompt.schema.v1/v2.json actually validates. not built
check_prompt_governance.sh does not call that extractor or the schema at all — only the subagent-cost rule is enforced today, and it fires on filename pattern alone rather than distinguishing which of §1's producing artifacts (or none) the file came from. not built
prompts/rebrand_system/rebrand_curriculum_factory.prompt.v1.md is not yet updated to v2 shape (model, agent, loop.resume_check). v1-shaped only
Restart procedure (§5) is documented and grounded in research, but no Prompt in this repo has actually exercised a real mid-run crash and resume yet — it is a designed, untested contract. designed, unverified
§1's Plan → Prompt and Meta-prompt → Prompt relationships are described narratively; no schema or tooling actually records, on a Prompt file, which Plan or meta-prompt (if any) produced it. not built
